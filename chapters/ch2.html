Chapitre 2 · Java SE 27 Edition

Grammaires

La spec décrit Java avec deux grammaires hors contexte empilées : l'une fabrique des jetons à partir de caractères, l'autre fabrique des programmes à partir de jetons. Savoir lire leur notation est indispensable pour tous les chapitres suivants.

Source : JLS SE 27, chapitre 2 Sections : 2.1 à 2.4

§2.1Grammaires hors contexte

Une grammaire hors contexte est un ensemble de productions. Chaque production a un côté gauche, un seul symbole non terminal, et un côté droit, une suite de symboles terminaux et non terminaux. Pour chaque grammaire, les terminaux sont tirés d'un alphabet fixé.

On part d'un symbole particulier, le symbole but (goal symbol), puis on remplace de façon répétée un non-terminal par le côté droit d'une de ses productions. Le langage défini par la grammaire est l'ensemble de toutes les suites de terminaux qu'on peut obtenir ainsi.

Note non normative

« Hors contexte » signifie qu'un non terminal se remplace de la même façon quel que soit ce qui l'entoure. C'est pour ça que certaines règles de Java ne peuvent pas être dans la grammaire : « une variable doit être déclarée avant usage » dépend du contexte, et c'est le rôle des chapitres 6, 15 ou 16, pas de la grammaire.

§2.2La grammaire lexicale

La grammaire lexicale, présentée au chapitre 3, a pour terminaux les caractères Unicode (§3.1). Ses productions décrivent comment une suite de caractères se découpe en éléments d'entrée : espaces, commentaires et jetons (§3.5). Les jetons sont les identifiants, mots-clés, littéraux, séparateurs et opérateurs.

Son symbole but est Input (§3.5). Dans la spec, une production lexicale se reconnaît à ses deux deux-points :: entre le nom et sa définition.

Production lexicale (forme simplifiée)
DecimalNumeral ::
    0
    NonZeroDigit [Digits]
    NonZeroDigit Underscores Digits

§2.3La grammaire syntaxique

La grammaire syntaxique a pour terminaux les jetons produits par la grammaire lexicale. Elle décrit comment une suite de jetons forme un programme syntaxiquement correct. Son symbole but est CompilationUnit (§7.3). Ses productions utilisent un seul deux-points :.

Production syntaxique
IfThenElseStatement:
    if ( Expression ) StatementNoShortIf else Statement

Elle est présentée morceau par morceau aux chapitres 4, 6 à 10, 14 et 15, puis rassemblée au chapitre 19.

Règle · la grammaire ne suffit pas

Une suite de jetons acceptée par la grammaire syntaxique n'est pas forcément un programme correct. Des règles supplémentaires, écrites en prose dans les autres chapitres, la restreignent encore. La grammaire accepte int x = "a"; ; c'est le §5.2 qui le rejette.

Une grammaire pensée pour l'exposé

Les productions des chapitres 4 à 15 servent à expliquer, pas à construire un analyseur : elles ne sont pas conçues pour un algorithme d'analyse particulier (LL, LALR…). Un compilateur réel réécrit souvent la grammaire et doit gérer plusieurs ambiguïtés que la spec traite à part.

Le « else pendant »Dans if (a) if (b) x(); else y();, à quel if appartient le else ? Java le résout dans la grammaire avec le non terminal StatementNoShortIf (§14.5) : le else se rattache au if le plus proche.
Le chevron doubleDans List<List<String>>, le lexique voit le jeton >> (décalage). La spec précise qu'en contexte de type, ces caractères se lisent comme deux > (§3.2).
Cast ou expression ?(a) - b est-il un cast de -b vers le type a, ou une soustraction ? La grammaire du cast (§15.16) n'accepte après (Type) qu'une UnaryExpressionNotPlusMinus pour les types référence : c'est donc une soustraction.
Comparaison ou génériques ?f(a < b, c > (d)) pourrait se lire comme un appel générique a<b,c>(d). Java exige le point dans un appel générique explicite (X.<T>m()), ce qui lève l'ambiguïté.

§2.4La notation de la grammaire

La spec utilise une notation compacte, variante de la forme de Backus-Naur. Les terminaux sont en chasse fixe, les non terminaux en italique. Comment la grammaire encode la priorité des opérateurs

Java n'a pas de « table de priorité » normative : la priorité découle de la structure des productions d'expression (§15.2 et suivants). Chaque niveau de priorité est un non terminal qui se décompose en éléments du niveau immédiatement supérieur :

Chaîne des expressions (extrait, §15)
AdditiveExpression:
    MultiplicativeExpression
    AdditiveExpression + MultiplicativeExpression
    AdditiveExpression - MultiplicativeExpression

MultiplicativeExpression:
    UnaryExpression
    MultiplicativeExpression * UnaryExpression
    MultiplicativeExpression / UnaryExpression
    MultiplicativeExpression % UnaryExpression

Deux conséquences se lisent directement dans ces lignes. * lie plus fort que +, car un opérande de + peut contenir un *, jamais l'inverse sans parenthèses. Et la récursivité à gauche (AdditiveExpression apparaît à gauche de +) rend l'opérateur associatif à gauche : a - b - c vaut (a - b) - c. L'affectation, elle, est récursive à droite : a = b = c vaut a = (b = c).

Piège classique

Parce que la priorité vient de la grammaire, des opérateurs « voisins » peuvent surprendre. a & b == c se lit a & (b == c) : l'égalité est plus haut dans la chaîne que le & binaire, héritage du C. Utilisez la figure pour le vérifier, puis mettez des parenthèses dans votre code.

Récapitulatif : lire une production de la spec

Exemple réel (§14.14.2, simplifié)
EnhancedForStatement:
    for ( LocalVariableDeclaration : Expression ) Statement
  1. Le nom avant : est le non terminal défini : EnhancedForStatement.
  2. Un seul : : c'est une production syntaxique, ses terminaux sont des jetons.
  3. for, (, : et ) sont des terminaux : ils apparaissent tels quels dans le code.
  4. LocalVariableDeclaration, Expression et Statement sont définis ailleurs (§14.4, §15.2, §14.5).
  5. La grammaire autorise for (int x : 42) ;. C'est la prose du §14.14.2 qui exige que l'expression soit un Iterable ou un tableau.
