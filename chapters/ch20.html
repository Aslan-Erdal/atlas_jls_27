Collections

Le framework de collections de java.util : les interfaces qui définissent les contrats, les implémentations qui les réalisent, leur coût réel, et les règles (égalité, ordre, immuabilité, concurrence) qui font la différence entre un code correct et un code qui marche par hasard.

Référence : API Java SE 27, java.util Liens avec la JLS : §4.5, §14.14.2, §8.9.3

20.1La hiérarchie des interfaces

Le framework sépare les contrats (interfaces) des implémentations (classes). Déclarez vos variables et paramètres avec l'interface la plus générale qui suffit (List, Map, voire Collection), et choisissez l'implémentation à un seul endroit : la création.

À retenir

Map n'est pas une Collection : elle associe des clés à des valeurs. On la parcourt par ses vues keySet(), values() et entrySet(), qui sont des collections reliées à la map (les modifier modifie la map).

20.2Les collections séquencées (Java 21)

Avant Java 21, obtenir le premier ou le dernier élément dépendait du type : list.get(0), deque.getFirst(), sortedSet.first(), linkedHashSet.iterator().next()… Les interfaces SequencedCollection, SequencedSet et SequencedMap unifient tout ça pour les collections qui ont un ordre de rencontre défini.

Java 21+
List<String> l = new ArrayList<>(List.of("a", "b", "c"));
l.getFirst();       // "a"
l.getLast();        // "c"
l.addFirst("z");    // [z, a, b, c]
l.reversed();       // vue inversée [c, b, a, z] : pas de copie

LinkedHashMap<String, Integer> m = new LinkedHashMap<>();
m.put("un", 1); m.put("deux", 2);
m.firstEntry();     // un=1
m.pollLastEntry();  // retire et renvoie deux=2
m.putFirst("zéro", 0);   // insère en tête

List.of(1, 2).addFirst(0);   // UnsupportedOperationException : liste immuable

Pièges classiques

LinkedList est rarement le bon choix : son accès indexé est en O(n), et même ses insertions « O(1) » sont souvent plus lentes qu'un ArrayList à cause de la mémoire dispersée. Pour une file ou une pile, prenez ArrayDeque (et jamais la vieille classe Stack).

list.remove(1) sur une List<Integer> retire l'élément d'index 1, pas la valeur 1 : la surcharge remove(int) est choisie en phase stricte (§15.12.2). Pour la valeur : list.remove(Integer.valueOf(1)).

20.4HashMap de l'intérieur

Une HashMap est un tableau de compartiments (buckets). Pour placer une clé :

  1. calculer h = key.hashCode() ;
  2. mélanger les bits de poids fort dans les bits faibles : h ^ (h >>> 16) ;
  3. prendre l'index (n - 1) & h, où n (la capacité) est une puissance de 2 ;
  4. dans ce compartiment, chercher une clé equals : la remplacer, sinon l'ajouter.

Quand le nombre d'entrées dépasse capacité × 0,75 (le facteur de charge), le tableau double et toutes les entrées sont redistribuées. Si un compartiment contient trop de collisions (8 entrées, dans une table d'au moins 64 cases), sa liste devient un arbre équilibré : le pire cas passe de O(n) à O(log n).

20.5Le contrat equals / hashCode

Contrat de Object

Si a.equals(b), alors a.hashCode() == b.hashCode(). L'inverse n'est pas exigé (les collisions sont permises). equals doit être réflexif, symétrique, transitif et cohérent, et x.equals(null) doit renvoyer false.

Java
class Point {
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) {
        return o instanceof Point p && x == p.x && y == p.y;
    }
    // hashCode oublié !
}
Set<Point> s = new HashSet<>();
s.add(new Point(1, 2));
s.contains(new Point(1, 2));   // false (presque toujours) : les deux objets ont des hashCode différents

record PointR(int x, int y) { }  // equals ET hashCode générés correctement (§8.10.3)
Clés mutables

Ne modifiez jamais un champ utilisé par hashCode pendant qu'un objet est clé d'une HashMap ou élément d'un HashSet : il reste rangé dans l'ancien compartiment et devient introuvable, même par contains sur lui-même.

20.6Ordre : Comparable et Comparator

Comparable<T> définit l'ordre naturel d'une classe (String, Integer, LocalDate…). Comparator<T> définit un ordre externe, composable :

Java
record Personne(String nom, String prenom, int age) { }

Comparator<Personne> ordre = Comparator
    .comparing(Personne::nom)
    .thenComparing(Personne::prenom, String.CASE_INSENSITIVE_ORDER)
    .thenComparingInt(Personne::age)
    .reversed();

personnes.sort(ordre);
TreeSet<Personne> tries = new TreeSet<>(ordre);
Comparator.nullsFirst(Comparator.<String>naturalOrder());   // gérer les null

(a, b) -> a.age() - b.age();       // piège : débordement si les valeurs sont grandes et de signes opposés
Integer.compare(a.age(), b.age()); // correct
Cohérence avec equals

Un TreeSet ou une TreeMap considère deux éléments égaux si le comparateur renvoie 0, sans appeler equals. Un comparateur qui ne compare que le nom fera disparaître les homonymes. new BigDecimal("1.0") et new BigDecimal("1.00") : égaux pour compareTo, différents pour equals, donc un élément dans un TreeSet, deux dans un HashSet.

20.8Itération et modification

Les itérateurs de ArrayList, HashMap… sont fail-fast : si la collection est modifiée structurellement pendant l'itération autrement que par l'itérateur, la prochaine opération lève ConcurrentModificationException (au mieux : ce n'est pas garanti).

Java
for (String s : liste) if (s.isBlank()) liste.remove(s);   // ConcurrentModificationException
liste.removeIf(String::isBlank);                           // correct

Iterator<String> it = liste.iterator();
while (it.hasNext()) if (it.next().isBlank()) it.remove();   // correct aussi

map.entrySet().removeIf(e -> e.getValue() == 0);
map.replaceAll((k, v) -> v * 2);
map.computeIfAbsent(cle, k -> new ArrayList<>()).add(valeur);   // regroupement en une ligne
map.merge(mot, 1, Integer::sum);                                  // compteur de fréquences
