Chapitre 17 · Java SE 27 Edition

Threads et verrous

Java est concurrent dès sa conception. Ce chapitre définit les moniteurs, wait/notify, l'interruption, et surtout le modèle mémoire : les règles qui disent quelles valeurs un thread peut lire quand d'autres écrivent en même temps.

Source : JLS SE 27, chapitre 17 Sections : 17.1 à 17.7

§17Threads

Un thread est représenté par un objet Thread ; le seul moyen d'en créer un est de passer par cette classe. Démarrer un thread (start()) exécute sa méthode run(). Plusieurs threads peuvent s'exécuter réellement en parallèle sur plusieurs cœurs, ou être entrelacés sur un seul.

Java
Thread t1 = new Thread(() -> travail("A"));       // thread de plateforme (thread de l'OS)
t1.start();
Thread t2 = Thread.ofVirtual().start(() -> travail("B"));   // thread virtuel (Java 21)
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10_000; i++) ex.submit(() -> appelReseau());
}
t1.join();     // attend la fin de t1 (et établit un happens-before, §17.4.4)
Note non normative

Les threads virtuels (Java 21) sont des objets Thread à part entière : toute la sémantique de ce chapitre s'applique à eux. Depuis Java 24 (JEP 491), un thread virtuel qui bloque dans un synchronized n'immobilise plus son thread porteur.

§17.1Synchronisation

Chaque objet possède un moniteur, qu'un seul thread à la fois peut détenir. Un thread peut verrouiller (lock) et déverrouiller (unlock) un moniteur ; les autres threads qui tentent de le verrouiller sont bloqués. Un thread peut verrouiller plusieurs fois le même moniteur (réentrance) ; chaque unlock annule un lock.

  • L'instruction synchronized (o) { … } (§14.19) verrouille le moniteur de o, exécute le bloc, puis le déverrouille, même en cas d'exception.
  • Une méthode synchronized (§8.4.3.6) verrouille le moniteur de this, ou de l'objet Class pour une méthode statique.

La spec ne détecte ni n'empêche les interblocages (deadlocks) : c'est au programme d'acquérir ses verrous dans un ordre cohérent. Les verrous de java.util.concurrent.locks offrent d'autres politiques (essai, délai, équité), mais leur sémantique mémoire est définie par l'API.

§17.2Ensembles d'attente et notification

Chaque objet a aussi un ensemble d'attente (wait set) : les threads qui ont appelé wait() sur cet objet.

§17.2.1wait

Appeler o.wait() sans détenir le moniteur de o lève IllegalMonitorStateException. Sinon, le thread est ajouté au wait set, libère complètement le moniteur (même s'il l'a verrouillé plusieurs fois), puis attend. Il en sort par notify, notifyAll, une interruption, l'expiration d'un délai, ou un réveil intempestif (spurious wakeup) que la spec autorise. Il reprend ensuite le moniteur avec le même nombre de verrous qu'avant. S'il a été interrompu, wait lève InterruptedException.

Java · le seul usage correct de wait
synchronized (verrou) {
    while (!condition) {            // TOUJOURS une boucle : réveils intempestifs et concurrents
        verrou.wait();
    }
    // la condition est vraie ET on détient le verrou
}

synchronized (verrou) {
    condition = true;
    verrou.notifyAll();             // notifyAll est plus sûr que notify si plusieurs conditions partagent l'objet
}

§17.2.2Notification

notify() retire un thread (non spécifié) du wait set ; notifyAll() les retire tous. Les threads réveillés ne peuvent continuer qu'après avoir repris le verrou, donc après que le notifiant l'a relâché.

§17.2.3Interruptions

t.interrupt() positionne le statut d'interruption de t. Si t est dans wait, sleep ou join, il en sort avec InterruptedException et le statut est effacé. Sinon, c'est au code de le tester (Thread.interrupted(), isInterrupted()). C'est le mécanisme standard d'annulation coopérative.

Piège

Ne jamais « avaler » une InterruptedException avec un catch vide. Soit on la propage, soit on restaure le statut : Thread.currentThread().interrupt();.

§17.2.4Interactions entre attente, notification et interruption

Si un thread en attente est à la fois notifié et interrompu, il peut soit sortir normalement (et rester interrompu), soit lever InterruptedException ; dans ce second cas, une autre notification ne doit pas être perdue : un autre thread du wait set doit la recevoir.

§17.3Sleep et yield

Thread.sleep(ms) suspend le thread sans libérer ses moniteurs. Thread.yield() suggère à l'ordonnanceur de laisser la main. Ni l'un ni l'autre n'a d'effet de synchronisation : le compilateur n'est pas obligé de relire les variables après un sleep.

Java · exemple de la spec
while (!this.fini)          // fini n'est pas volatile
    Thread.sleep(1000);
// Le compilateur peut lire this.fini UNE seule fois et boucler à l'infini,
// même si un autre thread met fini à true.  Solution : volatile boolean fini;

§17.4Le modèle mémoire

Un modèle mémoire décrit, pour un programme et une trace d'exécution, si cette trace est légale. Celui de Java ne dit pas comment exécuter le code : il dit quelles valeurs chaque lecture peut voir. Il laisse une grande liberté d'optimisation (réordonnancement par le compilateur, caches, tampons d'écriture des processeurs) tout en garantissant un comportement simple aux programmes correctement synchronisés.

Voici ce que cela signifie concrètement : un programme mal synchronisé peut produire des résultats impossibles par simple entrelacement.

§17.4.1Variables partagées

Seule la mémoire du tas est partagée entre threads : champs d'instance, champs statiques, composants de tableaux. Les variables locales, paramètres et paramètres d'exception ne sont jamais partagés. Deux accès à la même variable sont en conflit si l'un au moins est une écriture.

§17.4.2Actions

Le modèle raisonne sur des actions inter-threads : lecture et écriture (normale ou volatile), lock et unlock d'un moniteur, première et dernière action d'un thread (synthétiques), actions externes (entrées-sorties) et divergence (boucle infinie sans action). Les lectures volatiles, écritures volatiles, locks et unlocks sont des actions de synchronisation.

§17.4.3Programmes et ordre de programme

L'ordre de programme est l'ordre des actions d'un thread tel que décrit par la sémantique intra-thread (le reste de la spec). Une exécution est séquentiellement cohérente si toutes ses actions forment un ordre total compatible avec l'ordre de programme, chaque lecture voyant la dernière écriture précédente dans cet ordre. Java ne garantit pas la cohérence séquentielle en général : ce serait trop coûteux.

§17.4.4Ordre de synchronisation

Toutes les actions de synchronisation d'une exécution forment un ordre total, l'ordre de synchronisation. Il définit les relations synchronizes-with :

§17.4.5L'ordre happens-before

La relation happens-before (hb) est la fermeture transitive de l'ordre de programme et de synchronizes-with. Si x hb y, alors x est visible par y et ordonné avant y. Règles dérivées utiles :

  • la fin d'un constructeur hb le début du finaliseur de l'objet ;
  • les API de java.util.concurrent documentent leurs propres garanties (mettre dans une file concurrente hb en retirer ; Future.get voit le travail de la tâche ; etc.).
Définitions clés

Une course de données (data race) : deux accès en conflit à la même variable, non ordonnés par happens-before. Un programme est correctement synchronisé si aucune exécution séquentiellement cohérente ne contient de course de données.

Garantie centrale (DRF-SC) : si un programme est correctement synchronisé, toutes ses exécutions se comportent comme si elles étaient séquentiellement cohérentes. Le programmeur peut alors ignorer les réordonnancements.

Une exécution est cohérente avec happens-before si chaque lecture voit une écriture qui ne la suit pas en hb et qu'aucune autre écriture n'est intercalée en hb entre les deux. L'exemple 17.4.5-1 montre que cette cohérence autorise déjà le résultat surprenant de la figure 17.1.

§17.4.6Exécutions

Formellement, une exécution est un tuple : programme, ensemble d'actions, ordre de programme, ordre de synchronisation, fonction qui associe à chaque lecture l'écriture qu'elle voit, fonction de valeurs, synchronizes-with, happens-before.

§17.4.7Exécutions bien formées

Une exécution est bien formée si : chaque lecture voit une écriture de la même variable ; les lectures et écritures volatiles respectent l'ordre de synchronisation ; les locks et unlocks sont correctement imbriqués ; chaque thread respecte sa sémantique intra-thread ; et happens-before est cohérent.

§17.4.8Exécutions et exigences de causalité

La cohérence avec happens-before ne suffit pas : elle autoriserait des valeurs « sorties de nulle part » (out-of-thin-air), où une écriture se justifie elle-même par une lecture qui la voit (exemple 17.4.8-1 : r1 = x; if (r1 != 0) y = 1; et réciproquement ; le modèle interdit que x et y valent 1). La spec impose donc une procédure de validation : une exécution est légale si on peut la construire en engageant (committing) les actions progressivement, chaque étape étant justifiée par une exécution déjà cohérente.

Note non normative

Cette section est réputée l'une des plus difficiles de toute la spec, et la recherche a montré qu'elle n'interdit pas exactement ce qu'elle voudrait. En pratique : écrivez des programmes correctement synchronisés, et la garantie DRF-SC suffit.

§17.4.9Comportement observable et exécutions qui ne terminent pas

Le comportement observable d'un programme est défini par ses actions externes (entrées-sorties) et ses éventuelles boucles infinies. Une exécution qui ne termine pas peut avoir un comportement observable fini : un thread qui boucle sans fin ne doit pas empêcher les actions externes des autres d'être observées.

§17.5Sémantique des champs final

Les champs final bénéficient d'une garantie spéciale : un objet correctement construit (sa référence ne s'échappe pas pendant la construction) peut être partagé sans synchronisation, et tout thread qui obtient la référence voit les valeurs correctes de ses champs final, ainsi que des objets et tableaux qu'ils référencent, tels qu'à la fin du constructeur.

Java · exemple 17.5-1 reformulé
class Exemple {
    final int x;
    int y;
    static Exemple partage;
    Exemple() { x = 3; y = 4; }
    static void ecrivain() { partage = new Exemple(); }        // publication sans synchronisation
    static void lecteur() {
        if (partage != null) {
            int i = partage.x;    // garanti : 3
            int j = partage.y;    // PAS garanti : peut valoir 0
        }
    }
}

§17.5.1Sémantique formelle

À la fin du constructeur, une action de gel (freeze) a lieu pour chaque champ final. Tout thread qui lit la référence de l'objet après ce gel, sans l'avoir vue avant, voit les valeurs gelées. Le gel s'étend à tout ce qui est atteignable via le champ final au moment du gel (le contenu d'un tableau final int[] rempli dans le constructeur, par exemple).

Piège · fuite de this

Si le constructeur publie this (l'enregistre comme écouteur, le stocke dans un champ statique, démarre un thread qui l'utilise), un autre thread peut voir l'objet avant le gel : la garantie disparaît.

§17.5.2Lire des champs final pendant la construction

Le thread qui construit l'objet peut lire un champ final avant son affectation (via une méthode, §16.9) : il voit alors la valeur par défaut. Après l'affectation, il voit la nouvelle valeur.

§17.5.3Modifier ensuite des champs final

La réflexion (Field.setAccessible + set) et la désérialisation peuvent modifier un champ final après la construction. Les compilateurs étant autorisés à supposer que les champs final ne changent pas (exemple 17.5.3-1 : une lecture peut être déplacée ou mise en cache), d'autres threads, et même le thread courant, peuvent continuer à voir l'ancienne valeur.

Évolution

Le JDK s'oriente vers « final veut vraiment dire final » (JEP 500) : la modification de champs final par réflexion profonde émet désormais des avertissements, en vue d'être interdite par défaut. Les champs de records et de classes cachées ne sont déjà plus modifiables.

§17.5.4Champs protégés en écriture

System.in, System.out et System.err sont static final mais modifiables par System.setIn/setOut/setErr : ils sont dits protégés en écriture, et leurs lectures ne bénéficient pas des optimisations des champs final ordinaires.

§17.6Arrachement de mot (word tearing)

Chaque champ et chaque composant de tableau est une variable indépendante : écrire dans bytes[0] ne peut jamais modifier bytes[1], même si le processeur ne sait écrire que des mots de 32 ou 64 bits. Une JVM sur une telle architecture doit simuler les écritures fines, éventuellement au prix de performances (exemple 17.6-1).

§17.7Traitement non atomique de double et long

Règle

Une écriture d'un long ou d'un double non volatile peut être réalisée en deux écritures de 32 bits : un autre thread peut lire une valeur « mixte », moitié ancienne, moitié nouvelle. Les écritures et lectures de long et double volatile sont toujours atomiques, de même que celles des références et de tous les autres types primitifs.

Les JVM 64 bits actuelles rendent en pratique toutes ces écritures atomiques, mais la spec ne le garantit pas : déclarez volatile (ou utilisez AtomicLong) un long partagé sans verrou.

class Cache {
    private static volatile Ressource instance;          // volatile est INDISPENSABLE
    static Ressource get() {
        Ressource r = instance;
        if (r == null) {
            synchronized (Cache.class) {
                r = instance;
                if (r == null) instance = r = new Ressource();
            }
        }
        return r;
    }
}
// Sans volatile, un thread pourrait voir instance != null mais des champs non final
// de Ressource pas encore initialisés.  L'idiome du détenteur (§12.4.1) est plus simple.
