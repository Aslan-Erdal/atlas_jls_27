Chapitre 9 · Java SE 27 Edition

Interfaces

Une interface déclare un contrat que des classes sans lien entre elles peuvent remplir. Ce chapitre couvre ses membres (constantes, méthodes abstraites, default, static et private), l'héritage multiple et ses conflits, les annotations, et les interfaces fonctionnelles qui rendent les lambdas possibles.

Source : JLS SE 27, chapitre 9 Sections : 9.1 à 9.9

§9.1Déclarations d'interfaces

Il existe deux sortes d'interfaces : les interfaces normales (interface) et les interfaces d'annotation (@interface, §9.6). Une interface peut être de plus haut niveau, membre ou locale (depuis Java 16, une interface locale est permise dans un bloc).

§9.1.1Modificateurs d'interface

Annotations, public, protected, private, abstract, static, sealed, non-sealed, strictfp. Une interface n'est jamais final : ce serait absurde, elle n'existe que pour être implémentée.

  • §9.1.1.1 abstract : toute interface est implicitement abstraite ; le mot-clé est permis mais redondant et déconseillé.
  • §9.1.1.2 strictfp : sans effet depuis Java 17.
  • §9.1.1.3 static : une interface membre ou locale est implicitement static ; elle n'a jamais d'instance englobante.
  • §9.1.1.4 sealed et non-sealed : une interface sealed liste les classes et interfaces autorisées à l'étendre ou l'implémenter directement. Chaque sous-type autorisé est une classe (final, sealed ou non-sealed, ou un record/enum) ou une interface (sealed ou non-sealed).

§9.1.2Interfaces génériques

Comme les classes (§8.1.2) : interface Fonction<T, R> { R appliquer(T t); }. Les paramètres de type ne sont pas en portée dans les membres static.

§9.1.3Superinterfaces et sous-interfaces

Une interface peut étendre plusieurs interfaces : interface Lecteur extends AutoCloseable, Iterable<String>. Elle ne peut pas étendre une classe, et elle ne peut pas dépendre d'elle-même. Une interface sans clause extends n'a pas de superinterface, et Object n'est pas son supertype au sens de l'héritage (voir §9.2).

§9.1.4Sous-types directs autorisés

Clause permits d'une interface sealed, avec les mêmes règles que pour les classes (§8.1.6) : même module, extension directe, clause omise ⇒ sous-types déclarés dans la même unité.

§9.1.5Corps d'interface

Il contient des constantes, des méthodes, et des classes ou interfaces membres. Pas de constructeur, pas d'initialiseur, pas de champ d'instance : une interface n'a pas d'état propre.

§9.2Membres d'une interface

Les membres d'une interface sont ses membres déclarés et ceux hérités de ses superinterfaces directes. Une règle subtile concerne Object :

Règle · les méthodes implicites de Object

Une interface sans superinterface déclare implicitement une méthode abstraite publique pour chaque méthode public d'instance de Object (equals, hashCode, toString, getClass, notify…), sauf si elle déclare explicitement une méthode de même signature. C'est ce qui permet d'écrire monInterface.toString().

Redéclarer explicitement une méthode final de Object (getClass, wait…) est une erreur ; changer le type de retour d'une de ces méthodes aussi.

§9.3Champs (constantes)

Tout champ d'interface est implicitement public static final. Il doit avoir un initialiseur. Si deux superinterfaces fournissent un champ de même nom, l'utiliser par son nom simple est ambigu ; il faut le qualifier.

Java
interface Couleurs { int ROUGE = 1; }
interface Feux    { int ROUGE = 10; }
class Carrefour implements Couleurs, Feux {
    int f() { return ROUGE; }          // ERREUR : référence ambiguë
    int g() { return Feux.ROUGE; }     // OK
}
Note non normative

« Implémenter une interface pour hériter de ses constantes » (le constant interface antipattern) pollue l'API publique de la classe. Préférez une classe finale de constantes et un import static.

§9.3.1Initialisation des champs d'interface

Les champs sont initialisés quand l'interface est initialisée (§12.4). Mêmes restrictions de référence en avant que pour les classes. Une variable constante n'entraîne jamais l'initialisation : sa valeur est recopiée dans le code client.

Carre.unite();              // ERREUR : les méthodes static d'interface ne sont pas héritées
Règles

Une méthode d'interface ne peut pas être protected, ni à accès paquetage, ni final, synchronized ou native. Une méthode default ne peut pas avoir la signature d'une méthode publique de Object : default boolean equals(Object o) est interdit, car la classe gagnerait toujours (§9.4.1.3).

§9.4.1Héritage et redéfinition

Une interface I hérite des méthodes abstraites et default de ses superinterfaces qui ne sont pas redéfinies par une déclaration de I, ni déjà redéfinies par une autre superinterface de I (§9.4.1.1). Les exigences du §9.4.1.2 sont celles des classes : retour substituable, pas de nouvelles exceptions vérifiées.

§9.4.1.3Hériter plusieurs méthodes équivalentes : les règles de résolution

Les trois règles
  1. La classe gagne. Une méthode concrète héritée d'une superclasse l'emporte sur toute méthode default.
  2. L'interface la plus spécifique gagne. Si B étend A et que les deux fournissent un default, celui de B l'emporte.
  3. Sinon, c'est un conflit : la classe doit redéfinir la méthode, et peut appeler une version précise avec X.super.m().

§9.4.2Surcharge

Comme pour les classes : même nom, signatures non équivalentes. Aucune contrainte sur les types de retour ou les exceptions des surcharges.

§9.4.3Corps d'une méthode d'interface

Une méthode default, static ou private a un bloc ; une méthode abstraite, ;. Dans un default ou une private d'instance, this désigne l'objet qui implémente l'interface. super seul n'a pas de sens dans une interface ; seule la forme X.super.m() existe.

§9.5Classes et interfaces membres

Toute classe ou interface membre d'une interface est implicitement public et static. On s'en sert pour regrouper un type avec son contrat : Map.Entry, Thread.UncaughtExceptionHandler.

§9.6Interfaces d'annotation

Une interface d'annotation se déclare avec @interface. Elle définit un type d'annotation. Elle ne peut pas être générique, avoir de clause extends, ni être scellée ; sa superinterface implicite est java.lang.annotation.Annotation.

§9.6.1Éléments

Ses méthodes sont des éléments : sans paramètre, sans paramètre de type, sans throws. Leur type de retour est limité à : un type primitif, String, Class (éventuellement paramétré), un enum, une autre interface d'annotation, ou un tableau à une dimension de ces types.

§9.6.2Valeurs par défaut

Un élément peut avoir une valeur par défaut, qui doit être une expression constante (ou un littéral de classe, une constante d'enum, une annotation, un tableau de ceux-ci). null n'est jamais permis.

Java
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.METHOD, ElementType.TYPE})
public @interface Cache {
    String nom();                          // obligatoire à l'usage
    int dureeSecondes() default 60;
    Class<?>[] exclure() default {};
    Niveau niveau() default Niveau.LOCAL;  // enum
    String description() default "";      // null interdit : "" sert de « vide »
}

@Cache(nom = "produits", dureeSecondes = 300)
List<Produit> lister() { … }

§9.6.3Annotations répétables

Une annotation annotée @Repeatable(Conteneur.class) peut apparaître plusieurs fois au même endroit. Le compilateur regroupe les occurrences dans une annotation conteneur, dont l'élément value() est un tableau du type répétable. Le conteneur doit avoir une rétention au moins aussi longue et des cibles compatibles.

Java
@Repeatable(Roles.class)
@interface Role { String value(); }
@interface Roles { Role[] value(); }       // conteneur

@Role("admin") @Role("audit")              // stocké comme @Roles({@Role("admin"), @Role("audit")})
class Service { }
Service.class.getAnnotationsByType(Role.class);   // les deux @Role

§9.7Annotations

Une annotation associe des métadonnées à une construction du programme. Elle n'a aucun effet sur la sémantique du langage : ce sont les outils, le compilateur ou les frameworks qui l'exploitent.

§9.7.1 Normale@Cache(nom = "p", dureeSecondes = 30) : paires élément = valeur. Un tableau à un élément peut s'écrire sans accolades.
§9.7.2 Marqueur@Override : aucun élément (ou tous ont une valeur par défaut). Forme courte de @Override().
§9.7.3 Élément unique@SuppressWarnings("unchecked") : forme courte de value = "unchecked", si l'élément s'appelle value.

§9.7.4Où les annotations peuvent apparaître

Deux catégories : les annotations de déclaration (sur une classe, un champ, une méthode…) et les annotations de type (TYPE_USE, Java 8), qui s'appliquent à un usage de type dans l'un des 17 contextes du §4.11.

Java · annotations de type
@NonNull String nom;                  // si @NonNull cible TYPE_USE, il annote le type String
List<@NonNull String> noms;           // argument de type
String @NonNull [] tab;               // le TABLEAU est non nul (les éléments, eux, ne le sont pas forcément)
@NonNull String[] tab2;               // les ÉLÉMENTS sont non nuls
java.lang.@NonNull String q;          // dans un nom qualifié, l'annotation se place juste avant le nom simple
@NonNull java.lang.String r;          // ERREUR pour une annotation TYPE_USE seule : elle viserait le paquetage
Object o = (@NonNull Object) x;       // dans un cast
void m() throws @Critique IOException // dans throws
Règle · ambiguïté

Une annotation placée devant une déclaration de champ, de méthode, de paramètre ou de variable peut être à la fois une annotation de déclaration et une annotation de type, si ses cibles l'autorisent. Elle s'applique alors aux deux.

§9.7.5Plusieurs annotations du même type

Erreur, sauf si l'interface d'annotation est répétable (§9.6.3) : les occurrences sont alors regroupées dans un conteneur.

§9.8Interfaces fonctionnelles

Une interface fonctionnelle est une interface (non scellée) qui n'a qu'une seule méthode abstraite, en dehors des méthodes publiques de Object. Elle représente un contrat de fonction unique, et c'est le seul type cible possible pour une lambda (§15.27) ou une référence de méthode (§15.13).

Règles de comptage

Ne comptent pas : les méthodes default, static, private, et les méthodes abstraites qui correspondent à une méthode publique de Object. Si plusieurs méthodes abstraites héritées ont des signatures équivalentes et qu'une d'elles a un retour substituable à tous les autres, elles comptent pour une.

@FunctionalInterface n'est pas nécessaire pour qu'une interface soit fonctionnelle ; elle protège seulement contre l'ajout accidentel d'une deuxième méthode abstraite. Le paquetage java.util.function fournit les formes courantes :

§9.9Types de fonction

Le type de fonction d'une interface fonctionnelle I est ce qu'une lambda doit respecter : les types de paramètres, le type de retour et les exceptions de sa méthode abstraite unique, vus à travers le paramétrage de I. Pour un type paramétré avec jokers, comme Function<? super String, ? extends Number>, la spec dérive d'abord un paramétrage sans joker (non-wildcard parameterization, §9.9) : ici Function<String, Number>, donc le type de fonction String → Number.

Java
Function<? super String, ? extends Number> f = s -> s.length();
// paramétrage sans joker : Function<String, Number>
// type de fonction : (String) -> Number ; s est un String, s.length() (int) est boxé en Integer <: Number

interface Lecteur { String lire() throws IOException; }
Lecteur l = () -> Files.readString(Path.of("a.txt"));   // OK : le type de fonction autorise IOException
Supplier<String> s = () -> Files.readString(Path.of("a.txt"));  // ERREUR : get() ne lève rien de vérifié

Quand plusieurs méthodes abstraites héritées comptent pour une, leurs clauses throws sont intersectées : la lambda ne peut lever que ce que toutes autorisent.
