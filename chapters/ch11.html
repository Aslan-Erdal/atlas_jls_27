Chapitre 11 · Java SE 27 Edition

Exceptions

Quand un programme viole la sémantique du langage ou rencontre une situation anormale, le contrôle est transféré du point où l'exception est levée vers un point qui peut la traiter. Java vérifie à la compilation que les exceptions dites « vérifiées » sont toujours prises en charge.

Source : JLS SE 27, chapitre 11 Sections : 11.1 à 11.3

§11Le modèle

Une exception est un objet, instance de Throwable ou d'une sous-classe. Lever une exception provoque une terminaison abrupte des instructions et expressions en cours, jusqu'à trouver une clause catch qui l'accepte. Le modèle est sans reprise (non-resuming) : on ne revient jamais au point où l'exception a été levée.

Ce mécanisme est intégré au reste du langage : les blocs finally s'exécutent pendant la remontée, les verrous de synchronized sont relâchés, et les ressources d'un try-with-resources sont fermées.

§11.1Sortes et causes des exceptions

§11.1.1Les sortes d'exceptions

SorteSignificationFaut-il la traiter ?

§11.1.2Les causes des exceptions

Une exception est levée pour l'une de trois raisons :

  1. une instruction throw a été exécutée (§14.18) ;
  2. la JVM a détecté une condition d'exécution anormale :
    • une opération viole la sémantique du langage : division entière par zéro, accès via null, index hors bornes, cast invalide, stockage incompatible dans un tableau, taille de tableau négative… ;
    • une erreur de chargement ou de liaison (§12.2, §12.3) ;
    • une ressource manque, comme la mémoire.
  3. une exception asynchrone s'est produite (§11.1.3).

§11.1.3Exceptions asynchrones

La plupart des exceptions sont synchrones : elles surviennent à un point précis, comme effet d'une instruction. Une exception asynchrone peut survenir à n'importe quel point : une erreur interne de la JVM (VirtualMachineError). La spec autorise un léger délai pour qu'une implémentation la livre à un point bien défini. Historiquement, Thread.stop en provoquait aussi ; elle lève UnsupportedOperationException depuis Java 20, et l'interruption coopérative (interrupt(), §17.2.3) est la seule façon d'arrêter un thread.

§11.2Vérification des exceptions à la compilation

Le compilateur vérifie qu'un programme contient des gestionnaires pour les exceptions vérifiées. Pour cela, il calcule pour chaque expression et instruction l'ensemble des classes d'exceptions qu'elle peut lever.

§11.2.1Analyse des expressions

  • Un appel de méthode ou une création d'instance peut lever les exceptions de la clause throws de la méthode ou du constructeur choisi (après substitution des variables de type).
  • Une lambda ne lève rien en tant qu'expression : son corps est vérifié séparément, contre le type de fonction de sa cible (§9.9).
  • Une switch expression peut lever ce que ses expressions et ses throw peuvent lever.
  • Toute autre expression peut lever ce que ses sous-expressions peuvent lever.

§11.2.2Analyse des instructions

Une instruction throw e peut lever le type statique de e, avec une exception importante : le relancement précis (precise rethrow).

Règle · relancement précis

Si e est un paramètre de catch final ou effectivement final, throw e ne peut lever que les exceptions que le bloc try pouvait lever et que ce catch peut attraper, pas tout le type déclaré du paramètre.

Java
void f() throws IOException, SQLException {
    try {
        lireFichier();      // throws IOException
        requete();          // throws SQLException
    } catch (Exception e) {
        log(e);
        throw e;            // OK : le compilateur sait que e est une IOException ou une SQLException
    }
}

Une instruction try peut lever : ce que le bloc try peut lever et qu'aucun catch n'attrape, plus ce que les catch et le finally peuvent lever. Si le finally peut se terminer abruptement, il peut masquer tout le reste. Un try-with-resources ajoute les exceptions des méthodes close() de ses ressources.

§11.2.3Vérification des exceptions

Règles

Un corps de méthode ou de constructeur qui peut lever une exception vérifiée E doit la déclarer (E ou un supertype dans throws). Un initialiseur statique ou d'initialisation de champ statique ne peut lever aucune exception vérifiée. Un initialiseur d'instance ne peut lever une exception vérifiée que si tous les constructeurs la déclarent (et, pour une classe anonyme, elle peut lever n'importe quoi).

Une clause catch d'une exception vérifiée E1 est une erreur si le bloc try ne peut lever aucune exception vérifiée compatible avec E1, sauf si E1 est Exception ou une de ses superclasses. Un catch qui ne pourrait jamais rien attraper parce qu'un catch précédent couvre déjà son type est aussi une erreur.

§11.3Traitement d'une exception à l'exécution

Quand une exception est levée, le contrôle quitte l'instruction en cours et remonte : expressions, instructions, appels de méthodes, initialiseurs, jusqu'à la première clause catch dynamiquement englobante dont le paramètre peut recevoir l'exception (la classe de l'exception est la classe du paramètre ou une sous-classe). Pendant la remontée :

  • chaque finally traversé est exécuté ;
  • chaque moniteur d'une instruction ou méthode synchronized traversée est libéré ;
  • les ressources d'un try-with-resources sont fermées, dans l'ordre inverse de leur ouverture.

Si aucun gestionnaire n'est trouvé, le thread courant se termine : son UncaughtExceptionHandler (ou celui de son groupe, ou le gestionnaire par défaut) est appelé, et affiche par défaut la trace de pile.

Ce que la remontée ne fait pas

Pièges

Un finally qui fait return avale l'exception. Si le finally se termine abruptement (return, throw, break), l'exception en cours est perdue. Ne mettez jamais de return dans un finally.

Exception dans close(). Avec un try-with-resources, si le bloc et close() lèvent tous deux, l'exception de close() est ajoutée comme exception supprimée (getSuppressed()) à celle du bloc, au lieu de la remplacer.

Java
int f() {
    try { throw new IllegalStateException("perdue"); }
    finally { return 42; }          // f() renvoie 42, l'exception disparaît sans trace
}

try (var in = Files.newInputStream(p)) {
    throw new IOException("bloc");
} catch (IOException e) {
    e.getMessage();                 // "bloc"
    e.getSuppressed();              // contient l'éventuelle exception de close()
}

// chaîner les causes en convertissant une exception
try { … } catch (SQLException e) {
    throw new DonneesIndisponibles("lecture du client " + id, e);   // e devient getCause()
}
