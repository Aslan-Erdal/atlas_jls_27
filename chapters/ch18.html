Chapitre 18 · Java SE 27 Edition

Inférence de types

Quand vous écrivez List.of(1, 2), new HashMap<>() ou une lambda sans types, le compilateur doit deviner les types manquants. Ce chapitre décrit l'algorithme : des variables d'inférence, des contraintes réduites en bornes, des bornes combinées, puis résolues.

Source : JLS SE 27, chapitre 18 Sections : 18.1 à 18.5

§18Vue d'ensemble

L'inférence intervient dans quatre situations : choisir et typer un appel de méthode ou de constructeur générique (y compris le diamant), typer une lambda ou une référence de méthode, comparer deux méthodes génériques lors de la résolution de surcharge, et typer un motif d'enregistrement générique. Le processus a toujours la même forme :

§18.1Concepts et notation

§18.1.1Variables d'inférence

Les variables d'inférence, notées α, β, γ, sont des inconnues qui représentent les types à déterminer : un par paramètre de type de la méthode appelée. Elles ne sont jamais visibles dans le programme. Un type qui ne mentionne aucune variable d'inférence est dit propre.

§18.3Incorporation

Chaque fois qu'une borne est ajoutée, on la combine avec les bornes existantes pour en déduire de nouvelles formules. C'est ce qui propage l'information d'une variable à l'autre, et détecte les contradictions.

§18.3.2Bornes impliquant une capture

Une borne G<α1…> = capture(G<A1…>) est combinée avec les autres bornes des αi en tenant compte de la nature de chaque Ai (type, ?, ? extends, ? super). Elle permet, par exemple, d'inférer correctement le type de retour d'une méthode générique appelée sur une List<?>.

§18.4Résolution

Une fois toutes les contraintes réduites et incorporées, il faut choisir une valeur pour chaque variable. On résout les variables par groupes, dans l'ordre de leurs dépendances (α dépend de β si une borne de α mentionne β). Pour une variable α :

  1. si α a des bornes inférieures propres L1…Lk : α = lub(L1, …, Lk) (§4.10.4) ;
  2. sinon, si α a une borne throws α et ses bornes supérieures le permettent : α = RuntimeException ;
  3. sinon, avec des bornes supérieures propres U1…Uk : α = glb(U1, …, Uk), c'est-à-dire leur intersection ;
  4. si ces choix produisent false par incorporation, on recommence avec de nouvelles variables de capture (variables de type fraîches dont les bornes sont celles de α).

La préférence pour la borne inférieure explique pourquoi var l = List.of(1, 2) donne List<Integer> plutôt que List<Object>.

§18.5Usages de l'inférence

§18.5.1Inférence d'applicabilité

Pendant la résolution de surcharge (§15.12.2), on vérifie qu'une méthode générique est applicable. On crée les variables α, leurs bornes initiales, puis la formule ‹ei → Fi θ› pour chaque argument pertinent pour l'applicabilité. Ne sont pas pertinents : les lambdas à paramètres implicites, les références de méthodes inexactes, et ces mêmes formes imbriquées dans un conditionnel ou un switch. Leur type ne peut pas encore être déterminé ; ils seront traités à l'étape suivante. Si la réduction ne produit pas false, la méthode est applicable.

§18.5.2Inférence du type de l'invocation

Une fois la méthode choisie, on ajoute ce que l'applicabilité avait laissé de côté : la compatibilité du type de retour avec le type cible (§18.5.2.1, si l'appel est une poly-expression), puis les contraintes des arguments non pertinents, notamment les lambdas implicites (§18.5.2.2). On résout alors les variables : c'est le type final de l'appel.

Suivez l'inférence complète de deux appels :

§18.5.2.1Compatibilité d'une invocation poly

Si le type de retour R de la méthode mentionne ses paramètres de type et que l'appel a un type cible T, on ajoute ‹R θ → T›. Quelques cas particuliers évitent des inférences absurdes : si R θ est une variable α et que T est un type primitif, on infère d'abord α comme son enveloppe ; si T est un type référence paramétré et que α a une borne de capture, on résout α d'abord.

§18.5.2.2Contraintes supplémentaires sur les arguments

Pour chaque argument non pertinent à l'applicabilité (lambda implicite…), on ajoute ‹ei → Fi θ›. Ces contraintes sont traitées dans l'ordre de leurs dépendances : une lambda dont les types de paramètres dépendent de α ne peut être analysée qu'après la résolution de α. C'est ce qui permet l'inférence « de gauche à droite » de :

Java
Map<String, Integer> longueurs =
    mots.stream().collect(Collectors.toMap(m -> m, m -> m.length()));
// T de toMap est d'abord résolu à String (depuis Stream<String>) ;
// puis les lambdas sont typées : m : String ; K := String, U := Integer

Comparator<String> c = Comparator.comparing(s -> s.length());   // OK
Comparator<String> d = Comparator.comparing(s -> s.length()).reversed();
// ERREUR : sans type cible pour comparing(...), T est résolu à Object, et s.length() n'existe pas
Comparator<String> e = Comparator.comparing(String::length).reversed();   // OK : référence exacte
Pourquoi le dernier exemple échoue

Un appel en chaîne a().b() ne transmet pas le type cible de b() à a() : le récepteur d'un appel de méthode n'est jamais une poly-expression. Une lambda implicite y est donc typée sans information. Remèdes : référence de méthode exacte, paramètre de lambda typé (String s) -> …, ou argument de type explicite Comparator.<String, Integer>comparing(…).

§18.5.3Inférence du paramétrage d'une interface fonctionnelle

Quand une lambda à paramètres explicites cible un type avec jokers, comme Function<? super Integer, ?>, on infère le paramétrage à partir des types déclarés : (Integer i) -> … fixe le premier argument de type à Integer.

§18.5.4Inférence de la méthode la plus spécifique

Pour comparer deux méthodes génériques m1 et m2 lors de la résolution de surcharge (§15.12.2.5), on se demande si m2 pourrait accepter les paramètres de m1 : on crée des variables d'inférence pour les paramètres de type de m2 et on résout les contraintes ‹Si <: Ti›. Les arguments lambda font l'objet de règles spécifiques (comparaison des types de retour des types de fonction).

§18.5.5Inférence de type d'un motif d'enregistrement

Dans o instanceof Boite(var x) où Boite est un record générique, les arguments de type de Boite ne sont pas écrits : on les infère à partir du type de o. Si o est de type Boite<String>, le motif est Boite<String> et x est un String. Si o est un Object, on obtient un paramétrage avec joker, et x a pour type la borne supérieure : Object.

Java · exemple 18.5.5-1 reformulé
record Boite<T>(T contenu) { }
sealed interface Forme permits … { }

static void f(Boite<? extends Forme> b) {
    if (b instanceof Boite(var x)) {
        // motif inféré : Boite<CAP#1> ; x : CAP#1, dont la borne est Forme
        Forme forme = x;                       // OK
    }
}
