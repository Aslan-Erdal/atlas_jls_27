Chapitre 12 · Java SE 27 Edition

Exécution

Ce qui se passe quand un programme tourne : le démarrage de la JVM, le chargement, la liaison et l'initialisation des classes, la création des objets, leur récupération, le déchargement des classes et la fin du programme.

Source : JLS SE 27, chapitre 12 Sections : 12.1 à 12.8

§12Le cycle de vie d'une classe

Une classe ou interface passe par une suite d'états. La JLS décrit ce qu'elle impose au langage ; la JVMS (ch. 5) précise le reste.

§12.1Démarrage de la machine virtuelle

La JVM démarre en chargeant une classe initiale, désignée de façon dépendante de l'implémentation (en pratique, sur la ligne de commande : java Test), puis la lie, l'initialise, et appelle sa méthode main.

§12.1.1Charger la classe initiale

Si la JVM ne trouve pas de représentation binaire de la classe, ou que celle-ci est invalide, elle signale une erreur (ClassNotFoundException rapportée par le lanceur, ClassFormatError, UnsupportedClassVersionError si le fichier vient d'un JDK plus récent).

§12.1.2Lier : vérifier, préparer, (éventuellement) résoudre

Voir §12.3. La résolution peut être différée : une classe référencée par la classe initiale n'est chargée que lorsqu'elle est réellement utilisée, ce qui permet de démarrer même si une dépendance rarement utilisée manque.

§12.1.3Initialiser : exécuter les initialiseurs

L'initialisation de la classe initiale exécute ses initialiseurs statiques, après avoir initialisé sa superclasse. Voir §12.4.

§12.1.4Appeler une méthode main

Depuis Java 25 (JEP 512), la méthode main est plus souple. Une méthode est candidate si elle s'appelle main, n'est pas private, renvoie void, et a soit un seul paramètre String[], soit aucun paramètre. Elle peut être static ou d'instance, déclarée ou héritée.

Ordre de préférenceFormeComment elle est appelée
1main(String[] args) (static ou d'instance)avec les arguments de la ligne de commande
2main() (static ou d'instance)sans argument

Si la méthode choisie est d'instance, la classe doit avoir un constructeur non privé sans paramètre ; le lanceur crée une instance puis appelle main dessus.

Java · formes lançables
public static void main(String[] args) { }   // forme classique, toujours valide
static void main() { }                         // static sans paramètre
void main(String[] args) { }                   // d'instance
void main() { }                                // d'instance, sans paramètre (unités compactes)
private static void main(String[] a) { }       // non candidate : private

§12.2Chargement des classes et interfaces

Le chargement trouve la représentation binaire d'une classe à partir de son nom (dans un fichier, un JAR, une image de modules, ou même calculée à la volée) et construit l'objet Class qui la représente.

§12.2.1Le processus de chargement

Il est réalisé par des chargeurs de classes (ClassLoader). Ceux de la plateforme forment une hiérarchie : chargeur d'amorçage (bootstrap, pour java.base), chargeur de plateforme, chargeur d'application. Par convention, un chargeur délègue d'abord à son parent avant de chercher lui-même. Une classe est identifiée à l'exécution par son nom binaire et son chargeur définissant.

Erreur de chargementCause
ClassFormatErrorbinaire mal formé
UnsupportedClassVersionErrorversion de fichier non prise en charge (classe compilée pour un JDK plus récent, ou avec des previews d'une autre version)
ClassCircularityErrorla classe serait sa propre superclasse
NoClassDefFoundErroraucune définition trouvée pour une classe requise

§12.2.2Cohérence des chargeurs

Avec plusieurs chargeurs, le même nom peut désigner deux classes différentes. La JVM impose des contraintes de chargement (JVMS §5.3.4) pour qu'une méthode ne puisse pas recevoir, sous un même nom de type, des objets de deux classes distinctes : la sûreté du typage est préservée même entre chargeurs. Une violation produit une LinkageError.

§12.3Liaison des classes et interfaces

La liaison intègre la forme binaire dans l'état d'exécution de la JVM. Elle comporte trois activités ; la spec laisse à l'implémentation le choix du moment (immédiat ou paresseux), à condition que les erreurs soient signalées au point d'utilisation qui les déclenche.

§12.3.1Vérification de la représentation binaire

Le vérificateur s'assure que le bytecode est bien formé et sûr : types cohérents dans la pile d'opérandes, sauts vers des instructions valides, pas d'accès à des variables non initialisées, appels de méthodes avec les bons arguments. Il ne fait pas confiance au compilateur. Un échec lève VerifyError.

§12.3.2Préparation

Les champs statiques sont créés et mis à leur valeur par défaut (0, false, null). Aucun code Java n'est exécuté pendant la préparation : les initialiseurs viennent plus tard, à l'initialisation.

§12.3.3Résolution des références symboliques

Le binaire désigne les autres classes, champs et méthodes par des références symboliques (des noms). La résolution les remplace par des références directes, en chargeant les classes nécessaires. Les erreurs possibles sont des sous-classes de IncompatibleClassChangeError : IllegalAccessError, InstantiationError, NoSuchFieldError, NoSuchMethodError, AbstractMethodError. Elles apparaissent typiquement quand une bibliothèque a changé sans recompilation des clients (ch. 13).

§12.4Initialisation des classes et interfaces

Initialiser une classe, c'est exécuter ses initialiseurs statiques et les initialiseurs de ses champs statiques. Pour une interface, les initialiseurs de ses champs. L'initialisation est paresseuse : elle a lieu au premier usage actif, une seule fois.

§12.4.1Quand l'initialisation a lieu

Règle · les déclencheurs

Une classe ou interface T est initialisée juste avant la première occurrence de :

  • la création d'une instance de T (si T est une classe) ;
  • l'appel d'une méthode static déclarée par T ;
  • l'affectation d'un champ static déclaré par T ;
  • l'utilisation d'un champ static déclaré par T qui n'est pas une variable constante (§4.12.4).

Initialiser une classe initialise d'abord sa superclasse (et les superinterfaces qui déclarent des méthodes default). Certaines méthodes de réflexion (Class.forName) déclenchent aussi l'initialisation.

Java · l'idiome du détenteur paresseux
class Ressource {
    private Ressource() { /* coûteux */ }
    private static class Detenteur {            // pas initialisée tant qu'on ne la touche pas
        static final Ressource INSTANCE = new Ressource();
    }
    static Ressource get() { return Detenteur.INSTANCE; }  // 1er appel : initialise Detenteur, une seule fois
}
// Paresseux ET sûr entre threads : la procédure du §12.4.2 garantit l'exclusion mutuelle.

§12.4.2La procédure détaillée d'initialisation

Plusieurs threads peuvent tenter d'initialiser la même classe en même temps, et l'initialisation d'une classe peut en déclencher récursivement d'autres. La spec donne une procédure précise, fondée sur un verrou d'initialisation LC propre à chaque classe C :

Pièges

Interblocage d'initialisation. Si le thread 1 initialise A, qui touche B, pendant que le thread 2 initialise B, qui touche A, chacun attend l'autre à l'étape 2 : les deux threads sont bloqués pour toujours. Évitez les dépendances circulaires entre initialiseurs statiques.

Classe partiellement initialisée. L'étape 3 permet à un initialiseur de voir des champs statiques encore à leur valeur par défaut :

Java
class Singleton {
    static final Singleton INSTANCE = new Singleton();   // s'exécute EN PREMIER
    static int compteur = 0;                              // s'exécute ensuite : remet à 0 !
    Singleton() { compteur++; }
}
Singleton.compteur;   // 0, pas 1 : l'ordre textuel des initialiseurs compte

§12.5Création de nouvelles instances

Une instance est créée explicitement par new, ou implicitement (chargement d'un littéral chaîne, concaténation, boxing…). La mémoire est allouée pour tous les champs de la classe et de toutes ses superclasses ; s'il n'y en a pas assez, OutOfMemoryError. Tous les champs reçoivent leur valeur par défaut, puis le constructeur indiqué est exécuté selon cette procédure :

  1. Affecter les arguments aux paramètres du constructeur.
  2. S'il contient un appel explicite this(…) : exécuter son prologue, puis évaluer les arguments et traiter récursivement l'autre constructeur avec ces cinq étapes ; puis aller à l'étape 5.
  3. Sinon (classe autre que Object) : exécuter le prologue, puis l'appel super(…) explicite ou implicite, traité récursivement avec ces cinq étapes.
  4. Exécuter les initialiseurs d'instance et les initialiseurs de champs d'instance de cette classe, dans l'ordre textuel.
  5. Exécuter le reste du corps (l'épilogue).

La figure 8.2 (§8.8.7) déroule cette procédure pas à pas, y compris l'appel d'une méthode redéfinie depuis le constructeur de la superclasse. Contrairement à C++, la liaison dynamique fonctionne pendant la construction : la méthode de la sous-classe est appelée même si ses champs ne sont pas encore initialisés. L'exemple 12.5-3 de la spec montre comment le prologue (Java 25) permet de les initialiser à temps.

§12.6Finalisation des instances

Déprécié pour suppression

La finalisation (Object.finalize) est dépréciée pour suppression depuis Java 18 (JEP 421), et peut être désactivée avec --finalization=disabled. Elle reste décrite dans la spec, mais pour du code nouveau utilisez try-with-resources ou java.lang.ref.Cleaner.

Avant de récupérer un objet dont la classe redéfinit finalize, la JVM appelle ce finaliseur. La spec ne garantit ni quand il est appelé, ni sur quel thread, ni dans quel ordre par rapport aux autres finaliseurs, ni même qu'il sera appelé avant la fin du programme. Il est appelé au plus une fois par objet. Une exception qu'il lève est ignorée.

§12.6.1Implémentation de la finalisation

La spec définit des états d'atteignabilité (atteignable, atteignable par finaliseur, inatteignable) et de finalisation (non finalisé, finalisable, finalisé). Un finaliseur peut ressusciter un objet en stockant this quelque part ; il ne sera pas rappelé. Une optimisation peut rendre un objet inatteignable plus tôt que le code ne le laisse penser, dès que plus aucun calcul ne l'utilise.

§12.6.2Interaction avec le modèle mémoire

La fin d'un constructeur happens-before le début du finaliseur de l'objet (§17.4.5) : le finaliseur voit les écritures faites par le constructeur.

§12.7Déchargement des classes et interfaces

Une classe peut être déchargée si et seulement si son chargeur définissant peut être récupéré par le ramasse-miettes. Les classes du chargeur d'amorçage ne sont jamais déchargées. Le déchargement est invisible pour le programme, sauf par ses effets sur la mémoire : c'est pour ça qu'un serveur d'applications peut redéployer une application en jetant son chargeur.

§12.8Fin du programme

Un programme se termine quand l'une des situations suivantes se produit :

  • tous les threads qui ne sont pas des démons (setDaemon(true)) se sont terminés ; les threads démons sont alors arrêtés brutalement ;
  • un thread appelle Runtime.exit (ou System.exit) : les shutdown hooks enregistrés par Runtime.addShutdownHook s'exécutent, puis la JVM s'arrête ;
  • Runtime.halt arrête immédiatement, sans hooks.
Java
Runtime.getRuntime().addShutdownHook(Thread.ofPlatform().unstarted(() ->
    IO.println("fermeture propre")));          // exécuté sur exit ou Ctrl-C (SIGINT)

Thread t = Thread.ofPlatform().daemon(true).start(() -> { while (true) { } });
// main se termine : la JVM s'arrête malgré la boucle infinie, car t est un démon
