JVM et ramasse-miettes

La JLS décrit le langage ; la spécification de la machine virtuelle (JVMS) décrit le format .class et le bytecode. Entre les deux, HotSpot, l'implémentation de référence, ajoute ce qui fait les performances réelles : compilation à la volée, disposition des objets en mémoire et ramasse-miettes.

Les variables locales (§14.4) vivent dans la pile ; les objets qu'elles référencent, dans le tas. Grâce à l'analyse d'échappement, C2 peut toutefois supprimer l'allocation d'un objet qui ne sort pas de la méthode, en remplaçant ses champs par des variables locales (« scalar replacement »).

24.3Taille d'un objet en mémoire

Chaque objet commence par un en-tête : un mot de marque (hachage, état de verrou, âge pour le GC) et un pointeur vers sa classe. Avec les options par défaut sur 64 bits jusqu'à Java 26, il fait 12 octets. Les en-têtes compacts (JEP 450, production en Java 25 via JEP 519, par défaut en Java 27 via JEP 534) le réduisent à 8 octets. Les objets sont alignés sur 8 octets, et une référence occupe 4 octets tant que le tas reste sous 32 Gio (« compressed oops »).

Ordres de grandeur

Un Integer occupe 16 octets pour 4 octets utiles, un Long 16 ou 24. Une ArrayList<Integer> d'un million d'éléments pèse environ 20 Mo, contre 4 Mo pour un int[]. Pour de gros volumes de primitifs, les tableaux et les streams spécialisés (IntStream) évitent cette surcharge.

Les optimisations clés de C2 : inlining (insérer le corps d'une méthode appelée), appels virtuels rendus directs quand une seule implémentation est chargée, suppression des vérifications de bornes, déroulement et vectorisation de boucles, analyse d'échappement, élimination de verrous inutiles. Conséquence pratique : un microbenchmark naïf mesure souvent l'interpréteur ou du code éliminé. Utilisez JMH.

Pour réduire le temps de démarrage, le projet Leyden ajoute un cache AOT : une exécution d'entraînement enregistre les classes chargées et liées, des profils de méthodes et, depuis Java 26, des objets du tas.

Java 25+ · JEP 483, 514, 515, 516

java -XX:AOTCacheOutput=app.aot -jar app.jar
# 2. exécutions suivantes : démarrage et montée en régime plus rapides
java -XX:AOTCache=app.aot -jar app.jar

24.5Principes du ramasse-miettes

Un objet est vivant s'il est accessible depuis une racine : variables locales des piles, champs statiques, références JNI, moniteurs détenus. Tout le reste est récupérable, y compris les cycles d'objets qui se référencent entre eux (contrairement au comptage de références). Les étapes possibles sont : marquer les objets vivants, balayer les morts, compacter ou copier les vivants pour éviter la fragmentation.

L'hypothèse générationnelle constate que la plupart des objets meurent jeunes. Les collecteurs générationnels séparent donc une jeune génération, collectée souvent et à faible coût (on ne copie que les survivants), et une vieille génération, collectée rarement.

24.7Réglages essentiels et conteneurs

Options courantes
java -Xms2g -Xmx2g \                    # tas fixe : pas de redimensionnement
     -XX:MaxGCPauseMillis=100 \          # objectif de pause pour G1
     -Xlog:gc*:file=gc.log:time,uptime \ # journal de GC unifié (Java 9+)
     -XX:+HeapDumpOnOutOfMemoryError \   # image du tas en cas d'OOM
     -jar app.jar

# en conteneur : la JVM lit les limites cgroup (CPU, mémoire)
java -XX:MaxRAMPercentage=75 -jar app.jar   # défaut : 25 % de la mémoire du conteneur
java -XX:+PrintFlagsFinal -version | grep -E "UseG1GC|MaxHeapSize"

Le tas n'est qu'une partie de la mémoire du processus : il faut y ajouter Metaspace, piles, code cache, mémoire directe et structures du GC. Laissez donc une marge entre -Xmx et la limite du conteneur. -XX:NativeMemoryTracking=summary puis jcmd <pid> VM.native_memory détaille cette consommation.

La finalisation (§12.6) est dépréciée pour suppression (JEP 421) : exécution tardive, imprévisible, coûteuse. Pour libérer une ressource, utilisez AutoCloseable et try-with-resources ; en filet de sécurité, un java.lang.ref.Cleaner.

24.9Fuites mémoire en Java

Le GC ne récupère que ce qui est inaccessible. Une fuite Java est donc un objet encore référencé mais devenu inutile :

  • collections statiques ou caches sans limite ni éviction ;
  • écouteurs (listeners) enregistrés et jamais retirés ;
  • ThreadLocal jamais nettoyé dans un pool de threads ;
  • classes internes non statiques qui retiennent leur instance englobante (§8.1.3) ;
  • chargeurs de classes retenus après un redéploiement (fuite de Metaspace) ;
  • clés de HashMap dont hashCode change après insertion (section 20).

Diagnostic : la courbe du tas après chaque GC complet qui monte sans cesse, puis une image du tas (jcmd <pid> GC.heap_dump) analysée avec Eclipse MAT ou VisualVM. Les outils sont décrits à la section 25.
