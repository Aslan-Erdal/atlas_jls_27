22.2Threads de plateforme et threads virtuels

Depuis Java 21 (JEP 444), il existe deux sortes de threads. Un thread de plateforme est une enveloppe autour d'un thread du système d'exploitation : coûteux (une pile de l'ordre du mégaoctet, une création lente), donc limité à quelques milliers. Un thread virtuel est géré par la JVM : il est monté sur un thread porteur (carrier) quand il calcule, et démonté quand il bloque sur une entrée-sortie, libérant le porteur pour un autre.

Java 21+
Thread v = Thread.ofVirtual().name("worker-", 0).start(() -> traiter());
Thread p = Thread.ofPlatform().daemon(true).start(() -> surveiller());

try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {   // un thread virtuel par tâche
    List<Future<String>> fs = urls.stream().map(u -> ex.submit(() -> telecharger(u))).toList();
    for (var f : fs) afficher(f.get());
}   // close() attend la fin de toutes les tâches

Règles d'usage des threads virtuels
  • Ils accélèrent les tâches qui attendent (réseau, base de données, fichiers), pas le calcul pur : pour celui-ci, le nombre de cœurs reste la limite.
  • Ne les mettez jamais en pool : créez-en un par tâche. Pour limiter l'accès à une ressource rare (connexions), utilisez un Semaphore.
  • Méfiez-vous de ThreadLocal avec des millions de threads : préférez ScopedValue (24.9).
  • Depuis Java 24 (JEP 491), bloquer dans un synchronized ne monopolise plus le porteur. Un appel natif ou une méthode native sur la pile peut encore « épingler » le thread virtuel.

Piège

La file non bornée de newFixedThreadPool peut accumuler des millions de tâches et épuiser la mémoire. En production, construisez un ThreadPoolExecutor avec une file bornée (ArrayBlockingQueue) et une politique de rejet explicite (CallerRunsPolicy…).

Java
ExecutorService ex = new ThreadPoolExecutor(
    4, 8,                                    // cœur, maximum
    30, TimeUnit.SECONDS,                    // durée de vie des threads en surplus
    new ArrayBlockingQueue<>(1_000),         // file bornée
    Thread.ofPlatform().name("calcul-", 0).factory(),
    new ThreadPoolExecutor.CallerRunsPolicy());   // si plein : l'appelant exécute (régulation)

Future<Integer> f = ex.submit(() -> calculer());
f.get(2, TimeUnit.SECONDS);    // attend au plus 2 s : TimeoutException sinon
f.cancel(true);                // interrompt le thread qui l'exécute
ex.shutdown();                 // n'accepte plus de tâches
ex.awaitTermination(1, TimeUnit.MINUTES);

private final ReentrantLock verrou = new ReentrantLock();
private final Condition nonVide = verrou.newCondition();

void deposer(T x) {
    verrou.lock();
    try { file.add(x); nonVide.signal(); }
    finally { verrou.unlock(); }          // TOUJOURS dans un finally
}
T retirer() throws InterruptedException {
    verrou.lock();
    try {
        while (file.isEmpty()) nonVide.await();   // boucle, comme wait (§17.2.1)
        return file.remove();
    } finally { verrou.unlock(); }
}

22.6Variables atomiques

Les classes de java.util.concurrent.atomic exposent les instructions atomiques du processeur, sans verrou. Leur opération de base est le compare-and-set (CAS) : « remplace la valeur par v si elle vaut encore e ».

Java
AtomicInteger n = new AtomicInteger();
n.incrementAndGet();
n.updateAndGet(x -> Math.max(x, 10));        // fonction réessayée en boucle CAS : elle doit être sans effet de bord
n.compareAndSet(10, 11);                     // true si la valeur était 10

AtomicReference<Config> cfg = new AtomicReference<>(Config.DEFAUT);
cfg.set(nouvelle);                           // publication sûre (sémantique volatile)

LongAdder requetes = new LongAdder();        // plusieurs cellules : très peu de contention
requetes.increment();
long total = requetes.sum();

Pour du code de bas niveau (structures de données sans verrou), VarHandle donne accès aux mêmes opérations sur un champ ou un élément de tableau quelconque, avec différents niveaux d'ordre mémoire.

22.9Contexte partagé : ThreadLocal et ScopedValue

ThreadLocal donne à chaque thread sa propre copie d'une variable, mais elle est modifiable, vit aussi longtemps que le thread (fuites dans les pools) et coûte cher avec des millions de threads virtuels. ScopedValue (finalisé en Java 25, JEP 506) la remplace pour transmettre un contexte immuable à un appel et à tout ce qu'il appelle :

Java 25+
static final ScopedValue<Utilisateur> UTILISATEUR = ScopedValue.newInstance();

void traiterRequete(Requete r) {
    ScopedValue.where(UTILISATEUR, authentifier(r))
               .run(() -> controleur.executer(r));   // lié seulement pendant run
}
void journaliser(String msg) {
    String qui = UTILISATEUR.isBound() ? UTILISATEUR.get().nom() : "anonyme";
}

Les sous-tâches d'un StructuredTaskScope héritent automatiquement des valeurs liées : voir la section 27.4 pour la concurrence structurée, encore en preview en Java 27.
