Section 27 · Annexe de l'atlas

Les fonctionnalités preview de Java 27

Java 27 contient une preview de langage, trois previews d'API et un module en incubation. Cette section les décrit une par une : ce qu'elles font, leur état exact en Java 27, ce qui a changé depuis Java 25 et 26, et comment les essayer.

Spec : JLS 27 §1.5 État au 15 octobre 2026

27.1Vue d'ensemble

Rappel du §1.5 : une preview est entièrement spécifiée et implémentée, mais provisoire. Elle n'est disponible qu'avec --enable-preview, à la compilation et à l'exécution, et elle peut changer ou disparaître à la version suivante. Un module en incubation est autre chose : une API expérimentale livrée dans un module jdk.incubator.*, qu'on active avec --add-modules.

27.2Types primitifs dans les motifs, instanceof et switch

C'est la seule preview qui modifie la JLS. Avant elle, les motifs, instanceof et switch traitaient les types primitifs comme des citoyens de seconde zone : pas de switch sur un long, pas de motif int i au niveau supérieur, pas de instanceof vers un primitif. La preview unifie tout autour d'une seule question : la conversion est-elle exacte ?

Le principe : l'exactitude

Règles (document de preview, §5.7, §14.30, §15.20.2)

Un test v instanceof T ou un motif de type primitif T x réussit si la valeur v se convertit en T sans perte d'information : la conversion inverse redonne exactement la valeur de départ. Sinon, il échoue, sans exception et sans troncature.

Une conversion est inconditionnellement exacte si elle ne perd jamais d'information, quelle que soit la valeur : identité, et élargissements exacts comme byte → int, int → long, int → double, float → double. Un motif dont la conversion est inconditionnellement exacte est inconditionnel : il correspond toujours et rend un switch exhaustif.

Explorez les conversions : la matrice indique, pour chaque paire, si elle est inconditionnellement exacte (vert), exacte selon la valeur (orange) ou impossible (gris). Cliquez une case puis testez des valeurs.

instanceof avec un type primitif

Java 27 · --enable-preview
int i = 1000;
if (i instanceof byte b) { … }        // faux : 1000 ne tient pas dans un byte
if (i instanceof short s) { … }       // vrai : s == 1000

long horodatage = 1_700_000_000_000L;
if (horodatage instanceof int n) { … } // faux : dépasse Integer.MAX_VALUE

double d = 2.0;
if (d instanceof int n) { … }         // vrai : n == 2
if (-0.0 instanceof int n) { … }      // faux : le signe du zéro serait perdu
if (Double.NaN instanceof float f) { } // vrai : NaN se représente exactement en float

// Remplace la vérification manuelle de plage :
if (i >= Byte.MIN_VALUE && i <= Byte.MAX_VALUE) { byte b = (byte) i; … }   // avant
if (i instanceof byte b) { … }                                              // avec la preview

switch sur tous les types primitifs

Le sélecteur d'un switch peut être de n'importe quel type primitif, y compris long, float, double et boolean, avec des constantes et des motifs primitifs gardés :

Java 27 · --enable-preview
static String tranche(double montant) {
    return switch (montant) {
        case 0.0 -> "gratuit";
        case double m when m < 100   -> "petit";
        case double m when m < 1_000 -> "moyen";
        case double m                -> "grand";       // inconditionnel : rend le switch exhaustif
    };
}

static String etat(boolean actif) {
    return switch (actif) {
        case true  -> "actif";
        case false -> "inactif";                        // exhaustif sans default
    };
}

static String code(int statut) {
    return switch (statut) {
        case 200 -> "OK";
        case 404 -> "introuvable";
        case int s when s >= 500 -> "erreur serveur " + s;   // motif primitif au niveau supérieur
        case int s -> "autre " + s;
    };
}

Motifs primitifs imbriqués dans des records

Dans un motif d'enregistrement, un composant peut être testé contre un type primitif différent du sien, avec le même critère d'exactitude :

Java 27 · --enable-preview
sealed interface Json permits JsonNombre, JsonTexte { }
record JsonNombre(double valeur) implements Json { }
record JsonTexte(String valeur) implements Json { }

static String decrire(Json j) {
    return switch (j) {
        case JsonNombre(int n)    -> "entier " + n;      // seulement si valeur est un entier exact
        case JsonNombre(double d) -> "décimal " + d;
        case JsonTexte(String s)  -> "texte " + s;
    };
}
decrire(new JsonNombre(42.0));   // "entier 42"
decrire(new JsonNombre(4.2));    // "décimal 4.2"

Dominance : les règles plus strictes (depuis Java 26)

Une étiquette est interdite si une étiquette précédente accepte déjà toutes les valeurs qu'elle accepterait (§14.11.1). Avec les types primitifs, deux cas ont été ajoutés :

RègleExemple refuséCorrection
Une constante placée après un motif qui l'accepte est dominéecase float f -> …; case 16_777_216 -> …; (2²⁴ est un float exact)mettre la constante avant le motif
Toute étiquette placée après un motif inconditionnel est dominéecase int _ -> …; case float _ -> …;supprimer l'étiquette inaccessible
Piège

Avec --enable-preview, ce second contrôle s'applique aussi aux types référence : pour un sélecteur de type A, case A _ suivi de case B _ (B interface sans lien) compilait en Java 25 et est refusé depuis Java 26. Sans preview, ce code compile encore.

Exhaustivité

Un switch sur un primitif est exhaustif s'il a un default ou un motif inconditionnel pour le type du sélecteur : case long x pour un long. Attention, case double x ne l'est pas pour un long, car long → double peut perdre de la précision. Pour boolean, les deux constantes suffisent. En Java 27, l'erreur « does not cover all possible input values » nomme le motif qui manque, par exemple double _.

Java 27 · --enable-preview
long n = …;
switch (n) {
    case int i  -> …;      // les long qui tiennent dans un int
    case long l -> …;      // inconditionnel pour long : exhaustif
}
switch (n) {
    case int i    -> …;
    case double d -> …;    // ERREUR : long → double perd de la précision au-delà de 2^53, pas inconditionnel
}

Ce que la preview ne change pas

  • Les casts (byte) x gardent leur sémantique de troncature (§5.1.3) : seuls les tests et motifs vérifient l'exactitude.
  • Le boxing et l'unboxing restent ceux du ch. 5 ; un motif Integer i sur un sélecteur int utilise le boxing.
  • Le comportement des programmes qui n'utilisent pas la preview est inchangé.

27.3Lazy Constants (JEP 531, 3ᵉ preview)

Une constante paresseuse est une valeur calculée une seule fois, à la première demande, puis traitée par la JVM comme une vraie constante (elle peut être optimisée comme un champ final). Elle remplace les idiomes du détenteur (§12.4.1) et du double-checked locking (§17) pour les initialisations coûteuses.

Java 27 · --enable-preview
class Service {
    private final LazyConstant<Connexion> connexion =
        LazyConstant.of(() -> Connexion.ouvrir(config()));   // rien n'est calculé ici

    void envoyer(Message m) {
        connexion.get().envoyer(m);   // 1er appel : calcule et mémorise ; suivants : même instance
    }
}

// collections paresseuses : chaque élément est calculé à la première lecture
List<Page> pages = List.ofLazy(100, i -> chargerPage(i));
Map<Langue, Bundle> messages = Map.ofLazy(EnumSet.allOf(Langue.class), Bundle::charger);
Set<Pays> actifs = Set.ofLazy(tousLesPays, p -> p.estActif());   // nouveau en Java 27
VersionNom et API
Java 25 (JEP 502)StableValue, StableValue.list, StableValue.map
Java 26 (JEP 526)renommé LazyConstant : of(supplier), get(), isInitialized(), orElse(…) ; List.ofLazy, Map.ofLazy
Java 27 (JEP 531)ajout de Set.ofLazy ; suppression de isInitialized() et orElse(…) ; si le calcul échoue, get() lève NoSuchElementException à chaque appel, sans relancer le calcul
Points d'attention

La constante garantit une référence fixée, pas un objet immuable. LazyConstant n'est pas sérialisable. Et la variable qui la contient doit elle-même être final, sinon on peut la remplacer.

27.4Structured Concurrency (JEP 533, 7ᵉ preview)

La concurrence structurée traite un groupe de sous-tâches concurrentes comme une seule unité de travail : elles démarrent dans une portée, et la portée ne se termine qu'une fois toutes ses sous-tâches finies ou annulées. Une erreur dans l'une peut annuler les autres, et aucun thread ne survit à son bloc. Elle s'appuie sur les threads virtuels.

Java 27 · --enable-preview
Reponse commande(String id) throws InterruptedException {
    try (var scope = StructuredTaskScope.open(
            cfg -> cfg.withTimeout(Duration.ofSeconds(2)).withName("commande"))) {
        Subtask<Client> client     = scope.fork(() -> trouverClient(id));
        Subtask<List<Ligne>> lignes = scope.fork(() -> lignesCommande(id));
        scope.join();                                  // attend les deux ; si l'une échoue, l'autre est annulée
        return new Reponse(client.get(), lignes.get());
    } catch (ExecutionException e) {                   // Java 27 : remplace FailedException
        throw new IllegalStateException("échec de la commande", e.getCause());
    }
}
Changement en Java 27Effet
Les joiners standard lèvent ExecutionException au lieu de FailedExceptionles catch (FailedException e) doivent être réécrits
Troisième paramètre de type pour l'exception de join() : Joiner<T, R, R_X>sans effet pour open() ; les joiners personnalisés doivent le déclarer
Nouvelle surcharge open(UnaryOperator<Configuration>)politique par défaut avec délai, nom ou fabrique de threads, sans fournir de joiner

Les règles de structure restent : la portée s'utilise dans un try-with-resources, seul le thread propriétaire peut appeler fork et join (sinon StructureViolationException), et les sous-tâches héritent des ScopedValue liées.

27.5Encodages PEM (JEP 538, 3ᵉ preview)

Le format PEM (le texte entre -----BEGIN …----- et -----END …-----) est omniprésent pour les clés, certificats et listes de révocation. Jusqu'ici, Java n'avait pas d'API simple pour le lire ou l'écrire. La preview ajoute un encodeur et un décodeur dans java.security.

Java 27 · --enable-preview
KeyPair paire = KeyPairGenerator.getInstance("EC").generateKeyPair();

String pem = PEMEncoder.of().encodeToString(paire.getPublic());
// -----BEGIN PUBLIC KEY-----
// MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE…
// -----END PUBLIC KEY-----

PublicKey cle = PEMDecoder.of().decode(pem, PublicKey.class);
X509Certificate cert = PEMDecoder.of().decode(Files.readString(Path.of("cert.pem")), X509Certificate.class);
Changement en Java 27Effet
L'interface DEREncodable est renommée BinaryEncodablerenommer les usages
Le record PEM devient une classe ordinaire, avec des constructeurs acceptant un contenu Base64 en byte[]les déconstructions par motif d'enregistrement de PEM ne fonctionnent plus

27.6Vector API (JEP 537, 12ᵉ incubateur)

Ce n'est pas une preview mais une API en incubation : elle permet d'exprimer des calculs vectoriels (SIMD) que la JVM compile en instructions vectorielles du processeur. Elle reste en incubation en attendant les classes valeur du projet Valhalla.

Java 27 · --add-modules jdk.incubator.vector
static final VectorSpecies<Float> ESP = FloatVector.SPECIES_PREFERRED;

static void somme(float[] a, float[] b, float[] c) {
    int i = 0;
    for (; i < ESP.loopBound(a.length); i += ESP.length()) {
        var va = FloatVector.fromArray(ESP, a, i);
        var vb = FloatVector.fromArray(ESP, b, i);
        va.add(vb).intoArray(c, i);              // plusieurs additions en une instruction
    }
    for (; i < a.length; i++) c[i] = a[i] + b[i];   // reste scalaire
}

27.7Essayer les previews de Java 27

Terminal
javac --release 27 --enable-preview -Xlint:preview Main.java
java --enable-preview Main

# lanceur de fichier source
java --enable-preview --source 27 Main.java

# Vector API (incubateur, sans --enable-preview)
javac --add-modules jdk.incubator.vector Calcul.java
java  --add-modules jdk.incubator.vector Calcul

jshell --enable-preview
Bonnes pratiques
  • Réservez les previews aux essais, aux prototypes et aux retours vers OpenJDK, pas au code de production ni aux bibliothèques publiées.
  • Isolez le code preview dans un module ou un répertoire séparé, compilé avec ses propres options.
  • Relisez la JEP à chaque nouvelle version du JDK : les API et règles changent (voir les tableaux ci-dessus).
  • Les retours sont attendus sur les listes de diffusion d'OpenJDK (amber-dev pour le langage, loom-dev pour la concurrence, core-libs-dev pour les bibliothèques, security-dev pour PEM).
