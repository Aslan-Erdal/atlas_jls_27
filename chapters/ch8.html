Chapitre 8 · Java SE 27 Edition

Classes

Le plus long chapitre de la spec. Déclarer une classe, ses champs, méthodes et constructeurs ; hériter, redéfinir, masquer et surcharger ; construire un objet dans le bon ordre ; et les trois formes spécialisées : classes scellées, enums et records.

Source : JLS SE 27, chapitre 8 Sections : 8.1 à 8.10

§8Vue d'ensemble

Une déclaration de classe définit un nouveau type référence et décrit son implémentation. La spec distingue plusieurs sortes de classes selon l'endroit où elles sont déclarées :

SorteOùExemple
De plus haut niveaudirectement dans une unité de compilation (§7.6)public class Facture { }
Imbriquéetoute classe qui n'est pas de plus haut niveau—
  membredans le corps d'une autre classe ou interface (§8.5)class Ligne { } dans Facture
  localedans un bloc (§14.3)classe déclarée dans une méthode
  anonymedans une expression new (§15.9.5)new Runnable() { … }
Implicitement déclaréeunité compacte (§8.1.8)un fichier avec void main()

Et trois formes spécialisées : les enums (§8.9), les records (§8.10), et, transversale, les classes scellées (§8.1.1.2).

§8.1Déclarations de classes

Grammaire (§8.1, simplifiée)
NormalClassDeclaration:
    {ClassModifier} class TypeIdentifier [TypeParameters]
        [ClassExtends] [ClassImplements] [ClassPermits] ClassBody

§8.1.1Modificateurs de classe

Modificateurs possibles : annotations, public, protected, private, abstract, static, final, sealed, non-sealed, strictfp. Un même modificateur ne peut apparaître qu'une fois. protected, private et static ne s'appliquent qu'aux classes membres. Un seul parmi final, sealed, non-sealed.

§8.1.1.1Classes abstraites

Une classe abstract est incomplète : elle ne peut pas être instanciée par new, mais peut avoir des constructeurs (appelés par les sous-classes). Une classe normale qui a, déclare ou hérite une méthode abstraite sans l'implémenter est une erreur, sauf si elle est elle-même abstraite.

Java
abstract class Forme {
    private final String nom;
    protected Forme(String nom) { this.nom = nom; }   // constructeur d'une classe abstraite
    abstract double aire();
    String decrire() { return nom + " d'aire " + aire(); }   // méthode concrète qui appelle l'abstraite
}
new Forme("x");     // ERREUR : Forme est abstraite
final abstract class X { }  // ERREUR : final et abstract sont contradictoires

§8.1.1.2Classes sealed, non-sealed et final

Depuis Java 17, une classe sealed liste explicitement ses sous-classes directes autorisées. Chacune doit à son tour choisir : final (fin de la hiérarchie), sealed (nouvelle liste fermée) ou non-sealed (réouverture à tous).

Java
sealed interface Forme permits Cercle, Rectangle, Polygone { }
record Cercle(double r) implements Forme { }                  // record : implicitement final
sealed class Rectangle implements Forme permits Carre { }
final class Carre extends Rectangle { }
non-sealed class Polygone implements Forme { }                 // la hiérarchie se rouvre ici

static double aire(Forme f) {
    return switch (f) {                  // exhaustif sans default : le compilateur connaît tous les cas
        case Cercle c    -> Math.PI * c.r() * c.r();
        case Rectangle r -> 0;           // couvre aussi Carre
        case Polygone p  -> 0;
    };
}
Règles

Les sous-classes autorisées doivent être dans le même module que la classe scellée (ou dans le même paquetage si elle est dans le module sans nom), et doivent l'étendre directement. Si la clause permits est omise, les sous-classes autorisées sont celles déclarées dans la même unité de compilation. Une classe final ne peut pas avoir de sous-classe ; une classe non-sealed peut être étendue par n'importe quelle classe.

§8.1.1.3Classes strictfp

Toujours accepté, sans effet depuis Java 17 (JEP 306) : toutes les expressions flottantes sont strictes. Le compilateur peut émettre un avertissement.

§8.1.1.4Classes static

static ne s'applique qu'aux classes membres : une classe membre static n'a pas d'instance englobante. Les enums, records et interfaces membres sont implicitement static.

§8.1.2Classes génériques et paramètres de type

Une classe est générique si elle déclare des paramètres de type (§4.4). Les paramètres de type sont en portée dans toute la déclaration, mais une classe générique ne peut pas être une sous-classe directe ou indirecte de Throwable, et les paramètres de type ne peuvent pas être utilisés dans un contexte statique.

Java
class Noeud<T extends Comparable<T>> {    // borne récursive (F-bound)
    T valeur; Noeud<T> gauche, droite;
    static T defaut;                         // ERREUR : T dans un contexte statique
}
class Erreur<T> extends Exception { }        // ERREUR : générique et Throwable

§8.1.3Classes internes et instances englobantes

Une classe interne est une classe imbriquée qui n'est pas static (explicitement ou implicitement). Les classes locales et anonymes non statiques sont aussi internes. Chaque instance d'une classe interne déclarée dans un contexte non statique possède une instance immédiatement englobante : une référence cachée vers l'objet de la classe externe.

Java
class Externe {
    int compteur = 3;
    class Interne {
        int x = compteur;                // accède au champ de l'instance englobante
        void reset() { Externe.this.compteur = 0; }
        static int nbCrees;              // permis depuis Java 16 (membres static dans une classe interne)
    }
    static class Imbriquee { }           // pas d'instance englobante
}
Externe e = new Externe();
Externe.Interne i = e.new Interne();     // syntaxe qualifiée : précise l'instance englobante
Externe.Imbriquee n = new Externe.Imbriquee();
Règle · capture des locales

Une classe locale ou anonyme peut utiliser les variables locales et paramètres de la méthode englobante, à condition qu'ils soient final ou effectivement final (§4.12.4). La valeur est copiée dans l'objet au moment de sa création.

Piège · fuite mémoire

Une instance de classe interne garde son objet externe en vie tant qu'elle-même vit. Un écouteur anonyme ou une classe interne stockée dans un cache peut ainsi retenir un gros objet. Préférez une classe membre static quand l'instance englobante n'est pas nécessaire.

§8.1.4Superclasses et sous-classes

La clause extends nomme la superclasse directe. Sans elle, c'est Object (sauf pour Object lui-même, qui n'en a pas). Le type nommé doit être une classe accessible, non final, et non scellée sauf si la classe courante est autorisée. On ne peut pas étendre Enum ou Record directement.

Une classe ne peut pas dépendre d'elle-même : class A extends B {} et class B extends A {} forment une circularité interdite. La relation « sous-classe » est la fermeture transitive de « sous-classe directe ».

§8.1.5Superinterfaces

La clause implements liste les superinterfaces directes. Une même interface ne peut pas être nommée deux fois, et une classe ne peut pas être sous-type de deux paramétrages différents de la même interface générique :

Java
class A implements Comparable<A> { … }
class B extends A implements Comparable<B> { }   // ERREUR : Comparable<A> et Comparable<B>

C'est une conséquence directe de l'effacement : la JVM ne verrait qu'une seule interface Comparable.

§8.1.6Sous-classes directes autorisées

La clause permits d'une classe sealed nomme ses sous-classes directes autorisées. Chaque nom doit désigner une classe accessible, distincte, qui étend directement la classe scellée. Une clause permits sur une classe non scellée est une erreur.

§8.1.7Corps de classe et déclarations de membres

Le corps contient des déclarations de membres (champs, méthodes, classes et interfaces membres), des initialiseurs d'instance et statiques, et des constructeurs. La portée de chaque membre est tout le corps (§6.3).

§8.1.8Classes implicitement déclarées

Une unité de compilation compacte (§7.3) déclare implicitement une classe. Depuis Java 25 (JEP 512), c'est la façon la plus simple d'écrire un programme.

Règles

La classe implicite est final, de plus haut niveau, dans le paquetage sans nom, et étend Object. Ses membres sont les champs et méthodes déclarés au niveau de l'unité. Elle n'a que le constructeur par défaut. Son nom est choisi par l'hôte (en pratique, celui du fichier) mais ne peut pas être utilisé dans le code. Elle doit déclarer une méthode main lançable (§12.1.4).

Compteur.java
int total = 0;                     // champ d'instance de la classe implicite

void ajouter(int n) { total += n; }

void main() {                      // méthode main d'instance, sans String[] args
    ajouter(3); ajouter(4);
    IO.println("Total : " + total);
}

§8.2Membres d'une classe

Les membres d'une classe sont :

  • les membres hérités de sa superclasse directe (sauf pour Object) ;
  • les membres hérités de ses superinterfaces directes ;
  • les membres déclarés dans son corps.
Règle

Les membres private ne sont pas hérités. Les membres à accès paquetage ne sont hérités que par les sous-classes du même paquetage. Les constructeurs, initialiseurs statiques et initialiseurs d'instance ne sont pas des membres : ils ne sont jamais hérités.

Java
class Point { private int x; int y; protected int z; public int w; }
class Point3D extends Point {
    void f() {
        x = 1;   // ERREUR : x n'est pas hérité (il existe pourtant dans l'objet !)
        y = 1;   // OK seulement si Point3D est dans le même paquetage que Point
        z = 1;   // OK
        w = 1;   // OK
    }
}

Remarquez la nuance : l'objet Point3D contient bien un emplacement pour x, initialisé par le constructeur de Point. « Non hérité » signifie seulement que le nom n'est pas un membre de Point3D.

§8.3Déclarations de champs

Un champ est déclaré par un type et un ou plusieurs déclarateurs, chacun avec un initialiseur facultatif. Deux champs de même nom dans une même classe sont une erreur. Un champ masque (hides) tout champ de même nom hérité d'une superclasse ou superinterface, même de type différent : les deux coexistent, et l'accès dépend du type statique.

Java · masquage de champ
class A { String nom = "A"; }
class B extends A { String nom = "B"; }   // masque A.nom, ne le redéfinit pas

A a = new B();
a.nom;               // "A" : les champs sont liés statiquement, selon le type de l'expression
((B) a).nom;         // "B"
// dans B : super.nom vaut "A", ((A) this).nom aussi

§8.3.1Modificateurs de champ

§8.3.1.1Champs static

Un champ static (variable de classe) existe en un seul exemplaire, quel que soit le nombre d'instances, y compris zéro. Un champ non statique (variable d'instance) existe une fois par objet. Un champ static peut masquer un champ d'instance hérité, et inversement.

§8.3.1.2Champs final

Un champ final doit être affecté exactement une fois : dans son initialiseur, ou (blank final) dans chaque constructeur pour un champ d'instance, ou dans un initialiseur statique pour un champ statique. Un champ final bien initialisé bénéficie de garanties particulières du modèle mémoire (§17.5).

§8.3.1.3Champs transient

transient marque un champ qui ne fait pas partie de l'état persistant de l'objet. La spec n'en dit pas plus ; c'est la sérialisation Java (java.io.Serializable) qui l'ignore.

§8.3.1.4Champs volatile

Un champ volatile garantit que tous les threads voient une valeur cohérente : chaque écriture happens-before chaque lecture qui la suit dans l'ordre de synchronisation (§17.4). Les lectures et écritures d'un long ou double volatile sont atomiques (§17.7). Un champ ne peut pas être à la fois final et volatile.

Java
class Tache implements Runnable {
    private volatile boolean arret;          // sans volatile, la boucle pourrait ne jamais voir l'écriture
    public void run() { while (!arret) travailler(); }
    void stop() { arret = true; }
}

§8.3.2Initialisation des champs

L'initialiseur d'un champ statique est exécuté une fois, à l'initialisation de la classe (§12.4.2), dans l'ordre textuel avec les initialiseurs statiques. Celui d'un champ d'instance est exécuté à chaque création d'objet, dans l'ordre textuel avec les initialiseurs d'instance, juste après l'appel du constructeur de la superclasse (§12.5).

Règles

Un initialiseur de champ statique ne peut pas utiliser this, super, ni un champ d'instance. Un initialiseur ne peut lever une exception vérifiée que dans des cas très limités (§11.2.3).

§8.3.3Restrictions sur les références en avant

Dans les initialiseurs (de champ, d'instance ou statiques) d'une classe C, utiliser un champ de C déclaré plus bas est une erreur si les quatre conditions suivantes sont réunies : l'usage est un nom simple ; il n'est pas à gauche d'une affectation ; il est dans un initialiseur du même genre (instance/statique) que le champ ; et il est dans C, pas dans une classe imbriquée.

Java
class F {
    int a = b + 1;          // ERREUR : référence en avant, nom simple
    int c = this.b + 1;     // compile ! vaut 1 car b vaut encore 0 (valeur par défaut)
    int d = lireB() + 1;    // compile, vaut aussi 1
    { b = 5; }              // permis : b est à gauche d'une affectation
    int b = 10;             // l'initialiseur écrase le 5
    int lireB() { return b; }
}

Ces règles empêchent les erreurs évidentes, pas toutes : un accès qualifié ou via une méthode voit la valeur par défaut. L'ordre textuel des champs est donc significatif.

§8.4.1Paramètres formels

Chaque paramètre a un type et un nom ; il peut être final. Le dernier paramètre peut être variadique (T... args) : il est de type T[] et accepte zéro ou plusieurs arguments. Un paramètre récepteur facultatif (void m(@NonNull MaClasse this)) ne sert qu'à annoter le type de this.

Java
static int somme(int... t) { int s = 0; for (int x : t) s += x; return s; }
somme();            // 0 : tableau vide
somme(1, 2, 3);     // 6
somme(new int[]{4, 5}); // 9 : un tableau peut être passé directement
void f(int... a, int b) { }  // ERREUR : le paramètre variadique doit être le dernier
Piège

Pour un paramètre Object..., passer null ou un Object[] remplit directement le tableau. f(null) donne un tableau null, pas un tableau contenant null ; f((Object) null) donne [null].

§8.4.2Signature de méthode

La signature d'une méthode est son nom et les types de ses paramètres formels (après adaptation des paramètres de type). Le type de retour et la clause throws n'en font pas partie. Deux méthodes d'une même classe ne peuvent pas avoir des signatures équivalentes pour la redéfinition (override-equivalent).

  • m1 est une sous-signature de m2 si les signatures sont identiques, ou si celle de m1 est l'effacement de celle de m2.
  • m1 et m2 sont équivalentes pour la redéfinition si l'une est une sous-signature de l'autre.
Java
class C {
    int f(int x) { return x; }
    long f(int y) { return y; }          // ERREUR : même signature f(int), seul le retour diffère
    void g(List<String> l) { }
    void g(List l) { }                   // ERREUR : g(List) est une sous-signature de g(List<String>)
}

class Compte {

    static synchronized void audit() { }                     // verrou : Compte.class
}

§8.4.4Méthodes génériques

Une méthode est générique si elle déclare ses propres paramètres de type, placés avant le type de retour. Ils sont en portée dans toute la déclaration. Les arguments de type sont en général inférés (ch. 18), mais peuvent être explicites : Collections.<String>emptyList().

Java
static <K, V extends Comparable<? super V>> K cleDuMax(Map<K, V> m) {
    return m.entrySet().stream().max(Map.Entry.comparingByValue()).orElseThrow().getKey();
}

§8.4.5Résultat d'une méthode

Le résultat est void ou un type. Quand une méthode en redéfinit une autre, son type de retour doit être substituable : identique pour void et les primitifs ; pour un type référence R1 à la place de R2, R1 doit être un sous-type de R2 (retour covariant), ou convertible par conversion non vérifiée (avec avertissement), ou les signatures doivent différer et R1 = |R2|.

Java
class Animal { Animal reproduire() { return new Animal(); } }
class Chat extends Animal {
    @Override Chat reproduire() { return new Chat(); }   // retour covariant : Chat <: Animal
}

§8.4.6Clause throws

La clause throws liste les exceptions vérifiées que la méthode peut lever (§11.2). Y lister des exceptions non vérifiées est permis, à titre documentaire. Une variable de type bornée par Exception peut apparaître : <X extends Throwable> void f() throws X.

§8.4.7Corps de méthode

Un bloc, ou ; pour une méthode abstract ou native (et seulement pour elles). Une méthode non void ne doit pas pouvoir se terminer normalement (§14.1) : chaque chemin doit finir par return avec valeur ou throw. Une méthode void ne peut pas contenir return expr;.

§8.4.8Héritage, redéfinition et masquage

Une classe C hérite de sa superclasse et de ses superinterfaces toutes les méthodes concrètes, abstraites et default qui sont accessibles et ne sont pas redéfinies ou masquées par une déclaration de C. Trois relations sont à distinguer soigneusement :

§8.4.8.3Exigences pour redéfinir et masquer

Retour substituable (§8.4.5)int f() redéfinie par long f()

Accès au moins aussi largepublic void f() redéfinie par void f() (paquetage)

Ordre des accès, du plus large au plus étroit : public > protected > paquetage > private.

§8.4.8.4Hériter plusieurs méthodes équivalentes

Une classe peut hériter plusieurs méthodes de signatures équivalentes (d'une superclasse et d'interfaces). Si l'une est concrète, elle implémente les autres (et doit respecter leurs exigences de retour et de throws). Si aucune n'est concrète et que la classe n'est pas abstraite, erreur. Deux méthodes default conflictuelles exigent une redéfinition explicite (§9.4.1.3).

§8.4.9Surcharge

Si deux méthodes d'une classe (déclarées ou héritées) ont le même nom sans être équivalentes pour la redéfinition, le nom est surchargé. Cela n'impose aucune contrainte de retour ou de throws. La surcharge est résolue à la compilation (§15.12.2) ; la redéfinition, à l'exécution (§15.12.4).

§8.5Classes et interfaces membres

Une classe membre est déclarée directement dans le corps d'une autre. Elle peut avoir tous les modificateurs d'accès. Une classe membre masque les classes membres de même nom héritées. Les interfaces, enums et records membres sont implicitement static.

§8.6Initialiseurs d'instance

Un bloc { … } au niveau du corps de la classe est exécuté à chaque création d'objet, dans l'ordre textuel avec les initialiseurs de champs, après l'appel au constructeur de la superclasse. Il ne peut pas contenir return et ne peut lever une exception vérifiée que si tous les constructeurs la déclarent. Il est surtout utile dans les classes anonymes, qui n'ont pas de constructeur.

§8.7Initialiseurs statiques

Un bloc static { … } est exécuté une seule fois, à l'initialisation de la classe (§12.4.2). Il ne peut pas utiliser this, super, ni return, et doit pouvoir se terminer normalement. Une exception non vérifiée qu'il lève devient une ExceptionInInitializerError, et la classe est inutilisable ensuite (NoClassDefFoundError).

§8.8Déclarations de constructeurs

Un constructeur sert à créer une instance. Il porte le nom de sa classe, n'a pas de type de retour, et n'est pas un membre : il n'est jamais hérité ni redéfini.

§8.8.1Paramètres formels

Comme pour les méthodes (§8.4.1). Le constructeur d'une classe interne a en plus un paramètre implicite, l'instance englobante, que la JVM voit dans la signature binaire.

§8.8.2Signature de constructeur

Mêmes règles que pour les méthodes : deux constructeurs aux signatures équivalentes sont une erreur.

§8.8.3Modificateurs de constructeur

Seulement les modificateurs d'accès et les annotations. Pas de abstract, static, final, native, synchronized : un constructeur n'est pas hérité et l'objet en construction n'est pas encore partagé.

§8.8.4Constructeurs génériques

Un constructeur peut déclarer ses propres paramètres de type, indépendants de ceux de la classe : <T> Boite(T graine) { … }. L'appel peut les préciser : new <String>Boite("x").

§8.8.5Clause throws d'un constructeur

Comme pour les méthodes. Un constructeur doit déclarer les exceptions vérifiées que peuvent lever son corps, ses initialiseurs d'instance et de champs, et l'appel du constructeur de la superclasse.

§8.8.6Type d'un constructeur

Le type d'un constructeur est sa signature, ses paramètres de type et sa clause throws ; la notion sert à l'inférence et à la résolution de surcharge des créations d'instances.

§8.8.7Corps de constructeur

Le corps peut contenir un appel explicite de constructeur : this(…) (un autre constructeur de la même classe) ou super(…) (constructeur de la superclasse). S'il n'y en a pas, et que la classe n'est pas Object, le compilateur insère implicitement super(); au début.

Java 25 · corps de constructeur flexibles (JEP 513)

Avant Java 25, l'appel explicite devait être la première instruction. Désormais, des instructions peuvent le précéder : elles forment le prologue ; celles qui suivent forment l'épilogue. Le prologue sert à valider ou calculer les arguments, et à initialiser les champs de la classe courante avant que la superclasse ne s'exécute.

Règles du prologue

Dans le prologue, l'objet est « en construction précoce » : il est interdit d'utiliser this explicitement ou implicitement (lire un champ, appeler une méthode d'instance, passer this en argument), d'utiliser super.x, et d'écrire return. Une seule exception : affecter un champ déclaré dans la classe courante sans initialiseur.

Java 25+
class Positif extends Nombre {
    private final int valeur;
    Positif(int v) {
        if (v <= 0) throw new IllegalArgumentException("v doit être > 0");   // prologue : validation
        int carre = v * v;                        // prologue : calcul local
        this.valeur = v;                          // prologue : champ sans initialiseur, permis
        super(carre);                             // appel explicite
        System.out.println("créé : " + valeur);   // épilogue : this est utilisable
    }
}
class Interdit extends Nombre {
    int x;
    Interdit() {
        System.out.println(x);   // ERREUR : lecture de this.x dans le prologue
        afficher();              // ERREUR : méthode d'instance dans le prologue
        super(0);
    }
}

Le grand intérêt apparaît quand la superclasse appelle une méthode redéfinie pendant sa construction. Suivez la création d'un objet pas à pas :

§8.8.7.1Appels explicites de constructeur

FormeEffet
this(args)autre constructeur de la même classe ; les initialiseurs de champs ne seront exécutés que par le constructeur final de la chaîne
super(args)constructeur de la superclasse directe
expr.super(args)superclasse interne : précise son instance englobante
<T>this(…), <T>super(…)avec arguments de type explicites pour un constructeur générique

Un appel explicite ne peut apparaître qu'une fois, au niveau du corps du constructeur (pas dans un bloc imbriqué, ni dans un if). Un constructeur ne peut pas s'appeler lui-même, même indirectement par une chaîne de this(…).

§8.8.8Surcharge de constructeurs

Comme pour les méthodes ; la résolution suit les règles du §15.9.3 et §15.12.2.

§8.8.9Constructeur par défaut

Si une classe ne déclare aucun constructeur, le compilateur fournit un constructeur par défaut sans paramètre, qui appelle super(). Il a le même accès que la classe (une classe public obtient un constructeur public). Dès qu'un constructeur est écrit, il n'y a plus de constructeur par défaut.

Java
class Parent { Parent(int x) { } }
class Enfant extends Parent { }    // ERREUR : le constructeur par défaut appelle super(), qui n'existe pas

§8.8.10Empêcher l'instanciation

Une classe utilitaire déclare un constructeur private (et souvent final sur la classe) pour empêcher toute instanciation hors de son corps : public final class Maths { private Maths() {} … }.

§8.9Enums

Un enum est une classe dont les instances sont fixées à la compilation : ses constantes. Il étend implicitement java.lang.Enum<E> et ne peut pas être instancié par new, cloné, ni désérialisé en un doublon. Comparer des constantes d'enum avec == est donc correct.

§8.9.1Constantes d'enum

Chaque constante peut avoir des arguments (passés au constructeur) et un corps de classe : elle devient alors une instance d'une classe anonyme qui étend l'enum.

§8.9.2Déclarations dans le corps d'un enum

Règles

Les constructeurs d'un enum sont implicitement private et ne peuvent pas appeler super(…). Un enum est implicitement final, sauf si une constante a un corps : il est alors implicitement sealed, avec pour sous-classes autorisées les classes anonymes de ses constantes. Il peut déclarer des méthodes abstraites, que chaque constante doit implémenter.

Un constructeur ou initialiseur d'instance d'enum ne peut pas lire un champ static de l'enum (sauf variable constante) : les constantes sont créées avant que les autres champs statiques soient initialisés.

§8.9.3Membres d'un enum

En plus des membres hérités de Enum (name(), ordinal(), compareTo…), le compilateur déclare implicitement :

  • public static E[] values() : un nouveau tableau des constantes dans l'ordre de déclaration ;
  • public static E valueOf(String name) : la constante de ce nom exact, sinon IllegalArgumentException.
Java
enum Operation {
    PLUS("+")  { int appliquer(int a, int b) { return a + b; } },
    FOIS("×")  { int appliquer(int a, int b) { return a * b; } };

    private final String symbole;
    Operation(String s) { symbole = s; }       // implicitement private
    abstract int appliquer(int a, int b);      // chaque constante l'implémente
    String symbole() { return symbole; }
}

for (Operation op : Operation.values())
    System.out.println(op + " " + op.symbole() + " " + op.appliquer(3, 4));
Operation.valueOf("FOIS");                     // FOIS
Operation.PLUS.getClass();                     // classe anonyme Operation$1
Operation.PLUS.getDeclaringClass();            // Operation : à utiliser à la place
Piège

Ne persistez jamais ordinal() : il change si l'on insère une constante. Persistez name(), ou un code métier dédié. Pour des ensembles et des tables indexés par un enum, EnumSet et EnumMap sont bien plus rapides que leurs équivalents génériques.

§8.10Records

Un record est une classe qui sert d'agrégat transparent de valeurs. Son en-tête déclare des composants, et le compilateur en déduit l'essentiel de la classe. Il étend implicitement java.lang.Record.

§8.10.1Composants de record

Chaque composant a un type et un nom ; le dernier peut être variadique. Un composant ne peut pas s'appeler clone, finalize, getClass, hashCode, notify, notifyAll, toString ou wait (conflit avec les méthodes de Object). Les annotations d'un composant sont propagées au champ, à l'accesseur, au paramètre du constructeur et au composant lui-même, selon leurs cibles @Target.

§8.10.2Déclarations dans le corps d'un record

Interdits : champs d'instance, initialiseurs d'instance, méthodes native. Permis : champs, méthodes et initialiseurs static, méthodes d'instance, classes membres, constructeurs (qui doivent finir par déléguer au canonique avec this(…)).

§8.10.3Membres d'un record

Pour chaque composant : un champ private final implicite, et un accesseur public de même nom, sauf s'il est déclaré explicitement. Un accesseur explicite doit être public, sans paramètre, sans throws, non générique, non statique, et renvoyer exactement le type du composant. equals, hashCode et toString sont fournis s'ils ne sont pas déclarés.

Piège · transparence superficielle

Un record est immuable au sens où ses champs sont final, pas au sens profond. record Panier(List<String> articles) laisse modifier la liste : copiez-la dans le constructeur compact (articles = List.copyOf(articles);).

§8.10.4Constructeurs de record

§8.10.4.1Constructeur canonique normal

Ses paramètres doivent correspondre exactement aux composants (mêmes noms, mêmes types, même ordre). Il doit fournir un accès au moins aussi large que le record, ne pas avoir de clause throws ni être générique, et ne pas appeler this(…) ni super(…). Il doit affecter chaque champ exactement une fois.

§8.10.4.2Constructeur canonique compact

Il omet la liste de paramètres : ceux-ci sont implicites. Son corps ne peut ni affecter les champs ni contenir return ; à la fin, chaque champ reçoit la valeur (éventuellement modifiée) du paramètre correspondant. C'est l'endroit idéal pour valider et normaliser.

Avec les motifs

Les records s'accordent avec les motifs d'enregistrement (§14.30.1) : if (o instanceof Point(int x, int y)) déconstruit l'objet via ses accesseurs. Combinés aux interfaces scellées, ils permettent des switch exhaustifs sur des types algébriques.
