Chapitre 16 · Java SE 27 Edition

Affectation définie

Java refuse de compiler un programme qui pourrait lire une variable locale avant de lui avoir donné une valeur, ou affecter deux fois une variable final. Ce chapitre définit l'analyse de flux, simple et conservatrice, qui le garantit.

Source : JLS SE 27, chapitre 16 Sections : 16.1 à 16.9

§16Les deux garanties

Affectation définie (DA)Toute variable locale, et tout champ final sans initialiseur (blank final), doit être définitivement assigné avant tout accès à sa valeur. L'accès doit se faire par son nom simple (ou this.f pour un champ).
Non-affectation définie (DU)Toute variable blank final doit être définitivement non assignée au moment où on l'affecte. Elle ne peut donc l'être qu'une fois, et jamais dans une boucle.

L'analyse ne tient compte que de la structure des instructions et expressions, et des valeurs des expressions constantes (§15.29). Elle ne raisonne pas sur les valeurs à l'exécution, même évidentes pour un humain.

Java · exemple 16-2 de la spec, reformulé
int k;
if (n > 2) k = 3;
if (n <= 2) k = 4;
System.out.println(k);       // ERREUR : l'analyse ne sait pas que les deux conditions sont complémentaires

int m;
if (n > 2) m = 3; else m = 4;
System.out.println(m);       // OK : chaque branche affecte m

int z;
while (true) { z = 1; break; }
System.out.println(z);       // OK : true est une expression constante, la sortie se fait par le break
Notation de la spec

Pour chaque variable V et chaque point du programme, la spec définit « V est [non] assignée définitivement avant / après » une expression ou instruction. Pour une expression booléenne, elle distingue en plus « après quand elle est vraie » et « après quand elle est fausse ». C'est cette finesse qui rend utilisables les conditions composées.

Pour a && b, V est DA avant b si V est DA après a quand vraie : b n'est évalué que si a est vrai. Ces règles rendent légal un code idiomatique :

Java
int r;
if (pret && (r = calculer()) > 0) utiliser(r);   // OK : r est DA quand la condition est vraie
if (pret || (r = calculer()) > 0) utiliser(r);   // ERREUR : si pret est vrai, r n'est jamais affecté

String ligne;
while ((ligne = lecteur.readLine()) != null) traiter(ligne);  // OK : affectation dans la condition

§16.1.8Expressions d'affectation

V est DA après V = e (et après toute affectation dont le côté gauche est V). Pour une affectation composée V op= e, V doit être DA avant : elle lit V. Si V est blank final, elle doit être DU avant V = e.

§16.1.9Opérateurs ++ et --

V doit être DA avant V++, ++V… puisqu'ils lisent V. Ils sont interdits sur une variable final.

§16.1.10Autres expressions

Pour les autres expressions, l'analyse suit l'ordre d'évaluation (§15.7) : V est DA après l'expression si elle l'est après la dernière sous-expression évaluée. Le corps d'une lambda est analysé avec les variables DA avant la lambda ; une variable capturée doit être DA avant la lambda.

§16.2Affectation définie et instructions

Le principe : une instruction qui ne peut pas se terminer normalement (return, throw, break…) rend « vrai » n'importe quel fait d'affectation après elle, car ce point n'est jamais atteint.

Piège · try et catch

Dans un catch ou un finally, une variable affectée dans le try n'est pas DA : l'exception a pu survenir avant l'affectation. Pour la non-affectation (DU), c'est l'inverse : une blank final affectée dans le try n'est pas DU dans le catch, on ne peut donc pas la réaffecter « en secours ».

Java
int n;
try {
    n = Integer.parseInt(s);
} catch (NumberFormatException e) {
    n = 0;                        // OK pour une variable ordinaire
}
use(n);                           // OK : DA après le try et après le catch

final int f;
try { f = Integer.parseInt(s); }
catch (NumberFormatException e) { f = 0; }   // ERREUR : f n'est peut-être pas DU (déjà affectée ?)
final int g = parseOuZero(s);     // solution : une méthode, ou une switch/conditionnelle

§16.3Affectation définie et paramètres

Les paramètres de méthodes, constructeurs, lambdas et les paramètres d'exception sont DA (et pas DU) dès le début de leur corps : ils reçoivent toujours une valeur.

§16.4Affectation définie et initialiseurs de tableaux

Les expressions d'un initialiseur {a, b, c} sont analysées de gauche à droite, comme des arguments.

§16.5Affectation définie et constantes d'enum

Les arguments d'une constante d'enum sont analysés dans l'ordre des constantes ; une variable est DA avant une constante si elle l'est après la précédente.

§16.6Affectation définie et classes anonymes

V est DA avant un corps de classe anonyme si elle est DA après les arguments de la création. Les variables capturées doivent l'être.

§16.7Affectation définie et classes membres

Dans le corps d'une classe membre, les blank finals de la classe englobante sont considérées DA si elles le sont avant la déclaration de la classe membre.

§16.8Affectation définie et initialiseurs statiques

Règle

Un champ static final sans initialiseur doit être DA à la fin de l'ensemble des initialiseurs statiques et des initialiseurs de champs statiques de la classe, et y être affecté exactement une fois.

Java
class Config {
    static final Properties PROPS;
    static final int PORT;
    static {
        PROPS = charger();
        PORT = Integer.parseInt(PROPS.getProperty("port", "8080"));
    }
}

§16.9Constructeurs et initialiseurs d'instance

Règles

Un champ final d'instance sans initialiseur doit être DA à la fin de chaque constructeur qui ne commence pas par this(…) (en comptant les initialiseurs d'instance), et affecté au plus une fois sur chaque chemin. Avant son affectation, il ne peut pas être lu par son nom simple, ni par this.f.

Un constructeur qui délègue avec this(…) considère tous les blank finals comme DA après cet appel : c'est l'autre constructeur qui les affecte. Avec les corps flexibles (Java 25), les blank finals peuvent être affectés dans le prologue, avant super(…), et sont alors DA dans l'épilogue.

Java
class Point {
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }   // OK
    Point() { this(0, 0); }                           // OK : délégation
    Point(int v) {
        if (v > 0) x = v;                             // y n'est jamais affecté
    }                                                 // ERREUR : x pas DA sur tous les chemins, y jamais
    void bouger() { x = 1; }                          // ERREUR : affectation d'un final hors constructeur
}
Note non normative

L'analyse ne protège que les accès par nom simple. Une méthode appelée depuis le constructeur peut lire un champ final avant son affectation et voir sa valeur par défaut (figure 8.2). C'est une limite connue, que les corps de constructeur flexibles réduisent sans l'éliminer.
