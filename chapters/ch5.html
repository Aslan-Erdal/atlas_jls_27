Chapitre 5 · Java SE 27 Edition

Conversions et contextes

Chaque expression a un type, et chaque endroit où elle apparaît attend un type. Entre les deux, le compilateur applique des conversions, mais seulement celles que le contexte autorise. Ce chapitre fixe ces deux listes et leur croisement.

Source : JLS SE 27, chapitre 5 Sections : 5.1 à 5.7

§5Le principe

Une conversion change le type d'une expression, et parfois sa valeur. Certaines n'existent qu'à la compilation (on « voit » l'objet autrement), d'autres font un travail à l'exécution (calculer, vérifier, allouer). Un contexte est une position syntaxique qui autorise un ensemble précis de conversions.

§5.1.1Conversion identité

Toujours permise, de tout type vers lui-même. Elle paraît inutile, mais elle rend certains casts légaux ((int) x où x est déjà un int, pour la lisibilité) et elle simplifie l'écriture des règles : chaque contexte l'autorise.

§5.1.2Élargissement primitif

Dix-neuf conversions, qui suivent le graphe du §4.10.1 : byte vers short int long float double ; short vers int long float double ; char vers int long float double ; int vers long float double ; long vers float double ; float vers double.

Règles

Un élargissement ne perd jamais l'ordre de grandeur. Entre entiers, ou de float vers double, il est exact. Mais int → float, long → float et long → double peuvent perdre de la précision : la valeur est arrondie au plus proche (IEEE 754). Un entier signé est étendu par le signe ; un char est étendu par des zéros.

Un élargissement primitif ne lève jamais d'exception à l'exécution.

§5.1.3Rétrécissement primitif

Vingt-deux conversions : toutes celles qui vont « contre » le graphe, plus short ↔ char. Elles peuvent perdre l'ordre de grandeur, la précision et même le signe.

De → versRègleExemple
entier → entier plus petiton garde les n bits de poids faible(byte) 200 = −56
double → floatarrondi au plus proche ; trop grand → infini ; trop petit → zéro(float) 1e40 = Infinity
flottant → int/longNaN → 0 ; sinon arrondi vers zéro ; si hors plage, la valeur extrême (saturation)(int) -3.9 = −3, (int) 1e10 = 2147483647
flottant → byte/short/chard'abord vers int (ligne précédente), puis rétrécissement entier(byte) 300.7 = 44
Piège

La saturation ne vaut que pour int et long. (byte) 1e10 ne donne pas 127 : on passe d'abord par int (2147483647, soit 0x7FFFFFFF), puis on garde 8 bits, ce qui donne −1.

§5.1.4Élargissement puis rétrécissement

Une seule conversion : byte → char. Le byte est d'abord élargi en int (avec extension du signe), puis rétréci en char. Ainsi (char) (byte) -1 donne '￿' (65535), pas 'ÿ'.

§5.1.5Élargissement de référence

De tout type référence S vers tout type référence T si S <: T (§4.10). Aucune action à l'exécution, aucune exception possible : l'objet est simplement « vu » à travers un type plus général. C'est ce qui rend le polymorphisme gratuit.

Le type nul s'élargit vers tout type référence : c'est pourquoi String s = null; est permis.

§5.1.6Rétrécissement de référence

De S vers T quand S n'est pas un sous-type de T. Il exige une vérification à l'exécution, et n'est pas permis pour toutes les paires.

§5.1.6.1Rétrécissements permis

La règle de fond : un rétrécissement est permis s'il pourrait réussir, c'est-à-dire si un objet pourrait exister qui soit à la fois de type S et de type T. Le compilateur rejette les paires dont il peut prouver qu'elles sont disjointes.

§5.1.6.2Rétrécissements vérifiés et non vérifiés

Un rétrécissement est non vérifié quand l'exécution ne peut pas tout contrôler, parce que le type cible n'est pas réifiable (§4.7). Le compilateur émet alors un avertissement unchecked. Exception : si l'information générique se déduit sûrement du type source, la conversion reste vérifiée.

Java
Object o = List.of(1, 2);
List<String> l = (List<String>) o;     // avertissement unchecked : seul "List" est vérifié
List<?> w = (List<?>) o;               // vérifié, aucun avertissement

Collection<String> c = new ArrayList<>();
List<String> v = (List<String>) c;     // vérifié : String est connu depuis le type source

§5.1.6.3À l'exécution

Une conversion vérifiée teste la classe réelle de l'objet. Si la référence est null, elle réussit toujours. Sinon, si l'objet n'est pas du type cible effacé, elle lève ClassCastException. Une conversion non vérifiée ne teste que l'effacement : l'erreur, s'il y en a une, apparaîtra plus tard (pollution du tas, §4.12.2).

§5.1.7Boxing

Huit conversions, de chaque type primitif vers sa classe enveloppe : boolean → Boolean, byte → Byte, short → Short, char → Character, int → Integer, long → Long, float → Float, double → Double. Le type nul se « boxe » vers lui-même.

Règle · le cache garanti

Si la valeur boxée est true, false, un byte, un char entre \u0000 et \u007f, ou un int/short entre −128 et 127, alors deux boxings de la même valeur donnent la même référence. Au-delà, ce n'est pas garanti (la JVM peut être configurée pour cacher plus, par exemple avec -XX:AutoBoxCacheMax).

Java
Integer a = 100, b = 100;   a == b;   // true (garanti)
Integer c = 1000, d = 1000; c == d;   // false en général : ne jamais comparer des enveloppes avec ==
Long x = 127L, y = 127L;    x == y;   // true en pratique (Long.valueOf cache aussi -128..127)
Double p = 1.0, q = 1.0;    p == q;   // false : aucun cache pour Double et Float

§5.1.8Unboxing

Les huit conversions inverses, réalisées par booleanValue(), intValue(), etc. Si la référence est null, l'unboxing lève NullPointerException. C'est souvent invisible dans le code :

Java
Map<String, Integer> stock = new HashMap<>();
int n = stock.get("pomme");          // NullPointerException : get renvoie null, puis unboxing

Integer i = null;
int r = flag ? i : 0;                // NullPointerException si flag : le ? : est numérique (§15.25)
long total = 0;
for (Long v : valeurs) total += v;   // NPE si la liste contient null

§5.1.9Conversion non vérifiée

D'un type brut G vers n'importe quel type paramétré G<T1,…,Tn>, ou d'un tableau brut G[] vers G<…>[]. Elle provoque un avertissement unchecked, sauf si tous les arguments cibles sont des jokers non bornés (List<?> l = brute; ne prévient pas) ou si l'avertissement est supprimé par @SuppressWarnings("unchecked").

§5.1.10Conversion par capture

La capture remplace chaque joker d'un type paramétré par une variable de type fraîche, dont les bornes combinent celles du joker et celles du paramètre déclaré. Pour G<A1,…,An> dont le paramètre Pi a la borne Ui :

Argument AiNouvelle variable Si
?borne supérieure Ui[P1:=S1,…], borne inférieure le type nul
? extends Biborne supérieure glb(Bi, Ui[…]) (intersection), borne inférieure le type nul
? super Biborne supérieure Ui[…], borne inférieure Bi
un type TT lui-même

La capture n'est pas récursive : elle ne s'applique qu'au niveau le plus extérieur. Chaque évaluation d'une expression produit une capture différente, ce qui explique pourquoi on ne peut pas échanger deux éléments d'une List<?> sans méthode auxiliaire :

Java · la méthode auxiliaire de capture
static void echange(List<?> l, int i, int j) {
    l.set(i, l.get(j));          // ERREUR : set attend CAP#1, get renvoie un CAP#2 différent
}

static void echange2(List<?> l, int i, int j) { aide(l, i, j); }
private static <T> void aide(List<T> l, int i, int j) {
    l.set(i, l.get(j));          // OK : l'inférence lie T à la capture, une seule fois
}

class Boite<T extends Number> { T v; }
Boite<?> b = ...;
Number n = b.v;                  // OK : la capture de ? a pour borne Number (borne du paramètre)

§5.1.11Conversion en chaîne

Tout type se convertit en String, mais seulement dans un contexte chaîne (§5.4). Une valeur primitive passe d'abord par le boxing puis toString() (en pratique, le compilateur appelle directement String.valueOf). Une référence null donne "null" ; sinon on appelle toString(), et si celle-ci renvoie null, on obtient aussi "null".

§5.1.12Conversions interdites

Toute conversion qui n'est pas explicitement permise est interdite. Les cas fréquents :

  • boolean vers ou depuis un type numérique, dans n'importe quel contexte ;
  • un type référence vers un type primitif autrement que par unboxing ((int) "3") ;
  • une chaîne vers un autre type en dehors de l'API (Integer.parseInt).

§5.2Contextes d'affectation

Ils convertissent la valeur d'une expression vers le type d'une variable : affectation simple, initialiseur de variable, return (vers le type de retour), argument d'annotation, etc. Conversions permises :

  • identité ; élargissement primitif ; élargissement de référence ;
  • élargissement de référence suivi d'unboxing (puis éventuellement élargissement primitif) ;
  • boxing suivi éventuellement d'un élargissement de référence ;
  • unboxing suivi éventuellement d'un élargissement primitif ;
  • conversion non vérifiée, éventuellement après les précédentes.
Règle · le rétrécissement des constantes

Si l'expression est une expression constante (§15.29) de type byte, short, char ou int, et que la variable est de type byte, short ou char, un rétrécissement est permis si la valeur est représentable. Même chose vers Byte, Short, Character (rétrécissement puis boxing).

Ces règles sont précises et parfois surprenantes. Testez votre intuition :

Une affectation peut aussi produire une erreur à l'exécution sans aucun cast : lors de l'écriture dans un tableau dont le type d'exécution est plus précis (ArrayStoreException, §10.5), ou à cause d'une pollution du tas (ClassCastException).

§5.3Contextes d'invocation

Ils convertissent un argument vers le type du paramètre formel, dans un appel de méthode ou de constructeur. La spec distingue deux niveaux, qui structurent la résolution de surcharge (§15.12.2) :

Invocation stricteidentité, élargissement primitif, élargissement de référence (et conversion non vérifiée après celui-ci). Ni boxing ni unboxing.
Invocation soupletout ce qui précède, plus boxing (suivi d'élargissement de référence) et unboxing (suivi d'élargissement primitif).
Règle

Contrairement à l'affectation, l'invocation n'autorise pas le rétrécissement des constantes. Sinon, la résolution de surcharge dépendrait de valeurs, et f(1) pourrait choisir f(byte).

Java
static void f(byte b)    { }
f(10);                   // ERREUR : pas de rétrécissement de constante en invocation
f((byte) 10);            // OK

static void g(long x)    { System.out.println("long"); }
static void g(Integer x) { System.out.println("Integer"); }
g(5);                    // "long" : la phase stricte (élargissement) passe avant le boxing

§5.4Contextes chaîne

Un seul : l'opérande non chaîne d'un + dont l'autre opérande est de type String. Seule la conversion en chaîne (§5.1.11) y est permise. L'évaluation se fait de gauche à droite, ce qui donne des résultats piégeux :

Java
1 + 2 + "3";      // "33" : 1 + 2 = 3 (numérique), puis 3 + "3"
"1" + 2 + 3;      // "123" : chaque + a déjà un opérande String
'a' + 'b' + "c";  // "195c" : 'a' + 'b' est une addition d'entiers (97 + 98)
"" + 'a' + 'b';   // "ab"

Un cast d'une lambda ou d'une référence de méthode n'est pas une conversion : il fournit un type cible (§15.27.3).

§5.6Contextes numériques

Les opérandes des opérateurs arithmétiques sont convertis vers un type commun par promotion numérique. Elle comprend l'unboxing puis l'élargissement.

Règles · promotion

Unaire (opérande de +/-/~ unaires, index de tableau, dimension de création de tableau, chaque opérande d'un décalage) : un byte, short ou char devient int.

Binaire / générale (* / % + - < <= > >= == != & ^ |, branches numériques de ? : et d'une switch expression) : si un opérande est double, tout passe en double ; sinon float s'il y en a un ; sinon long ; sinon int.

Java
byte a = 1, b = 2;
var c = a + b;            // int
char x = 'x';
var y = x + 1;            // int (121), pas 'y'
var z = (char) (x + 1);   // 'y'
long l = 1L << 40;        // décalage : chaque opérande promu séparément ; résultat long
int bad = 1 << 40;        // 256 ! la distance est masquée à 5 bits pour un int (40 & 31 = 8)
var r = 5 / 2 * 2.0;      // 4.0 : 5 / 2 = 2 (int) avant la promotion en double

§5.7Contextes de test

Ils servent à instanceof et aux motifs (§14.30), y compris les case d'un switch. Ils autorisent : identité, élargissement de référence, rétrécissement de référence vérifié, et unboxing dans certains cas. Un rétrécissement non vérifié est interdit : o instanceof List<String> est rejeté si la vérification ne peut pas être complète (§4.7).

Preview Java 27

Avec --enable-preview, la preview des types primitifs dans les motifs (§1.5.2) étend ce contexte à toutes les conversions primitives, chacune accompagnée d'un test d'exactitude : i instanceof byte b réussit seulement si la valeur tient sans perte. Une conversion est dite inconditionnellement exacte quand elle ne peut jamais perdre d'information (byte → int), ce qui rend le motif inconditionnel pour l'exhaustivité.
