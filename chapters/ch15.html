Chapitre 15 · Java SE 27 Edition

Expressions

L'essentiel du travail d'un programme se fait en évaluant des expressions. Ce chapitre fixe leur type, leur ordre d'évaluation, et la sémantique de chaque forme : littéraux, créations, accès, appels avec résolution de surcharge, références de méthodes, opérateurs, lambdas, switch expressions et expressions constantes.

Source : JLS SE 27, chapitre 15 Sections : 15.1 à 15.29

§15.1Évaluation, dénotation et résultat

Évaluer une expression produit l'un de trois résultats : une variable (à gauche d'une affectation : a[i], x.f), une valeur, ou rien (appel d'une méthode void, permis seulement comme instruction). L'évaluation peut aussi avoir des effets de bord : affectations, appels, créations.

§15.2Formes des expressions

La spec distingue les expressions autonomes (standalone), dont le type se déduit de leur seul contenu, et les poly-expressions, dont le type dépend aussi du type cible du contexte. Sont des poly-expressions, dans un contexte d'affectation ou d'invocation : les lambdas, les références de méthodes, les créations avec diamant new X<>(), les appels de méthodes génériques dont le type de retour mentionne leurs paramètres de type, les conditionnels et switch expressions de type référence, et les expressions parenthésées qui en contiennent.

Java
List<String> a = new ArrayList<>();        // poly : <> inféré depuis la cible List<String>
List<String> b = List.of();                // poly : E inféré = String grâce à la cible
var c = List.of();                         // autonome : pas de cible → List<Object>
Runnable r = () -> {};                     // poly : une lambda n'a de type que par sa cible

§15.3Type d'une expression

Le type d'une expression est déterminé à la compilation. La valeur d'une expression est toujours compatible avec son type, sauf pollution du tas (§4.12.2). Quand le type mentionne des jokers, la conversion par capture (§5.1.10) est appliquée au résultat.

§15.4Expressions flottantes

Depuis Java 17, toute expression flottante est évaluée exactement selon IEEE 754 : chaque opération sur des float se fait en simple précision, sur des double en double précision, sans précision étendue intermédiaire. Les résultats sont identiques au bit près sur toutes les plateformes.

§15.5Expressions et vérifications à l'exécution

Le type statique ne garantit pas tout. Les opérations suivantes sont vérifiées à l'exécution et peuvent lever une exception : cast vers un type référence (ClassCastException), écriture dans un tableau (ArrayStoreException), accès à un tableau (ArrayIndexOutOfBoundsException), accès via null (NullPointerException), division entière par zéro (ArithmeticException), création de tableau de taille négative, unboxing de null, et correspondance de motif sur un record dont un accesseur échoue (MatchException).

§15.6Évaluation normale et abrupte

Une expression se termine abruptement si elle lève une exception. Si une sous-expression se termine abruptement, l'expression englobante aussi, immédiatement : les sous-expressions restantes ne sont pas évaluées (avec les exceptions précisées au §15.7).

§15.7Ordre d'évaluation

Contrairement à C, Java garantit un ordre d'évaluation apparent : un programme se comporte comme si les opérandes étaient évalués dans l'ordre défini ci-dessous. Le compilateur et la JVM peuvent réordonner tant que le résultat observable est le même.

Règles
  • §15.7.1 L'opérande gauche d'un opérateur binaire est entièrement évalué avant l'opérande droit. Pour une affectation composée a op= b, la valeur de a est sauvegardée avant d'évaluer b.
  • §15.7.2 Tous les opérandes sont évalués avant l'opération (sauf &&, || et ? :, qui sont paresseux).
  • §15.7.3 Les parenthèses et la priorité déterminent le groupement, pas l'ordre : (a + b) + c et a + (b + c) ne sont pas interchangeables en flottant ni pour la concaténation.
  • §15.7.4 Les arguments d'un appel sont évalués de gauche à droite.
  • §15.7.5 Les autres expressions (création d'instance, de tableau, accès) suivent un ordre précisé dans leur section.
Java · terminaison abrupte et ordre
int j = 1;
try {
    int i = forgetIt() / (j = 2);   // forgetIt() lève une exception
} catch (Exception e) {
    System.out.println(j);          // 1 : l'opérande droit n'a jamais été évalué (exemple 15.7.1-3)
}

int d = 0;
int r = d / d + effet();            // ArithmeticException AVANT l'appel à effet() (§15.7.2)
f(a(), b(), c());                   // a, puis b, puis c, puis l'appel

§15.8Expressions primaires

Les primaires sont les briques de base : littéraux, littéraux de classe, this, expressions parenthésées, créations, accès aux champs et aux tableaux, appels de méthodes, références de méthodes.

§15.9Création d'instances de classe

new C(args), éventuellement qualifié (externe.new Interne()), avec arguments de type explicites ou diamant (new ArrayList<>()), et éventuellement un corps de classe anonyme.

§15.9.1Déterminer la classe instanciée

La classe doit être accessible, non abstraite (sauf avec un corps anonyme), et ne pas être un enum. Avec un corps, une classe anonyme qui étend C (ou implémente l'interface C) est déclarée.

§15.9.2Déterminer les instances englobantes

Pour une classe interne, l'instance englobante est donnée par la qualification (o.new I()) ou, à défaut, c'est this (ou une instance englobante de this). Dans un contexte statique, créer une classe interne sans qualification est une erreur.

§15.9.3Choisir le constructeur

Comme pour les méthodes (§15.12.2), avec en plus l'inférence des arguments de type pour le diamant (§18.5.2).

§15.9.4Évaluation à l'exécution

Dans l'ordre : l'expression qualifiante (une null lève NullPointerException), puis l'allocation (avec OutOfMemoryError possible, avant l'évaluation des arguments : exemple 15.9.4-1), puis les arguments de gauche à droite, puis le constructeur (§12.5).

§15.9.5Classes anonymes

Une classe anonyme n'a pas de nom, est implicitement non final du point de vue de la spec (mais ne peut pas être étendue faute de nom), jamais abstract ni static. Elle ne peut pas déclarer de constructeur : son constructeur anonyme (§15.9.5.1) est implicite et transmet les arguments au constructeur de la superclasse. Depuis Java 9, le diamant est permis avec une classe anonyme si le type inféré est dénotable.

Java
Comparator<String> parLongueur = new Comparator<>() {        // diamant + anonyme (Java 9)
    public int compare(String a, String b) { return Integer.compare(a.length(), b.length()); }
};
Thread t = new Thread("nom") { public void run() { } };     // arguments transmis à Thread(String)

§15.10Création et accès aux tableaux

§15.10.1 : new T[d1][d2]…[] ; chaque dimension est promue en int. §15.10.2 : les expressions de dimensions sont évaluées de gauche à droite, toutes, avant l'allocation ; une dimension négative lève NegativeArraySizeException après l'évaluation de toutes (exemple 15.10.2-3). §15.10.3 et §15.10.4 : l'accès a[i] évalue a puis i, puis vérifie null, puis les bornes (voir ch. 10).

§15.11Accès aux champs

§15.11.1 : Primaire.f. Le champ est choisi à la compilation d'après le type statique du primaire : pas de liaison dynamique pour les champs. Pour un champ static, le primaire est évalué puis ignoré, même s'il vaut null. §15.11.2 : super.f désigne le champ tel que vu depuis la superclasse ; Externe.super.f pour la superclasse d'une classe englobante.

Java
class S { int x = 1; static int y = 10; }
class T extends S { int x = 2; }
S s = new T();
s.x;                 // 1 : type statique S (exemple 15.11.1-1)
((T) s).x;           // 2
S n = null;
n.y;                 // 10, aucune NullPointerException : champ static (exemple 15.11.1-2)

§15.12Appels de méthodes

La résolution d'un appel se fait en trois étapes à la compilation, puis une à l'exécution. C'est l'une des parties les plus techniques de la spec.

§15.12.1Étape 1 : le type où chercher

m(…) : la classe ou interface englobante la plus proche qui a un membre nommé m. T.m(…) : le type T. e.m(…) : le type de e. super.m(…) : la superclasse. I.super.m(…) : la superinterface directe I.

§15.12.2Étape 2 : la signature de méthode

On identifie d'abord les méthodes potentiellement applicables (§15.12.2.1) : bon nom, accessibles, bon nombre de paramètres (arité), compatibles en forme avec les lambdas passées. Puis trois phases successives ; la première qui trouve au moins une méthode applicable s'arrête :

PhaseConversions permises sur les argumentsVariadique ?
1 §15.12.2.2 — invocation stricteidentité, élargissement primitif, élargissement de référencenon (arité exacte)
2 §15.12.2.3 — invocation souple+ boxing et unboxingnon (arité exacte)
3 §15.12.2.4 — arité variabletout ce qui précèdeoui

Ces phases garantissent que du code écrit avant Java 5 (sans boxing ni variadiques) garde le même sens. Parmi les méthodes applicables d'une phase, on choisit la plus spécifique (§15.12.2.5) : m1 est plus spécifique que m2 si tout appel accepté par m1 l'est aussi par m2 (en gros, si les types de paramètres de m1 sont des sous-types de ceux de m2). S'il n'y en a pas une unique, l'appel est ambigu.

§15.12.2.6Type de l'invocation

Une fois la méthode choisie, son type de retour (après inférence, et après effacement si une conversion non vérifiée a été nécessaire) donne le type de l'expression d'appel ; ses throws donnent les exceptions possibles.

§15.12.3Étape 3 : la méthode choisie est-elle appropriée ?

Vérifications finales : pas de méthode d'instance appelée depuis un contexte statique ; pas de méthode abstraite via super ; pour I.super.m(), la méthode ne doit pas être redéfinie par une autre superinterface directe ; une méthode void n'est pas utilisée comme valeur.

§15.12.4Évaluation à l'exécution

  1. §15.12.4.1 Calculer la référence cible (si méthode d'instance) ; pour une méthode static, l'expression cible est évaluée puis ignorée (exemple 15.12.4.1-1).
  2. §15.12.4.2 Évaluer les arguments de gauche à droite ; pour un variadique, créer le tableau.
  3. §15.12.4.3 Vérifier l'accessibilité (la classe a pu changer depuis la compilation : IllegalAccessError).
  4. §15.12.4.4 Localiser la méthode à exécuter : pour un appel virtuel, on part de la classe réelle de l'objet cible et on remonte vers les superclasses pour trouver la méthode qui redéfinit celle choisie à la compilation. Si la cible vaut null : NullPointerException.
  5. §15.12.4.5 Créer le cadre de pile, acquérir le moniteur si la méthode est synchronized, transférer le contrôle.
Le point clé : surcharge statique, redéfinition dynamique

La signature est choisie à la compilation (types statiques des arguments) ; l'implémentation de cette signature est choisie à l'exécution (classe réelle du récepteur). Les deux mécanismes se combinent :

Java
class A { String f(Object o) { return "A.f(Object)"; } }
class B extends A {
    String f(Object o) { return "B.f(Object)"; }
    String f(String s) { return "B.f(String)"; }
}
A a = new B();
a.f("x");      // "B.f(Object)" : signature f(Object) choisie sur le type A, puis implémentée par B
((B) a).f("x"); // "B.f(String)"

§15.13Références de méthodes

Une référence de méthode :: désigne une méthode ou un constructeur sans l'appeler. Comme une lambda, elle n'a de type que par une interface fonctionnelle cible.

SorteFormeLambda équivalente
Méthode statiqueInteger::parseInts -> Integer.parseInt(s)
Méthode d'instance liée (récepteur fixé)System.out::println, this::fx -> System.out.println(x) (mais voir le piège)
Méthode d'instance non liée (récepteur = 1er argument)String::lengths -> s.length()
ConstructeurArrayList::new() -> new ArrayList<>()
Création de tableauint[]::newn -> new int[n]
Méthode de la superclassesuper::toString() -> super.toString()

§15.13.1 détermine la déclaration au moment de la compilation (avec une recherche qui peut trouver deux candidats pour Type::m, l'un statique, l'autre non lié : ambiguïté si les deux sont applicables) ; §15.13.2 son type ; §15.13.3 son évaluation.

Piège · évaluation du récepteur

Pour une référence liée expr::m, l'expression expr est évaluée une fois, quand la référence est évaluée, et une valeur null lève NullPointerException immédiatement. Une lambda x -> expr.m(x) évalue expr à chaque appel.

Java
Compteur c = null;
Runnable r1 = c::incrementer;        // NullPointerException ICI
Runnable r2 = () -> c.incrementer(); // OK ici ; NPE seulement à r2.run()

Supplier<Compteur> s = Compteur::new;   // référence de constructeur
IntFunction<String[]> f = String[]::new;
String[] t = liste.toArray(String[]::new);

§15.14Expressions postfixes

§15.14.1 : un nom d'expression seul est une expression postfixe. §15.14.2 et §15.14.3 : x++ et x-- ; l'opérande doit être une variable de type numérique (après unboxing) ; la valeur de l'expression est l'ancienne valeur ; un cast implicite ramène le résultat au type de la variable (byte b = 127; b++; donne −128).

§15.15Opérateurs unaires

SectionOpérateurRègles
§15.15.1 / §15.15.2++x, --xvaleur : la nouvelle valeur ; même cast implicite que le postfixe
§15.15.3+xpromotion unaire : +b d'un byte est un int

§15.16Expressions de cast

(T) e convertit e au type T dans un contexte de cast (§5.5). La forme (T & I1 & I2) e cast vers une intersection. Un cast d'une lambda ou référence de méthode fournit un type cible. Le résultat d'un cast n'est jamais une variable : (int) x = 3 est une erreur. La grammaire distingue (Type) -x (cast d'un type primitif seulement) pour lever l'ambiguïté avec la soustraction (§2.3).

§15.17Opérateurs multiplicatifs

§15.17.1 * : commutatif pour les entiers et sans effet de bord ; associatif pour les entiers, pas pour les flottants. §15.17.2 / : division entière tronquée vers zéro ; par zéro → ArithmeticException ; Integer.MIN_VALUE / -1 déborde et vaut MIN_VALUE. §15.17.3 % : (a/b)*b + (a%b) == a ; le signe du reste suit le dividende. Pour les flottants, % n'est pas le reste IEEE (qui serait Math.IEEEremainder) mais la troncature, comme pour les entiers.

Java
5 % 3 == 2;   -5 % 3 == -2;   5 % -3 == 2;   -5 % -3 == -2;   // exemple 15.17.3-1
5.0 % 3 == 2.0;   -5.0 % 3 == -2.0;   5.0 % 0 → NaN             // exemple 15.17.3-2
x % 2 == 1        // FAUX pour les impairs négatifs ! utiliser x % 2 != 0

§15.18Opérateurs additifs

§15.18.1Concaténation de chaînes

Si un opérande de + est de type String, l'autre subit la conversion en chaîne (§5.1.11) et le résultat est un nouvel objet String, sauf si l'expression est constante (§15.29), auquel cas elle est internée. L'implémentation est libre : depuis Java 9, javac utilise invokedynamic (StringConcatFactory) plutôt qu'un StringBuilder.

Java
String s = null;
s + "!";                 // "null!" : aucune exception
"" + 1 + 2;              // "12"
1 + 2 + "";              // "3"
"total : " + (a + b);    // parenthèses nécessaires pour additionner d'abord
String r = "";
for (String m : mots) r += m;   // quadratique : préférer StringBuilder ou String.join

§15.18.2+ et − numériques

Après promotion numérique binaire. Débordement silencieux pour les entiers ; IEEE 754 pour les flottants (∞ + (−∞) = NaN). L'addition flottante n'est pas associative : (1e20 + -1e20) + 1 == 1 mais 1e20 + (-1e20 + 1) == 0.

§15.19Opérateurs de décalage

<< (gauche), >> (droite arithmétique, propage le signe), >>> (droite logique, remplit de zéros). Chaque opérande subit une promotion unaire séparée ; le type du résultat est celui de l'opérande gauche promu. Seuls les 5 bits de poids faible de la distance comptent pour un int (& 0x1f), 6 bits pour un long (& 0x3f).

Java
1 << 32;          // 1 (32 & 31 = 0), pas 0 !
1L << 32;         // 4294967296
-16 >> 2;         // -4  (signe propagé)
-16 >>> 28;       // 15  (zéros insérés)
(byte) -16 >>> 4; // 268435455 : le byte est promu en int AVANT le décalage

§15.20Opérateurs relationnels

§15.20.1 : < <= > >= sur des types numériques (après promotion) ; faux si un opérande est NaN ; −0.0 et 0.0 sont égaux. §15.20.2 : instanceof.

§15.20.2L'opérateur instanceof

Deux formes : e instanceof T (test de type) et e instanceof Motif (§14.30). Le type de e doit pouvoir être converti en T par un cast vérifiable, sinon erreur de compilation (types prouvablement disjoints). Le résultat est false si e vaut null.

Java
Integer n = 5;
n instanceof String;                 // ERREUR : Integer et String sont disjoints
o instanceof List<String> l          // ERREUR si o est un Object : non réifiable (§4.7)
coll instanceof List<String> l       // OK si coll est une Collection<String> : vérification sûre
if (o instanceof String s && !s.isBlank()) use(s);   // variable de motif (§6.3.1)

§15.21Opérateurs d'égalité

§15.21.1 numérique : après promotion ; NaN ≠ NaN ; 0.0 == −0.0. §15.21.2 booléen. §15.21.3 référence : compare l'identité ; les deux types doivent être convertibles l'un vers l'autre par un cast, sinon erreur ("a" == 1). Si un opérande est numérique et l'autre une enveloppe, l'enveloppe est unboxée : comparaison de valeurs, et NullPointerException possible.

Java
Integer a = 1000, b = 1000;
a == b;          // false : deux références
a == 1000;       // true : a est unboxé (numérique)
a.equals(b);     // true
Integer z = null;
z == 0;          // NullPointerException

§15.22Opérateurs bit à bit et logiques

§15.22.1 sur des entiers : &, ^, | bit à bit après promotion. §15.22.2 sur des booléens : &, ^ (ou exclusif), | logiques, qui évaluent toujours les deux opérandes.

§15.23ET conditionnel &&

Évalue l'opérande droit seulement si le gauche est vrai. Associatif. Les variables de motif introduites à gauche quand il est vrai sont en portée à droite (§6.3.1.1).

§15.24OU conditionnel ||

Évalue l'opérande droit seulement si le gauche est faux.

Java
if (s != null && s.length() > 0) { }    // sûr : length() pas appelé si s est null
if (s != null & s.length() > 0) { }     // NullPointerException si s est null
boolean ok = verifierA() | verifierB();   // les deux méthodes sont TOUJOURS appelées

§15.25L'opérateur conditionnel ? :

c ? a : b évalue c, puis un seul des deux opérandes. Il est associatif à droite : a ? b : c ? d : e vaut a ? b : (c ? d : e). Son type dépend de la catégorie de ses opérandes :

CatégorieQuandType
Booléenne §15.25.1les deux opérandes sont boolean / Booleanboolean (unboxing si l'un est primitif)
Numérique §15.25.2les deux sont numériques (primitifs ou enveloppes)promotion numérique binaire ; cas spécial : une constante int représentable dans byte/short/char garde le type de l'autre
Référence §15.25.3tous les autres caspoly-expression avec cible : le type cible ; sinon lub des deux types (§4.10.4)
Pièges classiques
Java
Object o = true ? Integer.valueOf(1) : Double.valueOf(2);
System.out.println(o);           // 1.0 ! numérique : promotion en double, puis boxing en Double

Integer x = null;
int y = flag ? x : 0;            // NullPointerException si flag : unboxing de x
Integer z = flag ? x : 0;        // NullPointerException aussi : le conditionnel est numérique (int)
Integer w = flag ? x : Integer.valueOf(0);   // OK : référence

char c = 'a';
System.out.println(true ? c : 0);    // "a" : 0 est une constante représentable en char
System.out.println(true ? c : i);    // "97" si i est une variable int : promotion en int

§15.26Opérateurs d'affectation

Douze opérateurs : = et les composés *= /= %= += -= <<= >>= >>>= &= ^= |=. L'opérande gauche doit être une variable. Le résultat d'une affectation est la valeur affectée, mais ce n'est pas une variable. L'affectation est associative à droite.

§15.26.1Affectation simple

La valeur est convertie dans un contexte d'affectation (§5.2). Pour un composant de tableau, l'ordre est : tableau, index, côté droit, puis vérification null, bornes et ArrayStoreException (exemple 15.26.1-1).

§15.26.2Affectations composées

Règle

E1 op= E2 équivaut à E1 = (T) ((E1) op (E2)), où T est le type de E1, sauf que E1 n'est évalué qu'une fois. Le cast implicite permet des rétrécissements silencieux.

Java
short s = 1;
s += 1.7;          // compile : s = (short) (s + 1.7) = 2
s = s + 1;         // ERREUR : int vers short sans cast

char c = 'a';
c += 1;            // 'b'
int i = 0;
i += 3.99;         // 3 : rétrécissement silencieux, souvent un bogue
String t = "a";
t += 1;            // "a1" : += marche aussi avec une String à gauche

§15.27Expressions lambda

Une lambda (paramètres) -> corps ressemble à une méthode anonyme. Elle n'est permise que là où il y a un type cible fonctionnel : affectation, invocation, cast, ou retour d'une autre lambda. Évaluer une lambda produit une instance d'une interface fonctionnelle, sans exécuter le corps.

§15.27.1Paramètres

FormeExemple
un identifiant (type inféré)x -> x * 2
types inférés(x, y) -> x + y
types déclarés(int x, int y) -> x + y
var (pour annoter)(@NonNull var x, var y) -> …
paramètre sans nom(k, _) -> k (Java 22)

On ne peut pas mélanger les formes ((int x, y) est une erreur). Un paramètre ne peut pas masquer une variable locale de la méthode englobante (§6.4).

§15.27.2Corps

Une expression ou un bloc. Un corps bloc est compatible void si aucun return n'a de valeur, compatible valeur s'il ne peut pas se terminer normalement et que chaque return a une valeur. Dans le corps :

  • this et super désignent ceux de l'environnement englobant, pas l'objet lambda (contrairement à une classe anonyme) ;
  • les variables locales capturées doivent être final ou effectivement finales ;
  • break, continue et yield ne peuvent pas en sortir.
Java
class Bouton {
    String nom = "OK";
    void installer() {
        Runnable lambda = () -> System.out.println(this.nom);          // this = le Bouton
        Runnable anonyme = new Runnable() {
            public void run() { System.out.println(this); }            // this = l'objet anonyme
        };
    }
}
int total = 0;
liste.forEach(x -> total += x);       // ERREUR : total n'est pas effectivement final
int somme = liste.stream().mapToInt(Integer::intValue).sum();   // la bonne façon

§15.27.3Type d'une lambda

Le type d'une lambda est son type cible T, s'il est compatible : même nombre de paramètres que le type de fonction de T (§9.9), types compatibles, corps compatible void ou valeur selon le retour, exceptions vérifiées autorisées. Si T contient des jokers, la spec dérive un type cible de base (ground target type) : à partir des types de paramètres explicites (§18.5.3) ou par le paramétrage sans joker (§9.9).

§15.27.4Évaluation à l'exécution

L'évaluation produit une référence vers un objet qui implémente l'interface. La spec laisse une grande liberté : ce peut être un nouvel objet ou un objet existant (une lambda sans capture est en pratique un singleton). Ne comptez donc jamais sur l'identité, l'égalité ou le verrou d'une lambda.

§15.28Switch expressions

Un switch utilisé comme expression produit une valeur. Ses règles -> donnent une expression, un bloc qui se termine par yield, ou un throw ; avec des groupes :, chaque chemin doit finir par yield.

§15.28.1Le bloc d'une switch expression

Règles

Le bloc doit être exhaustif (§14.11.1.1). Il doit produire une valeur sur chaque chemin : pas de chute en fin de bloc, pas de return, break ou continue qui en sortent. Son type suit la même logique que le conditionnel : booléen, numérique, ou référence (poly-expression avec cible).

§15.28.2Évaluation à l'exécution

Le sélecteur est évalué ; la première étiquette qui s'applique est choisie (§14.11.1.2) ; sa valeur est le résultat. Si aucune ne s'applique (exhaustivité rompue par une compilation séparée), MatchException.

Java
String taille(Object o) {
    return switch (o) {
        case null                          -> "rien";
        case Integer i when i > 1_000      -> "grand entier";
        case Integer i                     -> "entier";
        case String s when s.length() > 10 -> "long texte";
        case String s                      -> "texte";
        case int[] t                       -> "tableau de " + t.length;
        default                            -> o.getClass().getSimpleName();
    };
}

§15.29Expressions constantes

Une expression constante est une expression de type primitif ou String calculable à la compilation, construite uniquement à partir de :

  • littéraux de type primitif et de String (pas null) ;
  • casts vers un type primitif ou String ;
  • opérateurs unaires + - ~ ! (pas ++/--), multiplicatifs, additifs, décalages, relationnels (pas instanceof), égalités, bit à bit et logiques, && || ? : ;
  • expressions parenthésées ;
  • noms simples ou qualifiés T.nom de variables constantes (§4.12.4).

Elles servent aux étiquettes case, à l'initialisation des variables constantes, au rétrécissement implicite des affectations (§5.2), à l'analyse de flux (§14.22, ch. 16), et sont recopiées dans le binaire (§13.1). Les chaînes constantes sont internées.

Java
final int A = 2 * 3;                // constante : 6
final String S = "x" + A;           // constante : "x6", internée
final int B = Math.max(1, 2);       // PAS constante : appel de méthode
final Integer C = 5;                // PAS constante : type Integer
switch (n) { case A -> {} case B -> {} }   // ERREUR sur B : étiquette non constante
byte b = A;                          // OK : A est constante et 6 tient dans un byte
