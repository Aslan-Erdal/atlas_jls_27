Section 26 · Annexe de l'atlas

Java 25 vs Java 27

Ce qui a changé entre la JLS 25 et la JLS 27, et autour d'elles dans la plateforme Java SE et le JDK. La réponse courte pour le langage : presque rien de permanent. La réponse longue tient dans les détails de la preview, d'Unicode et des 19 JEP livrés par les JDK 26 et 27.

Conclusion pour le langage

Un programme Java 25 compilé sans --enable-preview a exactement le même sens en Java 27. Aucune règle permanente de la JLS n'a été ajoutée, retirée ou modifiée de façon visible entre les deux éditions. Les écarts portent sur les références (Unicode, JVMS), sur la preview, et sur la plateforme.

Note non normative

Comme chaque année, des corrections éditoriales ponctuelles (formulations, exemples) peuvent exister entre deux éditions sans changer la structure. La spec ne publie pas de liste de ces corrections ; elles n'ont pas d'effet connu sur des programmes réels.

Unicode 17 : ce que ça change pour vous

Le langage délègue la notion de lettre et de chiffre Java à Character.isJavaIdentifierStart et isJavaIdentifierPart (§3.8), qui suivent la version d'Unicode de la plateforme. Avec Unicode 17, de nouveaux caractères (nouvelles écritures, idéogrammes, symboles) deviennent valides dans les identifiants ou reçoivent des propriétés. En pratique :

  • un identifiant écrit avec un caractère introduit par Unicode 17 compile en Java 26 et 27, mais pas en Java 25 ;
  • les méthodes de Character, les expressions régulières (\p{L}…) et les conversions de casse peuvent répondre différemment pour ces caractères ;
  • le code existant n'est pas affecté.

26.3La preview de langage : de la 3ᵉ à la 5ᵉ itération

La seule fonctionnalité preview de langage est la même dans les trois versions : les types primitifs dans les motifs, instanceof et switch (section 27). Mais ses règles ont évolué. D'après les tests publiés par HappyCoders, le JDK 26 (JEP 530) a introduit deux contrôles de dominance plus stricts ; le JDK 27 (JEP 532) ne change pas ce qui compile, et améliore le message d'erreur d'exhaustivité, qui nomme désormais le motif manquant.

Sources divergentes

Le résumé d'InfoQ attribue ces deux raffinements (exactitude inconditionnelle, dominance) à la 5ᵉ preview. Les essais de HappyCoders les situent dès Java 26. Les deux s'accordent sur le résultat en Java 27, que décrit la figure ci-dessous.

Conséquence pour la migration

Du code qui utilisait la preview en Java 25 peut ne plus compiler en Java 26 ou 27. C'est précisément le contrat d'une preview (§1.5) : elle peut changer à chaque version. En plus, les classes compilées en preview pour Java 25 (version 69.65535) ne se chargent pas sur une JVM 27 : il faut recompiler.

26.4La plateforme : les JEP des JDK 26 et 27

Le langage bouge peu, mais le JDK, lui, évolue à chaque version. Voici tous les JEP livrés depuis Java 25, filtrables par domaine :

Les JEP qui comptent le plus pour un développeur

HTTP/3 dans HttpClient (JEP 517, Java 26)Le client HTTP de java.net.http sait parler HTTP/3 (sur QUIC). On l'active explicitement par version : HttpClient.newBuilder().version(HttpClient.Version.HTTP_3).
« final veut dire final » (JEP 500, Java 26)Modifier un champ final par réflexion profonde (Field.set après setAccessible(true)) émet désormais un avertissement à l'exécution, en vue d'être interdit par défaut. Des options de ligne de commande permettent d'autoriser explicitement ces mutations pour certains modules. Voir §17.5.3.
Suppression de l'API Applet (JEP 504, Java 26)java.applet, javax.swing.JApplet et les classes associées, dépréciées pour suppression depuis Java 17, disparaissent. Un code qui les référence ne compile plus.
G1 par défaut partout (JEP 523, Java 27)Sans option, HotSpot choisit toujours G1, même sur les petites machines et conteneurs où il choisissait auparavant Serial. Pour garder l'ancien comportement : -XX:+UseSerialGC.
En-têtes d'objets compacts par défaut (JEP 534, Java 27)Les en-têtes d'objets passent à 8 octets sur les plateformes 64 bits (fonctionnalité de production depuis Java 25, JEP 519). Gain mémoire sans changer le code ; désactivable avec -XX:-UseCompactObjectHeaders.
Cryptographie post-quantique pour TLS 1.3 (JEP 527, Java 27)Échange de clés hybride (algorithme classique combiné à ML-KEM) dans les connexions TLS 1.3, pour protéger les échanges contre un futur ordinateur quantique.
