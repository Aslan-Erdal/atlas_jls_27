Chapitre 13 · Java SE 27 Edition

Compatibilité binaire

Quand une bibliothèque évolue, les programmes qui l'utilisent ne sont pas toujours recompilés. Ce chapitre dit précisément quels changements laissent fonctionner les anciens binaires, et lesquels les cassent à l'édition de liens.

Source : JLS SE 27, chapitre 13 Sections : 13.1 à 13.5

§13Pourquoi ce chapitre existe

Les outils de développement recompilent en général tout ce qui dépend d'une classe modifiée. Mais quand une bibliothèque est distribuée (Maven Central, le JDK lui-même), ses utilisateurs ne recompilent pas : un JAR compilé contre la version 1 tourne avec la version 2. Ce chapitre est donc essentiel pour quiconque publie une API.

§13.1La forme d'un binaire

La spec ne fixe pas le format .class (c'est la JVMS), mais elle impose des propriétés au binaire produit par un compilateur. Les plus importantes :

  • Noms binaires. Une classe de plus haut niveau a pour nom binaire son nom canonique. Une classe membre : Externe$Membre. Une classe locale : Externe$1Locale (un nombre, puis le nom). Une classe anonyme : Externe$1.
  • Références symboliques. Un accès à un champ ou un appel de méthode est compilé avec le nom du membre et un type qualifiant : le type statique de l'expression qualifiante (ou la classe courante), pas forcément la classe qui déclare le membre. Une méthode est identifiée par son nom et son descripteur (types effacés des paramètres et du retour).
  • Constantes recopiées. Une référence à une variable constante (§4.12.4) est remplacée par sa valeur : le binaire client ne référence pas le champ.
  • Le binaire doit conserver assez d'information pour les génériques (signatures), les classes imbriquées, les records, les classes scellées (liste des sous-classes autorisées) et les paramètres de méthodes.

§13.2Ce que la compatibilité binaire est, et n'est pas

Définition

Un changement d'un type est compatible binaire avec des binaires préexistants si ceux-ci, qui se liaient sans erreur avant le changement, continuent à se lier sans erreur après.

Les deux autres compatibilités sont indépendantes. Exemples typiques :

Compatible binaire, pas sourceAjouter une méthode surchargée f(Integer) à côté de f(Object) : les anciens binaires appellent toujours f(Object) (descripteur figé), mais un client recompilé appellera f(Integer), ou ne compilera plus en cas d'ambiguïté.
Compatible source, pas binaireChanger int taille() en long taille() : un client recompilé fonctionne (long t = x.taille(); s'il faisait var), mais un ancien binaire lève NoSuchMethodError, car le retour fait partie du descripteur.

§13.3Évolution des paquetages et modules

Ajouter une classe ou un paquetage est compatible, sauf conflit de nom avec un type existant. Supprimer une classe utilisée provoque NoClassDefFoundError. Pour les modules, retirer un exports ou un requires transitive casse les clients qui en dépendaient ; renommer un module casse tous ses requires.

§13.5Évolution des interfaces

Les règles sont les mêmes que pour les classes, avec trois particularités, toutes visibles dans la catégorie « Interfaces » de la figure 13.1 :

  • Ajouter une méthode abstraite ne casse pas l'édition de liens, mais un appel sur une ancienne implémentation lève AbstractMethodError (§13.5.4). C'est la raison d'être des méthodes default : faire évoluer Collection en Java 8 (stream(), removeIf) sans casser les implémentations existantes.
  • Ajouter une méthode default peut créer, à l'exécution, un conflit entre deux defaults hérités par une classe compilée avant : l'appel lève alors IncompatibleClassChangeError (§13.5.7).
  • Interfaces d'annotation : ajouter un élément avec une valeur par défaut est sûr ; sans valeur par défaut, lire cet élément sur une annotation compilée avant lève IncompleteAnnotationException (§13.5.8).

Rendre une interface sealed (§13.5.2), retirer public (§13.5.1) ou une superinterface (§13.5.3) casse les clients comme pour les classes. Changer ses paramètres de type (§13.5.5) ou ses champs (§13.5.6) suit les règles des §13.4.5 et §13.4.8.

Les autres règles à retenir

Ajouter est presque toujours sûrNouvelles classes, méthodes, champs, constructeurs, constantes d'enum, méthodes default : compatibles binaires. Les risques sont surtout source (ambiguïtés) ou comportementaux.
Retirer casse toujoursSupprimer un élément public ou protégé utilisé produit NoSuchMethodError, NoSuchFieldError ou NoClassDefFoundError chez les clients.
Changer une signature = retirer + ajouterType d'un paramètre, type de retour, nombre de paramètres, ordre des composants d'un record : l'ancien descripteur disparaît.
Restreindre casseRendre une classe final, abstract ou sealed, réduire l'accès, rendre une méthode final, changer static en instance ou l'inverse.
Note non normative

Des outils automatisent ces vérifications avant publication : japicmp, revapi, ou le plugin animal-sniffer. Le JDK lui-même suit ces règles pour garantir que les binaires anciens tournent sur les nouvelles versions.
