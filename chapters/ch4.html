Chapitre 4 · Java SE 27 Edition

Types, valeurs et variables

Le cœur du système de types : les huit types primitifs et leur arithmétique exacte, les types référence, les génériques avec jokers, l'effacement, le sous-typage, et les différentes sortes de variables.

Source : JLS SE 27, chapitre 4 Sections : 4.1 à 4.12

§4.1Les sortes de types et de valeurs

Java est statiquement typé : chaque variable et chaque expression a un type connu à la compilation. Il est aussi fortement typé : le type limite les valeurs qu'une variable peut contenir et les opérations permises. Les types se répartissent en deux familles, et les valeurs aussi :

Membresboolean et les types numériques : byte short int long char (intégraux), float double (flottants)types classe, types interface, variables de type, types tableau
Valeursvaleurs primitives, copiées à chaque affectationréférences vers des objets, ou null
Partagejamais : deux variables n'ont jamais la même valeur « en commun »plusieurs références peuvent désigner le même objet
Défini dans§4.2§4.3

Il existe un troisième type à part : le type nul, le type de l'expression null. Il n'a pas de nom, on ne peut donc ni déclarer une variable de ce type ni faire un cast vers lui. La valeur null se convertit en n'importe quel type référence ; en pratique, on peut faire comme si null était un littéral spécial de tous les types référence.

§4.2Types primitifs et valeurs

Un type primitif est prédéfini et nommé par son mot-clé réservé. Les valeurs primitives ne partagent pas d'état entre elles : int b = a; copie la valeur, et modifier b ne touche jamais a.

Règles

Si l'un des opérandes (hors décalages) est long, l'opération se fait sur 64 bits ; sinon elle se fait sur 32 bits, même pour des byte ou des short : ils sont promus en int (§5.6).

Les débordements sont silencieux : le résultat garde les bits de poids faible. Les seules exceptions levées sont ArithmeticException pour / et % par zéro, NullPointerException lors d'un unboxing de null, et OutOfMemoryError si un boxing n'a plus de mémoire.

Java
int max = Integer.MAX_VALUE;
max + 1;                      // -2147483648 : débordement silencieux
Math.addExact(max, 1);        // ArithmeticException : version vérifiée
Math.abs(Integer.MIN_VALUE);  // -2147483648 ! l'opposé de MIN_VALUE n'existe pas en int

byte b = 10;
b = b + 1;                    // ERREUR : b + 1 est un int (promotion), perte possible
b += 1;                       // OK : l'affectation composée contient un cast implicite (§15.26.2)
b++;                          // OK : idem

7 / 2;     // 3   (division entière tronquée vers zéro)
-7 / 2;    // -3  (pas -4 : troncature, pas arrondi inférieur)
-7 % 2;    // -1  (le reste a le signe du dividende)
Math.floorMod(-7, 2);  // 1
1 / 0;     // ArithmeticException
1.0 / 0;   // Infinity : en flottant, pas d'exception

§4.2.3Types flottants et leurs valeurs

float et double sont les formats binaires 32 et 64 bits de la norme IEEE 754. Une valeur finie non nulle s'écrit s × m × 2e−N+1, avec un signe, une mantisse entière et un exposant borné :

Paramètrefloatdouble
Précision N (bits de mantisse, implicite compris)2453
Bits d'exposant / biais8 / 12711 / 1023
Emin / Emax−126 / 127−1022 / 1023
Chiffres décimaux fiables6–915–17

En plus des nombres finis, chaque format contient deux zéros (+0.0 et −0.0), deux infinis et des valeurs NaN (« not a number »). Les nombres trop petits pour l'exposant minimal deviennent sous-normaux : la précision diminue graduellement au lieu de tomber d'un coup à zéro.

Règles · NaN et zéros

NaN est non ordonné : <, <=, >, >= et == renvoient false si un opérande est NaN, et != renvoie true. Donc x != x est vrai si et seulement si x est NaN.

+0.0 et −0.0 sont égaux pour ==, mais se distinguent par d'autres opérations : 1.0 / -0.0 vaut -Infinity.

Java
double nan = 0.0 / 0;
nan == nan;                  // false
Double.isNaN(nan);           // true : la bonne façon de tester
Double.valueOf(nan).equals(nan);  // true : equals compare les bits, pas ==
0.0 == -0.0;                 // true
Double.valueOf(0.0).equals(-0.0); // false
Double.compare(0.0, -0.0);   // 1 : compare et equals ordonnent -0.0 < 0.0 < ... < NaN

§4.2.4Opérations sur les flottants

Les opérateurs sont les mêmes que pour les entiers, sauf les décalages et le complément ~. Si un opérande est double, le calcul se fait en double, sinon en float s'il y a un float.

Règles · l'arithmétique IEEE 754

Chaque résultat est arrondi au plus proche, avec égalité vers le pair (« round to nearest, ties to even »). Le débordement donne l'infini ; le sous-dépassement donne un sous-normal ou zéro. Aucune opération flottante ne lève d'exception : 0.0/0 donne NaN.

Depuis Java 17 (JEP 306), toutes les opérations flottantes sont strictes : mêmes résultats au bit près sur toutes les plateformes. Le modificateur strictfp est devenu sans effet.

Java
0.1 + 0.2;                  // 0.30000000000000004 : 0.1 et 0.2 ne sont pas représentables
0.1 + 0.2 == 0.3;           // false
Math.abs(a - b) < 1e-9;     // comparer avec une tolérance adaptée au problème

float f = 16_777_216f;
f + 1 == f;                 // true : au-delà de 2^24, un float ne distingue plus les entiers consécutifs

(int) 3.99;                 // 3     : troncature vers zéro
(int) Double.NaN;           // 0
(int) 1e20;                 // 2147483647 : saturation (§5.1.3)

new BigDecimal("0.1").add(new BigDecimal("0.2"));   // 0.3 exactement : pour l'argent
Piège

new BigDecimal(0.1) donne 0.1000000000000000055511151231257827… : le constructeur à partir d'un double conserve l'erreur de représentation. Utilisez BigDecimal.valueOf(0.1) ou le constructeur à partir d'un String.

§4.2.5Le type boolean

Deux valeurs, true et false. Opérateurs : == !=, !, & ^ | (évaluent toujours les deux opérandes), && || (court-circuit), ? :, et la concaténation ("x" + true).

  • Les instructions if, while, do, for, l'opérande de ! et les conditions de ? : exigent une expression boolean (ou Boolean, unboxé).
  • Aucune conversion entre boolean et les types numériques. Pour un entier : x != 0. Pour un booléen vers un entier : b ? 1 : 0.

§4.3Types référence et valeurs

Quatre sortes de types référence : les types classe (§8.1), les types interface (§9.1), les variables de type (§4.4) et les types tableau (§10.1). Un type classe ou interface peut être paramétré (List<String>) et qualifié par un type englobant (Map.Entry<K,V>, Externe<A>.Interne<B>). Des annotations de type peuvent s'y placer (@NonNull String).

§4.3.1Objets

Un objet est soit une instance de classe, soit un tableau. Les valeurs référence sont des pointeurs vers ces objets, ou null. Façons de créer un objet dans le langage :

Explicitesnew Classe(...) (§15.9) ; création de tableau new int[3] ou initialiseur {1, 2} (§15.10, §10.6)
Implicitesconcaténation de chaînes (§15.18.1) ; boxing (§5.1.7) ; évaluation d'une lambda ou référence de méthode (§15.27.4, §15.13.3) ; littéraux chaîne et text blocks

Les opérations sur les références sont : accès aux champs, appel de méthode, cast, concaténation, instanceof, égalité == / != (identité), et l'opérateur conditionnel.

Java · identité et état partagé
class Point { int x, y; }

Point p = new Point();
Point q = p;          // q et p désignent LE MÊME objet
q.x = 5;
System.out.println(p.x);   // 5 : la modification est visible par les deux références

Point r = new Point(); r.x = 5;
p == r;               // false : même contenu, objets distincts
int a = 5, b = a; b++;
System.out.println(a);     // 5 : les primitifs ne partagent rien
Évolution à surveiller

Le projet Valhalla prépare des classes valeur sans identité (JEP 401). Elles ne font pas partie de Java SE 27, même en preview (§1.5.2 ne liste qu'une preview de langage). Dans la JLS 27, tout objet a une identité.

§4.3.3La classe String

Les instances de String représentent des suites d'unités de code Unicode. Une String est immuable : sa valeur ne change jamais. Le langage lui donne trois privilèges : les littéraux (§3.10.5), les text blocks (§3.10.6) et l'opérateur + de concaténation (§15.18.1).

§4.3.4Quand deux types référence sont-ils identiques ?

Deux types classe ou interface sont identiques s'ils ont le même nom binaire (§13.1) et, s'ils sont paramétrés, des arguments de type identiques (récursivement). Deux variables de type sont identiques si elles sont issues de la même déclaration. Deux types tableau, si leurs types de composants le sont.

Note non normative

À l'exécution, l'identité d'une classe inclut aussi son chargeur : deux classes de même nom chargées par deux chargeurs différents sont distinctes, et un cast de l'une vers l'autre échoue (§12.2). C'est la source des célèbres « ClassCastException: Foo cannot be cast to Foo » des serveurs d'applications.

§4.4Variables de type

Une variable de type est un identifiant non qualifié utilisé comme type dans le corps d'une classe, interface, méthode ou constructeur générique. Elle est introduite par une déclaration de paramètre de type, avec une borne facultative :

Grammaire (§4.4)
TypeParameter:
    {TypeParameterModifier} TypeIdentifier [TypeBound]

TypeBound:
    extends TypeVariable
    extends ClassOrInterfaceType {AdditionalBound}

AdditionalBound:
    & InterfaceType
Règles

Sans borne, la borne est Object. Avec plusieurs bornes T extends A & B & C, seule la première peut être une classe ou une variable de type ; les suivantes sont des interfaces. Si la première est une variable de type, aucune autre borne n'est permise.

Les membres d'une variable de type sont ceux de l'intersection de ses bornes (§4.9) : on peut appeler sur un T toute méthode de A, B ou C.

Java
static <T extends Number & Comparable<T>> T max(List<T> xs) {
    T best = xs.get(0);
    for (T x : xs)
        if (x.compareTo(best) > 0) best = x;    // méthode de Comparable<T>
    System.out.println(best.doubleValue());      // méthode de Number
    return best;
}

<T extends Comparable & Number> void f() {}   // ERREUR : la classe doit venir en premier
<T, U extends T & Runnable> void g() {}        // ERREUR : après une variable de type, aucune autre borne
Piège

Les membres private d'une borne de classe ne sont pas accessibles via la variable de type, même depuis l'intérieur de cette classe : une variable de type n'hérite que des membres accessibles comme le ferait une sous-classe fictive.

§4.5Types paramétrés

Une déclaration générique C<F1,…,Fn> définit un ensemble de types paramétrés C<T1,…,Tn>. Chaque argument est un type référence ou un joker. Il faut exactement n arguments ; chaque argument (après capture) doit respecter la borne du paramètre correspondant.

Java
Map<String, Integer> m;   // bien formé
List<int> l;               // ERREUR : les arguments de type sont des types référence
Map<String> x;             // ERREUR : mauvais nombre d'arguments
class Boite<T extends Number> {}
Boite<String> b;           // ERREUR : String n'est pas un sous-type de Number

§4.5.1Arguments de type et jokers

Un joker (wildcard) ? représente un type inconnu, éventuellement borné :

FormeLit-on ?Écrit-on ?Usage typique
List<? extends Number>oui, des Numbernon (sauf null)producteur : on en extrait des valeurs
List<? super Integer>seulement des Objectoui, des Integerconsommateur : on y dépose des valeurs
List<?>des Objectnon (sauf null)code indépendant du type d'élément

Mnémotechnique de Joshua Bloch : PECS, « Producer Extends, Consumer Super ». La signature de Collections.copy en est l'exemple type : <T> void copy(List<? super T> dest, List<? extends T> src).

Règle · la relation de contenance

La spec définit quand un argument de type contient un autre (noté T <= S). C'est la base du sous-typage entre types paramétrés :

  • ? extends T <= ? extends S si T <: S
  • ? extends T <= ?
  • ? super T <= ? super S si S <: T
  • ? super T <= ? et ? super T <= ? extends Object
  • T <= T, T <= ? extends T, T <= ? super T

Le point fondamental : sans joker, les types paramétrés sont invariants. List<Integer> n'est pas un sous-type de List<Number>, sinon on pourrait y ajouter un Double. Vérifiez n'importe quelle paire :

§4.5.2Membres et constructeurs des types paramétrés

Les membres de C<T1,…,Tn> s'obtiennent en appliquant la substitution [F1:=T1,…,Fn:=Tn] aux membres de la déclaration générique. Si certains arguments sont des jokers, on applique d'abord la conversion par capture (§5.1.10), qui remplace chaque joker par une nouvelle variable de type fraîche :

Java
List<? extends Number> nums = List.of(1, 2.5);
Number n = nums.get(0);   // get renvoie CAP#1, dont la borne supérieure est Number
nums.add(3);              // ERREUR : add attend un CAP#1, et 3 n'est pas un CAP#1

List<? super Integer> sink = new ArrayList<Number>();
sink.add(3);              // OK : Integer est un sous-type de CAP#2 (borne inférieure Integer)
Object o = sink.get(0);   // on ne sait rien de plus que Object

Les messages de javac nomment ces types capturés CAP#1, capture of ? : c'est ce mécanisme qui est à l'œuvre.

§4.6Effacement de type

L'effacement (type erasure), noté |T|, associe à chaque type un type sans paramètres. Les génériques Java sont vérifiés à la compilation puis effacés : la JVM ne voit que les types effacés.

Type TEffacement |T|Exemple
Type paramétré G<T1,…,Tn>|G|Map<K,List<V>> → Map
Type imbriqué T.C|T|.CExterne<A>.Interne → Externe.Interne
Tableau T[]|T|[]List<String>[] → List[]
Variable de typeeffacement de sa borne la plus à gaucheT extends Number & Comparable → Number
Intersection A & B|A|
Tout autre typelui-mêmeint, String

L'effacement d'une signature de méthode efface ses types de paramètres. Deux méthodes de même nom dont les signatures s'effacent pareil ne peuvent pas coexister :

Java
class C {
    void f(List<String> l) {}
    void f(List<Integer> l) {}   // ERREUR : même effacement f(List)
}

static <T extends Comparable<? super T>> T max(Collection<? extends T> c)  // signature réelle
// dans le bytecode : Comparable max(Collection)
// Collections.max utilise <T extends Object & Comparable<? super T>> pour que
// l'effacement reste Object, compatible avec l'ancienne API d'avant Java 5

Quand une classe redéfinit une méthode générique et que les effacements diffèrent, le compilateur génère une méthode pont (bridge method) synthétique pour que le polymorphisme fonctionne dans le bytecode.

§4.7Types réifiables

Un type est réifiable si l'information de type est entièrement disponible à l'exécution, c'est-à-dire si l'effacement ne perd rien. Sont réifiables :

  • les types primitifs ;
  • les types classe ou interface non génériques (String) ;
  • les types bruts (List) ;
  • les types paramétrés dont tous les arguments sont des jokers non bornés (Map<?,?>) ;
  • les types tableau dont le type d'élément est réifiable ;
  • les types imbriqués T.C dont chaque composant est réifiable.

Seuls les types réifiables peuvent servir là où une vérification d'exécution est nécessaire :

Java
o instanceof List<?>          // OK
o instanceof List<String>     // ERREUR (sauf si le type statique de o garantit déjà List<String>)
new List<?>[10]               // OK
new List<String>[10]          // ERREUR : création de tableau générique
new T[10]                     // ERREUR : T n'est pas réifiable
catch (MonExc<String> e)      // impossible : une classe générique ne peut pas étendre Throwable
Note non normative

Depuis Java 16, instanceof accepte un type non réifiable si le test est sûr : List<String> l; if (l instanceof ArrayList<String> a) est permis car l'information générique est déjà connue statiquement (§15.20.2).

§4.8Types bruts

Un type brut est le nom d'une classe ou interface générique utilisé sans arguments de type (List au lieu de List<String>). Il existe uniquement pour la compatibilité avec le code antérieur à Java 5.

Règles

Les membres d'un type brut sont les effacements des membres de la déclaration générique : List.get renvoie Object. Utiliser un membre d'un type brut d'une manière qui pourrait être incorrecte produit un avertissement non vérifié (unchecked warning).

L'usage des types bruts dans du nouveau code est fortement déconseillé ; la spec prévient qu'une version future pourrait l'interdire.

Java
List brute = new ArrayList();
brute.add("texte");                 // avertissement unchecked
List<Integer> ints = brute;          // avertissement unchecked : conversion non vérifiée (§5.1.9)
int i = ints.get(0);                // ClassCastException, loin de la vraie cause

class Exemple<T> { List<String> noms() { return List.of(); } }
Exemple e = new Exemple();          // type brut
List<String> n = e.noms();          // avertissement : les membres sont effacés, même ceux sans T !
Piège

Le dernier cas surprend : sur un type brut, tous les membres sont effacés, y compris ceux qui ne dépendent pas des paramètres de type. Un seul type brut contamine ainsi toute l'API de l'objet.

§4.9Types intersection

Un type intersection s'écrit T1 & … & Tn. Il n'apparaît que dans certaines positions : bornes de variables de type (§4.4), casts (§15.16), et comme résultat de l'inférence ou de la borne supérieure minimale (§4.10.4). Ses membres sont ceux d'une classe fictive qui hériterait de tous les Ti.

Java
Runnable r = (Runnable & Serializable) () -> System.out.println("ok");
// la lambda implémente les deux interfaces : elle peut être sérialisée

var x = flag ? 1 : "a";    // type inféré : une intersection, voir §4.10.4

§4.10Sous-typage

Les relations de sous-typage et de supertypage sont binaires. La spec définit d'abord les supertypes directs (S >1 T), puis S :> T comme la fermeture réflexive et transitive. T <: S se lit « T est un sous-type de S ». Un sous-type propre exclut l'égalité.

§4.10.1Sous-typage entre types primitifs

Une flèche va d'un type vers son supertype direct. boolean n'a aucune relation avec les autres.

Ce « sous-typage » primitif ne signifie pas qu'une valeur int est un long : il sert à l'inférence et à la résolution de surcharge. La conversion réelle est l'élargissement (§5.1.2). Notez que char et short ne sont sous-types l'un de l'autre dans aucun sens, et que long → float est permis malgré la perte de précision possible.

§4.10.2Sous-typage entre classes et interfaces

Pour une classe ou interface non générique C, les supertypes directs sont : sa superclasse directe, ses superinterfaces directes, et Object si C est une interface sans superinterface.

Pour un type générique C<F1,…,Fn>, les supertypes directs de C<T1,…,Tn> sont :

  • les supertypes directs de la déclaration, avec la substitution [F1:=T1,…] ;
  • C<S1,…,Sn> où chaque Si contient Ti (§4.5.1) : c'est ce qui rend List<Integer> <: List<? extends Number> ;
  • le type brut C ;
  • Object si C est une interface sans superinterface.

Avec des jokers dans C<R1,…>, on capture d'abord (§5.1.10), puis on applique la règle ci-dessus au type capturé.

§4.10.3Sous-typage entre tableaux

  • Si S et T sont des types référence et S >1 T, alors S[] >1 T[] : les tableaux sont covariants.
  • Object >1 Object[], Cloneable >1 Object[], java.io.Serializable >1 Object[].
  • Pour un type primitif P : Object, Cloneable et Serializable sont supertypes directs de P[]. Mais int[] n'est jamais sous-type de long[] ni de Object[].

La covariance des tableaux est vérifiée à l'exécution : écrire un Double dans un Integer[] vu comme Number[] lève ArrayStoreException (§10.5). Les génériques, invariants, évitent ce problème à la compilation.

§4.10.4Borne supérieure minimale (lub)

La lub (least upper bound) d'un ensemble de types est le supertype commun le plus précis. Elle sert à typer l'opérateur conditionnel (§15.25), à l'inférence (ch. 18) et aux switch expressions. L'algorithme :

  1. Pour chaque type, calculer l'ensemble de ses supertypes effacés (EST) ; intersecter ces ensembles (EC).
  2. Garder les éléments minimaux de EC (MEC) : ceux dont aucun sous-type propre n'est dans EC.
  3. Pour chaque élément générique de MEC, calculer le meilleur paramétrage commun, avec des jokers si besoin (fonction lcta, possiblement récursive).
  4. La lub est l'intersection de ces candidats.
Java
var x = flag ? Integer.valueOf(1) : "a";
// lub(Integer, String) =
//   Object & Serializable & Comparable<? extends Object & Serializable & Comparable<?> & ...>
//          & Constable & ConstantDesc
x.compareTo(null);   // compile : x a toutes les méthodes de l'intersection

var l = flag ? new ArrayList<String>() : new LinkedList<String>();
// lub = AbstractList<String> & Serializable & Cloneable (List<String> en découle)

La lub peut être infinie en théorie (types récursifs comme Comparable) ; la spec autorise le compilateur à couper la récursion avec un joker non borné.

§4.10.5Projections de type

Un type inféré peut mentionner des variables de capture, qui n'ont pas de nom dans le langage. Pour donner un type à une variable déclarée avec var (§14.4.1), la spec calcule une projection supérieure : le supertype le plus précis qui ne mentionne plus ces variables. Il existe aussi une projection inférieure, utilisée pour les bornes ? super.

Java
List<? extends Number> nums = ...;
var e = nums.get(0);           // type de l'expression : CAP#1 ; type de e : Number (projection)
var copie = nums;              // List<? extends Number> : le joker est rétabli

List<?> inconnue = ...;
var x = inconnue.get(0);       // Object

§4.11Où les types sont utilisés

La spec distingue 17 contextes de type : des positions syntaxiques où un type apparaît. Ils comptent pour deux raisons : les annotations de type (§9.7.4) et l'exception lexicale >> (§3.2).

Dans les déclarations
  • extends / implements d'une classe, extends d'une interface
  • type de retour d'une méthode, y compris d'un élément d'annotation
  • throws d'une méthode ou d'un constructeur
  • extends d'un paramètre de type
  • type d'un champ, d'un paramètre formel, d'un paramètre récepteur
  • type d'une variable locale, d'un composant de record
  • type d'un paramètre d'exception
  • type dans un motif (§14.30)
Dans les expressions
  • arguments de type explicites d'un appel
  • création d'instance de classe non qualifiée ou qualifiée
  • création de tableau
  • opérateur de cast
  • instanceof
  • référence de méthode (Type::m, Type::new)

Les types n'apparaissent pas comme valeurs : String.class est une expression de type Class<String>, pas un type.

§4.12Variables

Une variable est un emplacement de stockage, associé à un type (son type à la compilation). Sa valeur change par affectation ou par ++/--. La compatibilité entre la valeur et le type est garantie par le langage, sauf en cas de pollution du tas (voir §4.12.2).

§4.12.1Variables de type primitif

Elle contient toujours une valeur primitive de ce type exact.

§4.12.2Variables de type référence

Une variable de type classe T contient null ou une référence vers une instance de T ou d'une sous-classe. Une variable de type interface, null ou une instance d'une classe qui implémente l'interface. Une variable de type tableau T[], null ou un tableau de type S[] avec S affectable à T.

Règle · pollution du tas

Une variable de type paramétré peut désigner un objet qui n'est pas de ce type paramétré. C'est la pollution du tas (heap pollution). Elle ne peut arriver que si le programme a produit un avertissement non vérifié à la compilation ; sans avertissement, il n'y a jamais de pollution.

Java
static void pollue(List<String>... listes) {   // avertissement : varargs générique
    Object[] tab = listes;                     // un tableau List<String>[] vu comme Object[]
    tab[0] = List.of(42);                      // aucune erreur : la vérification ne voit que List
    String s = listes[0].get(0);               // ClassCastException ici
}

C'est pour ça que les méthodes à paramètres variadiques génériques produisent un avertissement, que @SafeVarargs (§9.6.4.7) permet de supprimer quand le code est réellement sûr.

§4.12.3Les sortes de variables

§4.12.4Variables final

Une variable final ne peut être affectée qu'une seule fois. Une variable final déclarée sans initialiseur est dite blank final ; elle doit être définitivement affectée exactement une fois (ch. 16).

final int[] t = {1, 2};
t[0] = 9;                    // OK : la référence est final, pas le contenu

final int MAX = 10;          // variable constante
final int n = lireEntier();  // final, mais pas constante

int compteur = 0;
Runnable r = () -> System.out.println(compteur);   // OK tant que compteur est effectivement final
compteur++;                  // rend la ligne précédente illégale : ERREUR à la capture

final int x;
if (cond) x = 1; else x = 2; // OK : blank final affectée exactement une fois sur chaque chemin

§4.12.6Types, classes et interfaces

Il faut distinguer le type d'une variable ou expression, connu à la compilation, de la classe de l'objet désigné, connue à l'exécution. Une variable a toujours un type ; un objet a toujours une classe. Une variable de type interface désigne un objet dont la classe implémente l'interface ; il n'existe pas d'objet « d'interface ».

Java
CharSequence cs = new StringBuilder("abc");
// type de cs : CharSequence (compilation) ; classe de l'objet : StringBuilder (exécution)
cs.length();       // OK : méthode de CharSequence
cs.append("d");    // ERREUR : append n'est pas un membre du type CharSequence
((StringBuilder) cs).append("d");   // OK après un cast vérifié à l'exécution
