§1Quel genre de langage est Java ?

La spec ouvre sur une définition en quelques adjectifs. Chacun est un engagement précis que le reste du document tient :

PropriétéCe que ça veut dire concrètementOù c'est défini
GénéralistePas de domaine cible : serveurs, outils, mobile, embarqué.—
ConcurrentLes threads, verrous et le modèle mémoire font partie du langage lui-même, pas d'une bibliothèque ajoutée.ch. 17
Basé sur les classes, orienté objetTout code vit dans une classe ou une interface ; héritage simple de classes, héritage multiple d'interfaces.ch. 8, ch. 9
Fortement et statiquement typéChaque expression a un type connu à la compilation ; aucune conversion silencieuse dangereuse.ch. 4, ch. 5, ch. 15
Haut niveauPas d'accès à la représentation machine (pas de pointeurs, pas d'arithmétique d'adresses), gestion mémoire automatique.ch. 4, ch. 12
SûrAucune construction au comportement non spécifié : un accès hors bornes lève une exception au lieu de corrompre la mémoire.ch. 10, ch. 15

Le choix de conception le plus structurant est la philosophie « langage de production, pas de recherche » : les auteurs citent l'article de C. A. R. Hoare sur la conception des langages pour justifier qu'on n'intègre que des idées déjà éprouvées ailleurs. C'est pour cette raison que Java évolue lentement et passe par des phases de preview (§1.5) avant de figer une fonctionnalité.

Distinction fondamentale

La spec sépare rigoureusement deux mondes. Les erreurs de compilation sont celles que le compilateur peut et doit détecter ; tout le reste se passe à l'exécution (chargement, liaison, optimisation dynamique, exécution). Savoir de quel côté tombe une règle est la première question à se poser en lisant n'importe quelle section.

Les deux couloirs ne se confondent jamais. Le même programme peut illustrer les deux catégories :

Java
String s = 42;            // ERREUR de compilation : int n'est pas assignable à String (§5.2)

Object o = "texte";
Integer i = (Integer) o;  // compile (le cast est permis, §5.5)
                          // mais lève ClassCastException à l'exécution (§15.16)

int[] t = new int[3];
t[3] = 1;                 // compile, puis ArrayIndexOutOfBoundsException (§15.10.4)

Le deuxième cas montre une idée-clé du chapitre : il n'y a pas de faille dans le système de types. Un cast vers un type référence que le compilateur ne peut pas prouver correct est accepté, mais un contrôle est exécuté au moment du cast. Le programme ne peut jamais manipuler un String en croyant tenir un Integer.

§1.1Organisation de la spécification

Le §1.1 résume les 18 autres chapitres. Plutôt que de les lire dans l'ordre, il est plus utile de voir comment ils s'empilent : du texte brut tout en bas jusqu'au comportement des threads tout en haut. Chaque couche s'appuie sur celles du dessous.

Les points que le §1.1 pose dès maintenant

Deux familles de types

Les types primitifs sont identiques sur toutes les machines et toutes les implémentations. C'est une rupture nette avec C, où la taille d'un int dépend de la plateforme. Les valeurs primitives ne partagent jamais d'état : copier un int copie la valeur.

Les types référence sont les classes, les interfaces et les tableaux. Ils désignent des objets créés dynamiquement, vers lesquels plusieurs références peuvent pointer. Tout objet, tableaux compris, possède les méthodes de Object, racine unique de la hiérarchie.

Ce qu'une variable peut contenir

Java
int n = 7;                       // exactement un int, jamais null
Number x = Integer.valueOf(7);   // null, ou une instance de Number ou d'une sous-classe
Comparable<String> c = "abc";    // null, ou toute instance d'une classe qui implémente l'interface
int[] tab = {1, 2, 3};           // null, ou une référence vers un tableau d'int
Object o = tab;                  // null, ou n'importe quel objet, tableaux compris

Boxing et unboxing

Chaque primitif a une classe enveloppe (Integer, Double…). Le compilateur insère lui-même les conversions dans beaucoup de contextes. Pratique, mais c'est une vraie conversion avec ses pièges :

Java
Integer a = 127, b = 127;
System.out.println(a == b);      // true  : valeurs dans le cache garanti -128..127 (§5.1.7)
Integer c = 128, d = 128;
System.out.println(c == d);      // false en général : == compare des références
System.out.println(c.equals(d)); // true

Integer rien = null;
int v = rien;                    // NullPointerException : l'unboxing appelle rien.intValue()

L'ordre des déclarations compte peu

Une classe peut utiliser une méthode ou une autre classe déclarée plus bas. L'ordre n'a d'importance que pour les variables locales, les classes et interfaces locales, et l'ordre des initialiseurs de champs.

Java
class A {
    void m() { aide(); }  // OK : aide() est déclarée plus bas
    void aide() {}

    int b = a + 1;        // ERREUR : référence en avant illégale vers a (§8.3.3)
    int a = 1;
}

Pas de goto, des booléens stricts

Java
int n = 3;
if (n) { }          // ERREUR : int ne se convertit pas en boolean
if (n = 0) { }      // ERREUR aussi : le bug classique du C devient impossible
if (n != 0) { }     // correct

externe:
for (int i = 0; i < 10; i++)
    for (int j = 0; j < 10; j++)
        if (i * j > 20) break externe;   // sort des deux boucles d'un coup (§14.15)

Java
int[][] triangle = new int[3][];
triangle[0] = new int[1];
triangle[1] = new int[2];

Note non normative

La spec recommande que la plupart des exceptions définies par l'utilisateur soient vérifiées. En pratique, beaucoup de bibliothèques modernes préfèrent des exceptions non vérifiées, car les exceptions vérifiées s'accordent mal avec les lambdas. Le chapitre 11 donne les règles exactes pour trancher en connaissance de cause.

Évolution depuis le texte d'origine

Le §1.1 décrit encore la méthode finalize comme un moyen de nettoyer un objet avant sa récupération. Elle est dépréciée pour suppression depuis le JDK 18 (JEP 421). Pour libérer des ressources, on utilise try-with-resources (§14.20.3) ou java.lang.ref.Cleaner.

§1.2Les exemples de la spec

La plupart des exemples sont des programmes complets, exécutables tels quels. Le modèle type est une classe avec une méthode main :

Test.java
class Test {
    public static void main(String[] args) {
        for (int i = 0; i < args.length; i++)
            System.out.print(i == 0 ? args[i] : " " + args[i]);
        System.out.println();
    }
}
Terminal
javac Test.java
java Test Hello, world.
# affiche : Hello, world.

L'opérateur conditionnel ? : n'insère l'espace qu'entre les mots, pas avant le premier.

Ce que Java 27 permet en plus

Depuis Java 11 on peut lancer un fichier source sans compilation séparée, et depuis Java 25 (JEP 512) un fichier peut se réduire à une méthode main d'instance dans une classe implicitement déclarée (§8.1.8, §12.1.4).

Hello.java
void main() {
    IO.println("Hello, world.");
}
Terminal
java Hello.java    # compile en mémoire puis exécute

Normatif ou non normatif ?

Seul le texte normatif définit le langage. Les exemples et notes en retrait servent à comprendre mais ne créent aucune règle. Dans cet atlas, les encadrés bleus « Règle » correspondent au texte normatif, les blocs gris « Note non normative » au texte explicatif.

La substitution, en pratique

Java
class Boite<T> {
    T contenu;
    T get() { return contenu; }
}
// Pour Boite<String>, la spec applique [T:=String] :
//   champ   T contenu   devient   String contenu
//   méthode T get()     devient   String get()
Boite<String> b = new Boite<>();
String s = b.get();   // aucun cast nécessaire

Avec plusieurs paramètres, la substitution est simultanée : pour Map<K,V> utilisé comme Map<String,Integer>, on applique [K:=String, V:=Integer] en une fois.

Angle mort volontaire

La spec ne décrit pas la réflexion (java.lang.reflect) ni javax.lang.model. Quand elle énumère les façons de créer un objet, elle ne compte que les moyens du langage. En réalité, Constructor.newInstance, clone(), la désérialisation ou les MethodHandle créent aussi des objets, parfois sans passer par un constructeur. Gardez ces chemins en tête quand vous raisonnez sur des invariants.

§1.5Les fonctionnalités preview

Une fonctionnalité preview est entièrement spécifiée, entièrement implémentée, mais provisoire. Elle est livrée pour recueillir des retours sur du code réel, et peut devenir permanente, changer ou disparaître. Le processus est décrit par le JEP 12 d'OpenJDK.

TypeNatureSpécifiée dansIntégrée à la spec
Langagesyntaxe ou sémantique nouvelledocument « diff » de la JLSseulement si previews activées à la compilation
Machine virtuellecomportement nouveau de la JVMdocument « diff » de la JVMSseulement si previews activées à l'exécution
APImodule, paquetage, classe, méthode, champ, constante d'enum de java.* / javax.*documentation de l'APIprésente, encadrée par le §1.5.1

Activer les previews

Terminal

java --enable-preview Main

# lanceur de fichier source
java --enable-preview --source 27 Main.java

# shell interactif
jshell --enable-preview
build.gradle.kts

tasks.withType<Test>().configureEach { jvmArgs("--enable-preview") }
tasks.withType<JavaExec>().configureEach { jvmArgs("--enable-preview") }
pom.xml (extrait)
<plugin>
  <artifactId>maven-compiler-plugin</artifactId>
  <configuration>
    <release>27</release>
    <compilerArgs><arg>--enable-preview</arg></compilerArgs>
  </configuration>
</plugin>
<plugin>
  <artifactId>maven-surefire-plugin</artifactId>
  <configuration><argLine>--enable-preview</argLine></configuration>
</plugin>
Règle · tout ou rien

Il est impossible d'activer une seule preview : --enable-preview active toutes celles de la version. L'option n'est acceptée qu'avec la version courante du JDK (--release 27 sur un JDK 27).

Piège de déploiement

Une classe compilée avec des previews est marquée dans son .class : version majeure de Java 27 (71) et version mineure 0xFFFF. La JVM refuse de la charger sans --enable-preview, et un JDK 28 la refusera aussi, car la preview a pu changer entre-temps.

§1.5.1Les règles d'usage à la compilation

La spec distingue quatre sortes de référence dans le code source et trois issues : une erreur, un avertissement preview, ou rien. Les avertissements preview peuvent être supprimés par @SuppressWarnings("preview") (§9.6.4.5). Testez les règles :

L'asymétrie de l'API réflexive. Utiliser une API preview réflexive ne provoque jamais d'erreur, même previews désactivées : les outils (IDE, processeurs d'annotations, frameworks) doivent pouvoir inspecter du code preview sans l'activer.

L'avertissement sur la syntaxe preview n'est pas exigé. La JLS encourage fortement les compilateurs à émettre un avertissement non supprimable pour chaque usage de syntaxe preview ; javac le fait sous forme de note.

Le même module est exempté. Le JDK doit pouvoir utiliser ses propres API preview en interne.

§1.5.2La preview de langage de Java SE 27

Java SE 27 définit une seule preview de langage : les types primitifs dans les motifs, instanceof et switch, en cinquième version preview.

JEP 455JDK 23
JEP 488JDK 24
JEP 507JDK 25
JEP 530JDK 26
JEP 532JDK 27

Un motif de type peut désormais être primitif, et instanceof vers un type primitif répond à la question « cette valeur se convertit-elle sans perte vers ce type ? ».

Java · preview
int n = 300;
if (n instanceof byte b) { }      // faux : 300 sort de -128..127, rien n'est tronqué
int m = 42;
if (m instanceof byte b) { }      // vrai : b vaut 42

double d = 3.0;
if (d instanceof int i) { }       // vrai : 3.0 → 3 sans perte
double e = 3.5;
if (e instanceof int i) { }       // faux : la partie décimale serait perdue

int grand = 16_777_217;
if (grand instanceof float f) { } // faux : 2^24 + 1 n'est pas représentable exactement en float
Java · preview
static String taille(long octets) {
    return switch (octets) {
        case 0L -> "vide";
        case long n when n < 1_024     -> n + " o";
        case long n when n < 1_048_576 -> (n / 1_024) + " Ko";
        case long n                    -> (n / 1_048_576) + " Mo"; // motif inconditionnel : exhaustif
    };
}

static String libelle(boolean ok) {
    return switch (ok) {
        case true  -> "succès";
        case false -> "échec";      // exhaustif sans default
    };
}

record NombreJson(double valeur) {}
// ne correspond que si valeur est un entier exact représentable en int
if (json instanceof NombreJson(int age)) { }
Note non normative

Les règles exactes (conversions inconditionnellement exactes, dominance, exhaustivité) sont dans le document de modifications publié avec la JLS 27. Elles touchent les §5.7, §14.11, §14.30 et §15.20.2 ; elles sont reprises dans les chapitres 5, 14 et 15.
