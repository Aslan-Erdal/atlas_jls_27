Chapitre 7 · Java SE 27 Edition

Paquetages et modules

Un programme Java est un ensemble de paquetages, regroupés en modules. Ce chapitre décrit les unités de compilation, les déclarations de paquetage, les cinq formes d'import, et les déclarations de modules qui contrôlent dépendances, encapsulation et services.

Source : JLS SE 27, chapitre 7 Sections : 7.1 à 7.7

§7.1Membres d'un paquetage

Les membres d'un paquetage sont ses sous-paquetages et toutes les classes et interfaces de plus haut niveau déclarées dans ses unités de compilation. Un paquetage ne peut pas contenir deux membres de même nom : une classe a.b et un sous-paquetage a.b sont incompatibles.

Règle

La hiérarchie des noms de paquetages n'a aucune signification pour l'accès. java.util et java.util.concurrent sont deux paquetages indépendants ; importer l'un n'importe pas l'autre, et les membres à accès paquetage de l'un ne sont pas visibles dans l'autre.

Les paquetages de la plateforme commencent par java. ou javax.. Un programme ordinaire ne peut pas déclarer de paquetage java.* : le module java.base les possède déjà, et un paquetage ne peut appartenir qu'à un module.

§7.2Le système hôte

La spec ne dit pas où sont stockés les modules, paquetages et unités de compilation : c'est l'affaire du système hôte. En pratique, avec le JDK, on utilise le système de fichiers : un paquetage correspond à un répertoire, une unité de compilation à un fichier .java, un module à un répertoire contenant module-info.java ou à un JAR modulaire.

Arborescence typique
src/
└── com.exemple.app/                 # module (convention : nom du module)
    ├── module-info.java
    └── com/exemple/app/             # paquetage com.exemple.app
        ├── Main.java
        └── internal/                # paquetage com.exemple.app.internal (indépendant)
            └── Outil.java

Un hôte peut imposer des règles supplémentaires ; javac impose qu'une classe public (ou référencée depuis d'autres fichiers) soit dans un fichier qui porte son nom (§7.6).

§7.3Unités de compilation

Une unité de compilation est le symbole but de la grammaire syntaxique (§2.3). Il en existe trois formes :

FormeContenuExemple
Ordinairedéclaration de paquetage facultative, imports, déclarations de classes et interfaces de plus haut niveauMain.java
Modulaireimports, puis une déclaration de modulemodule-info.java
Compacteimports et déclarations de champs et de méthodes au niveau le plus haut, qui forment une classe implicitement déclarée (§8.1.8)Hello.java avec void main()
Règles · imports implicites

Toute unité de compilation importe implicitement les types publics de java.lang (comme import java.lang.*;).

Une unité de compilation compacte importe en plus, implicitement, le module java.base tout entier (comme import module java.base;, §7.5.5) : List, Map, Path… sont disponibles sans import. La classe java.lang.IO fournit IO.println et IO.readln.

Notes.java · unité compacte (Java 25+)
List<String> notes = new ArrayList<>();     // List et ArrayList : import module java.base implicite

void main() {
    String n = IO.readln("Note : ");
    notes.add(n);
    IO.println(notes);
}

§7.4Déclarations de paquetage

§7.4.1Paquetages nommés

La déclaration package a.b.c; en tête d'une unité ordinaire indique le paquetage de ses types. Des annotations ne peuvent être placées sur une déclaration de paquetage que dans un fichier dédié, package-info.java, qui sert aussi à porter la Javadoc du paquetage.

package-info.java
/** Calcul des factures et des taxes. */
@NullMarked
package com.exemple.facturation;

import org.jspecify.annotations.NullMarked;

§7.4.2Le paquetage sans nom

Une unité sans déclaration de paquetage appartient à un paquetage sans nom. Il est prévu pour les petits programmes et les essais. Ses types ne peuvent pas être importés depuis un paquetage nommé, ce qui les rend inutilisables comme bibliothèque.

§7.4.3Observabilité et visibilité

Une unité de compilation est observable si le système hôte la fournit au compilateur. Un paquetage est observable si au moins une unité qui le déclare est observable, ou si un de ses sous-paquetages l'est. Un paquetage est visible dans un module M s'il est déclaré dans M ou dans un module que M lit et qui l'exporte vers M. Il doit être uniquement visible : deux modules lus par M qui contiennent le même paquetage sont une erreur (« split package »).

§7.5Déclarations d'import

Un import permet de désigner un type ou un membre statique par son nom simple au lieu de son nom qualifié. Il ne charge rien et n'a aucun coût à l'exécution : c'est un raccourci de nommage valable dans une unité de compilation.

§7.5.1Import de type simple

Règles

Le type doit exister et être accessible. Deux imports simples de types différents de même nom simple sont une erreur ; un import simple d'un type qui a le même nom qu'un type déclaré dans l'unité aussi. Un import simple masque les types de même nom importés à la demande et ceux du paquetage courant.

Java
import java.util.Date;
import java.sql.Date;       // ERREUR : deux imports simples nommés Date
import java.util.*;         // n'importe PAS java.util.concurrent.*
import java.util.Map.Entry; // import d'un type membre : permis
class Date { }              // ERREUR si java.util.Date est importé simplement

§7.5.2Import de types à la demande

import p.*; rend disponibles tous les types accessibles de p, mais seulement s'ils ne sont pas masqués par un type de même nom déclaré dans l'unité, importé simplement, ou membre du paquetage courant. Deux imports à la demande qui fournissent le même nom ne sont une erreur que si ce nom est utilisé.

§7.5.3Import statique simple

import static T.n; importe tous les membres statiques accessibles nommés n de T : champs, méthodes (toutes les surcharges), types membres. Une méthode importée statiquement est masquée par une méthode de même nom déclarée ou héritée dans la classe courante, quel que soit le nombre de paramètres.

§7.5.4Import statique à la demande

import static T.*; importe tous les membres statiques accessibles de T. Pratique pour les constantes et les méthodes utilitaires (org.junit.jupiter.api.Assertions.*), mais à utiliser avec parcimonie : le lecteur ne sait plus d'où viennent les noms.

Java
import static java.lang.Math.*;
import static java.util.stream.Collectors.toList;

double r = sqrt(pow(3, 2) + pow(4, 2));   // 5.0
class Calcul {
    static int max(int[] t) { ... }
    void f() { max(1, 2); }               // ERREUR : max(int[]) de la classe masque Math.max
}

§7.5.5Import de module

Finalisé en Java 25 (JEP 511), import module M; importe à la demande toutes les classes et interfaces publiques de plus haut niveau de tous les paquetages que M exporte vers le module courant, ainsi que de ceux exportés par les modules que M exige transitivement (requires transitive).

Règles · priorités

Un import de module est le plus faible : il est masqué par les types déclarés dans l'unité, par les imports simples, par les types du paquetage courant et par les imports de paquetage à la demande. Si deux imports de modules fournissent le même nom simple et que ce nom est utilisé, c'est une erreur d'ambiguïté, que l'on résout par un import simple.

Java
import module java.base;      // java.util, java.io, java.nio.file, java.time…
import module java.desktop;   // java.awt, javax.swing…

List<String> l;               // ERREUR : java.util.List et java.awt.List sont ambigus
// Correction :
import java.util.List;        // un import simple masque les imports de modules

import module java.sql;       // java.sql requires transitive java.xml et java.logging :
                              // org.w3c.dom.Document et java.util.logging.Logger sont aussi importés
Note non normative

Dans le même mouvement, Java 25 a permis requires transitive java.base afin que le module agrégateur java.se l'exige transitivement : import module java.se; importe ainsi toute l'API publique de la plateforme, java.base compris.

§7.6Classes et interfaces de plus haut niveau

Leur portée est l'ensemble des unités du paquetage (§6.3). Deux types de plus haut niveau de même nom dans le même paquetage sont une erreur. Une déclaration de plus haut niveau peut être public ou sans modificateur d'accès ; protected, private et static sont interdits à ce niveau. Des ; supplémentaires entre les déclarations sont tolérés.

Règle d'hôte (javac)

Si un type est public, ou s'il est référencé depuis d'autres unités du paquetage, et que le système stocke les paquetages dans des fichiers, alors le type doit être déclaré dans un fichier nommé Nom.java. Il y a donc au plus une classe publique par fichier.

§7.7Déclarations de modules

Un module est un ensemble nommé de paquetages, décrit par module-info.java. Sa déclaration exprime cinq choses : ce qu'il exige, ce qu'il exporte, ce qu'il ouvre à la réflexion, les services qu'il utilise et ceux qu'il fournit.

module-info.java
open module com.exemple.app {          // open : tous les paquetages ouverts à la réflexion
    requires com.exemple.lib;           // dépendance
    requires transitive java.sql;       // dépendance relayée aux modules qui exigent app
    requires static lombok;             // obligatoire à la compilation, facultative à l'exécution

    exports com.exemple.app.api;                     // accessible à tous les modules qui lisent app
    exports com.exemple.app.spi to com.exemple.plug; // export qualifié

    uses com.exemple.lib.Codec;                       // consomme un service
    provides com.exemple.lib.Codec
        with com.exemple.app.Base64Codec;            // fournit une implémentation
}

Les mots module, open, requires, transitive, exports, opens, to, uses, provides et with sont des mots-clés contextuels (§3.9) : ils restent utilisables comme identifiants ailleurs.

Règles

Tout module dépend implicitement de java.base. Exiger deux fois le même module, ou créer un cycle de requires, est une erreur de compilation.

Utilisez requires transitive quand votre API publique expose des types d'un autre module : si une méthode exportée renvoie un java.sql.Connection, vos clients doivent lire java.sql.

Les formes qualifiées exports p to M1, M2; et opens p to M; restreignent l'accès aux modules nommés. opens sert typiquement aux frameworks (JPA, Jackson, Spring) qui doivent lire des champs privés par réflexion sans que le code client y ait accès à la compilation. Un open module ne peut pas contenir de directive opens.

§7.7.3Consommation de services

uses S; déclare que le module cherche des implémentations du service S, une interface ou classe abstraite, via java.util.ServiceLoader. Le type S doit être accessible.

§7.7.4Fourniture de services

provides S with I1, I2; déclare des implémentations. Chaque fournisseur doit être dans le module, et soit déclarer une méthode public static sans paramètre nommée provider qui renvoie un sous-type de S, soit être une classe publique concrète, sous-type de S, avec un constructeur public sans paramètre. Le paquetage du fournisseur n'a pas besoin d'être exporté.

Java · côté consommateur
ServiceLoader<Codec> loader = ServiceLoader.load(Codec.class);
for (Codec c : loader) System.out.println(c.nom());   // instancie les fournisseurs trouvés
Optional<Codec> premier = loader.findFirst();

§7.7.5Modules sans nom

Le code chargé depuis le classpath appartient au module sans nom de son chargeur de classes. Ce module lit tous les autres modules et exporte tous ses paquetages. Une unité ordinaire hors de tout module y appartient. Un module nommé, lui, ne peut pas exiger le module sans nom : il n'a pas de nom.

Note non normative

Entre les deux, la plateforme propose les modules automatiques : un JAR non modulaire placé sur le module path devient un module nommé d'après le JAR (ou l'entrée Automatic-Module-Name de son manifeste), qui lit tout et exporte tout. C'est la voie de migration progressive vers les modules.

§7.7.6Observabilité d'un module

Un module est observable si sa déclaration (ou un module automatique équivalent) est fournie par le système hôte. Deux modules observables de même nom ne peuvent pas être utilisés ensemble, et un même paquetage ne peut pas être dans deux modules lus par un même module.
